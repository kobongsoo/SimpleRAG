인덱싱 속도 개선 설계서 — 전체 인덱싱은 스레드 · 겹치기 · 단계형으로, 증분 인덱싱은 BM25 를 고쳐서

인덱싱 시간은 상황에 따라 잡아먹는 곳이 다르다. 처음(전체) 인덱싱은 시간의 대부분이 벡터 생성이고, 문서 몇 건을 넣거나 고치는 증분 인덱싱(자동 인덱싱)은 시간의 대부분이 BM25 전체 재구축이다. 그래서 두 갈래로 나눠 고친다 — ① 전체 인덱싱: 다음 문서의 파싱 · 청킹을 임베딩과 겹치고, CPU 임베딩 스레드 수를 장시간 측정으로 정하며, BM25 를 먼저 만들어 바로 검색되게 하고 벡터는 뒤에서 채우는 단계형 인덱싱으로 "검색 가능까지"를 66분 → 약 6분으로 줄인다. 가장 효과가 큰 OpenVINO iGPU 임베딩(약 2.1배)은 모델 파일을 하나 더 넣어야 해 배포 용량이 약 335MB 늘어나므로 보류하고 추후 고려 사항(§8)으로 둔다. ② 증분 인덱싱: BM25 를 바뀐 부분만 고치게 하고, 수정된 문서는 바뀐 청크만 다시 임베딩한다.

1부 전체 인덱싱 — 지금 모델 · 엔진(onnxruntime CPU int8)은 그대로 두고, 배포 변경 없이 넣을 수 있는 두 가지를 한다. ① 다음 문서의 파싱 · 청킹을 임베딩과 겹친다(최대 약 7%). ② CPU 임베딩 스레드를 4 → 8로 올린다 — 이 PC 장시간 측정(2026-10-30)에서 평균 1.30배 · 가장 고르게 빨라 확정, 다른 PC 도 측정 없이 8 을 쓴다.

단계형 인덱싱 — 문서를 많이 넣을 때(500청크 넘음)는 파싱 · 청킹 · 메타 · BM25 까지만 먼저 끝내 약 6분 만에 검색되게 하고, 벡터는 뒤에서 조금씩 채운다(질문이 오면 비켜 줌). 벡터 없이 BM25+동의어만으로 답한 RAGAS 측정에서 문서 용어 질문은 지금과 같았고(골든 0.767 → 0.782), 일상어 질문은 벡터가 채워질수록 지금 품질(일반어 CR 0.62 → 0.76)로 돌아온다. 일의 양은 같고 순서만 바뀐다.

보류 — OpenVINO iGPU 임베딩 — 이 PC 에서 벡터 생성이 약 2.1배 빨랐지만, iGPU 는 int8 모델을 가속하지 못해 fp16 모델 파일(약 235MB)과 OpenVINO DLL(약 100MB)을 더 넣어야 한다(배포 약 +335MB). 모델이 둘이 되면 벡터 계열도 둘로 나뉜다. 그래서 이번에는 넣지 않고 추후 고려 사항(§8)으로 둔다. 측정 · 설계 내용은 §8 에 그대로 남긴다.

2부 증분 인덱싱 — BM25 를 3단계로 고친다: A) 토큰화 병렬(바로 효과) → B) 청크별 토큰 저장(토큰화 0) → C) 세그먼트형 BM25(새 청크만 덧붙이고 가중치는 질의 때 계산, 재구축 0). 함께 수정 문서의 벡터 재사용을 넣는다.

⚠️ 정정 — 앞선 검토에서 "운영 규모 BM25 재구축 112.7초"로 보고했으나, 그 값은 bge-m3 측정이 동시에 돌던 상태였다. 단독으로 다시 재면 36~49초(실제 증분 인덱싱 1건 실행 36.2초 · 단독 측정 49.2초, 발열 상태에 따라 다름)다. 이 설계서는 새 수치를 쓴다.

3-1. 파싱 · 청킹과 임베딩 동시 진행 모든 PC

지금은 문서 하나를 파싱 → 청킹 → 임베딩 → 메타 → 저장 순서로 끝내고 다음 문서로 간다. 임베딩하는 동안 파싱은 놀고, 파싱하는 동안 임베딩은 논다. 임베딩 외 단계(파싱 3.8 · 청킹 2.6 · 메타 1.2 · DB 0.2 = 1쪽당 7.8ms, 전체의 약 7%)를 앞 문서의 임베딩과 겹치면 그만큼 숨는다.

  • Python 판: 파서 · onnxruntime 이 계산 중에 GIL 을 놓으므로 스레드로 충분할 것으로 본다. 효과가 안 나오면 준비를 프로세스로 옮긴다 측정 후 결정.

결과 읽기

  • 60초 식힘으로는 발열이 다 빠지지 않는다. 각 바퀴에서 늦게 돈 쪽이 크게 느려졌다(1바퀴 12스레드 46.4 · 2바퀴 4스레드 33.4). 이 노트북은 1분 넘게 돌리면 전력 · 열 한도에 걸린다.
  • 그 속에서 8스레드만 순서와 상관없이 60~66 청크/초로 고르게 나왔다(마지막에 돈 3바퀴에서도 66.4). 4스레드는 처음에 돌면 가장 빨랐지만(71.9) 늦게 돌면 절반 이하로 떨어졌다.
  • 실제 전체 인덱싱은 수십 분 동안 계속 도는 "발열이 쌓인 상태"이므로, 최고값보다 흔들림이 작은 쪽이 실제 시간을 더 잘 나타낸다 — 8 을 고른 근거다.
  • Python 판 onnxruntime(1.26)으로 쟀다. Rust 판(onnxruntime.dll)도 같은 엔진이라 경향은 같을 것으로 보지만, 구현 때 Rust 판으로 한 번 확인한다.
  • 아직 하지 않은 것: ① 의 "확인"(운영 규모 전체 인덱싱을 8스레드로 한 번 돌려 실제 단축 기록 — 약 1시간)은 구현 뒤 한다. 아래 §3-4 의 8스레드 줄은 그때까지 이 측정의 평균 배수(1.30배)로 계산한 추정이다.
  • 실행 중 자동 측정은 하지 않는다. 이유:
    • 문서가 적은 인덱싱(예: 청크 1,000개 → 4스레드로 약 15초)은 1분짜리 측정이 이득(8스레드여도 몇 초)보다 훨씬 크다.
    • 몇 초짜리 짧은 측정은 발열 상태에 따라 판정이 뒤집힌다(같은 설정이 57~92 청크/초로 흔들림) — 짧게 재서 고르는 방식은 믿을 수 없다.
    • 스레드 수는 벡터를 바꾸지 않으므로 잘못 골라도 손해는 "조금 느림"뿐이다. PC 마다 재서 고를 만큼의 이득이 없다.
  • 설정으로 뺀다: embed.threads: auto | 4 | 8 …. auto = ① 에서 정한 기본값 8(물리 코어 수를 넘지 않게). 특정 PC 에서 느리면 사용자가 직접 숫자를 넣어 바꾼다.
  • 전체 인덱싱에만 적용한다. 자동(증분) 인덱싱은 사용자가 다른 일을 하는 중에 돌므로 지금처럼 4스레드로 두어 PC 가 무거워지지 않게 한다.
  • 질문 임베딩 · 리랭커는 그대로 4스레드. 지금 리랭커 스레드가 임베딩 상수를 따라가므로(RERANK_THREADS = EMBED_THREADS) 둘을 떼어 놓는다 — 질문 응답 속도는 따로 측정된 값이 있어 건드리지 않는다.
  • 벡터는 스레드 수와 상관없이 같다(실측 코사인 1.0) — 재인덱싱 필요 없음.

3-5-3. 저장 구조 — "벡터 대기" 청크

  • Rust 판(points.sqlite): vec 칸에 길이 0 인 값을 넣어 "벡터 대기"로 둔다. 표 정의(vec BLOB NOT NULL)는 빈 값도 받으므로 표를 바꾸지 않는다. 옛 인덱스는 대기 청크가 없을 뿐 그대로 읽힌다.
  • Python 판(Qdrant local): 점에는 벡터가 반드시 있어야 하므로, 대기 청크는 자리 표시 단위 벡터와 payload vec_pending: true 로 넣고, 벡터 검색에서 vec_pending 인 점을 거른다(must_not 필터). 2단계에서 벡터를 넣고 표시를 지운다.
  • 대기 청크도 payload(본문 · 문서 · 쪽 · 절 …)는 처음부터 다 있으므로 BM25 · 리랭커 · 근거 표시 · 정밀 모드 이웃 청크 · 탐색기 모드 · 메타데이터 검색은 그대로 동작한다.
  • 상태 파일(index_state.json)은 지금처럼 1단계 끝에 문서를 "반영됨"으로 적는다. "벡터가 남았는가"는 저장소의 대기 청크 수가 기준이다 — 따로 적지 않아 둘이 어긋날 일이 없다.

3-5-4. 검색 — 대기 청크는 BM25 로만

  • 벡터 검색(dense)은 대기 청크를 건너뛴다(Rust VectorStore::search 에서 빈 벡터 제외 · Python 은 위 필터). 벡터가 없는 점을 0점으로 줄 세우지 않게 한다.
  • BM25(동의어 넓힘) 후보에는 대기 청크도 들어가고, RRF · 리랭커 · 근거 3건 고르기는 지금과 같다. 리랭커는 본문만 보므로 대기 청크도 똑같이 점수 낸다.
  • 2단계 도중에는 벡터가 있는 청크만 dense 후보가 된다 — 채워질수록 지금 검색으로 다가간다.

3-5-5. 2단계 — 벡터 채우기

명령줄 index (워커가 없을 때)

  1. 1단계를 모든 문서에 대해 끝내고 BM25 · 상태 파일을 저장한다 — "검색 가능 · 벡터 채우는 중 0 / 186,919" 를 찍는다.
  2. 이어서 같은 실행에서 대기 청크를 배치 8 로 채운다(진행률 · 남은 시간 표시).
  3. 도중에 끊겨도 대기 청크는 저장소에 남으므로 다음 index 나 워커가 이어 채운다.

RAGSearchBox 워커 (자동 인덱싱)

  1. 새 명령 /embed-pending {"max": 64} — 대기 청크 최대 64개를 채우고 남은 수를 돌려준다(4스레드로 약 1초).
  2. 메인 스레드(jobs.rs tick)가 질문을 처리하지 않을 때만 이 명령을 보낸다 — 질문이 오면 1초 안에 비켜 준다.
  3. 남은 수가 0 이 되면 멈춘다. 워커를 다시 띄우면 시작할 때 대기 청크 수를 보고 이어 간다.
  • 채우는 순서: 먼저 넣은 문서부터(id 순). 문서 하나를 끝까지 채운 뒤 다음 문서로 가서, 채워진 문서가 하나씩 늘어나게 한다.
  • 스레드: §3-2 규칙 그대로 — 명령줄 전체 인덱싱은 8, 자동 인덱싱은 4.
  • 배치 구성: 문서 경계를 넘어 8개씩 묶일 수 있다. int8 벡터가 배치 구성에 따라 미세하게 달라지는 것(코사인 0.99 수준)은 §4-5 벡터 재사용과 같은 수준이라 검색에 영향이 없다고 보고 §6 시험으로 확인한다.

3-5-6. 언제 단계형으로 하나

  • 한 번의 인덱싱에서 새로 임베딩할 청크가 index.defer_vectors_over(기본 500청크 ≈ 4스레드 7초)를 넘을 때만 단계형으로 한다.
  • 그 이하(자동 인덱싱의 문서 몇 건)는 지금처럼 그 자리에서 바로 임베딩한다 — 몇 초짜리 일에 "대기" 상태를 만들지 않는다.
  • 대표적으로 쓰이는 때: 처음 인덱싱 · --rebuild · 폴더를 새로 지정해 문서가 한꺼번에 들어올 때.

4-2. 단계 A — 토큰화 병렬 바로 효과 · 형식 그대로

  • bm25.build 안의 청크별 토큰화(전체의 약 60%)를 스레드 N개로 나눈다(N = 물리 코어 수, 상한 8).
  • 실측: 토큰화 29.6초 → 8스레드 11.8초(2.5배). BM25 전체 약 49초 → 약 31초(약 −35%).
  • 결과 파일은 바이트까지 같아야 한다 — 단어 번호를 "첫 등장 순서"로 매기므로, 병렬로 토큰화한 뒤 합칠 때는 청크 순서대로 번호를 매긴다.

4-3. 단계 B — 청크별 토큰 결과 저장 토큰화 0

  • 청크를 넣을 때(sync_doc 4단계) 그 청크의 단어별 빈도를 함께 저장한다 — points.sqlite 에 표 bm25_tf(id, terms BLOB). 청크 100개 토큰화는 수십 ms 라 문서 처리 시간에 거의 영향이 없다.
  • 청크를 지울 때(delete_doc_except · delete_ids) 같이 지운다. 복사 · 이동(copy_doc · move_doc)은 원본 것을 베낀다.
  • BM25 재구축은 이 표만 읽어 역색인을 만든다 — 토큰화(약 60%)가 사라진다. 남는 것은 역색인 정렬 · 가중치 계산 · 저장(단독 측정 약 20초).
  • 옛 인덱스(표가 없음): 처음 한 번 빠진 청크만 토큰화해 채운다(이 한 번은 단계 A 의 병렬로).
  • 토크나이저가 바뀌면(모델 교체) 표를 비운다 — chunk_params 의 계열 값으로 판단.

4-4. 단계 C — 세그먼트형 BM25 재구축 0

가중치를 미리 계산해 저장하지 않고, 단어 빈도(tf)만 저장해 두었다가 질의 때 지금의 N · 평균 길이 · df 로 가중치를 계산한다. 그러면 전체 통계가 바뀌어도 다시 만들 필요가 없다. 점수 공식은 지금과 같다(k1 · b 그대로).

저장 구조

  • 본 세그먼트: 단어 → (청크, tf) 목록 · 청크 길이 — 전체 인덱싱 때 만든다
  • 덧붙임 세그먼트: 그 뒤 새로 넣은 청크들(같은 모양, 작음)
  • 지움 표시: 지운 청크 id 모음
  • 전체 통계(N · 길이 합)는 따로 숫자 두 개로 들고 다닌다

동작

  • 문서 추가: 새 청크를 덧붙임 세그먼트에 넣고 통계를 더한다 — ms 단위
  • 문서 삭제 · 수정: 옛 청크를 지움 표시, 새 청크는 덧붙임 — ms 단위
  • 질의: 질의 단어의 목록만 두 세그먼트에서 읽어, 지운 청크는 빼고 df 를 세어 가중치 계산
  • 합치기: 덧붙임이 전체의 5% 를 넘거나 지움이 5% 를 넘으면, 한가할 때(자동 인덱싱 쉬는 동안) 본 세그먼트로 합친다. 전체 인덱싱 때도 합친다
  • 점수는 전체 재구축과 똑같아야 한다 — 지운 청크를 빼고 df 를 세므로 통계가 정확하다(§6 시험).
  • 질의 비용: 질의 단어 몇 개의 목록만 훑는다. 흔한 단어는 목록이 길 수 있어 질의 시간 증가를 시제품에서 잰다(목표 +10ms 이내) 미측정.
  • 동의어 넓힘(synonyms)으로 질의 단어가 늘어도 같은 방식으로 계산된다.
  • 파일 형식이 바뀌므로 매직 값을 올린다(SRBM25\0\x03). 옛 파일은 처음 한 번 새 형식으로 만든다.

4-5. 수정 문서의 벡터 재사용

문서를 고치면 지금은 그 문서의 청크를 전부 다시 임베딩한다. 절 경계로 자르는 청킹이라, 한 군데를 고쳐도 대부분의 청크 글은 그대로다.

  • 청킹은 문서 전체를 다시 한다 — 1쪽당 2.6ms 라 비용이 거의 없다. 비싼 것은 임베딩이므로, 다시 자른 청크 가운데 옛 버전과 글이 똑같은 청크의 벡터만 재사용한다.
  • 청크마다 해시값으로 비교한다.
    • 청크를 저장할 때 청크 글(접두 [문서명 > 절] 포함, 임베딩에 넣는 글 그대로)의 SHA-1 해시를 payload 에 chunk_hash 로 함께 남긴다.
    • 문서가 바뀌면 다시 청킹한 새 청크마다 해시를 계산하고, 그 문서의 옛 청크 해시 → 점 id 표와 맞대어 본다.
    • 해시가 같은 청크는 그 id 의 벡터를 저장소에서 꺼내 쓰고(points_of), 해시가 없는 청크만 임베딩한다. 같은 해시가 여러 번 나오면(같은 글이 반복되는 청크) 개수만큼만 짝짓는다.
    • 해시로 비교하므로 옛 청크 글 전체를 다시 읽어 비교할 필요가 없다. SHA-1 이 우연히 겹칠 가능성은 무시할 수준이다(이미 문서 내용 해시에 같은 방식을 쓴다).
    • 해시 계산 비용은 무시할 수준이다 — 운영 인덱스 18.7만 청크(71MB) 전체 SHA-1 이 0.16초, 청크당 약 0.9μs(Python 실측). 청크 100개 문서는 0.1ms, 1,376청크 문서도 1.2ms 다. 임베딩은 청크당 약 15ms 라 해시는 그 1만분의 1도 안 된다. 저장 공간은 청크당 40글자(16진수) — 18.7만 청크에 약 7.5MB(지금 저장소 982MB 의 1% 미만).
    • chunk_hash 가 없는 옛 인덱스는 payload 에 남아 있는 청크 글(text)로 그 자리에서 해시를 계산해 비교한다 — 재인덱싱이 필요 없다.
  • 인덱스의 청킹 설정 · 모델(chunk_params)이 지금과 같을 때만 재사용한다(다르면 어차피 증분 인덱싱이 거부된다).
  • 배치 구성이 달라지면 int8 벡터가 미세하게 달라진다(같은 글도 함께 묶인 글에 따라 코사인 0.99 수준). 재사용 벡터는 "같은 글을 다른 배치로 만든 벡터"와 같은 수준의 차이라 검색에 영향이 없다고 본다 — §6 시험으로 확인.

연쇄가 문서 전체로 번지지 않는 이유 — 청커 구조 때문이다.

  • 긴 절(128토큰 넘음)은 그 절 안에서 문단 단위로 채워 자른다. 글이 늘면 그 절의 수정 지점 뒤 청크까지만 밀린다. 다음 절은 절 시작에서 경계를 새로 잡으므로 그대로다.
  • 짧은 절들은 여러 개를 한 청크로 묶는다. 한 절이 길어지면 묶음이 바뀌어 뒤로 번질 수 있지만, 다음 긴 절이 나오면 묶음이 다시 시작되어 멈춘다.

연쇄가 커지는 경우 — 재사용률이 떨어지지만 틀린 결과가 나오지는 않는다(바뀐 청크는 새로 임베딩).

  • 제목(번호) 인식이 안 되는 문서: 문서 전체가 절 하나로 잡히면 수정 지점부터 문서 끝까지 밀린다.
  • 긴 절의 앞부분 수정: 그 절의 거의 모든 청크가 바뀐다(이번 실험은 문서 한가운데만 고쳤다).
  • 절 제목 수정: 모든 청크 앞에 [문서명 > 절] 접두가 붙으므로 그 절 아래 청크가 모두 바뀐다 — 내용이 실제로 바뀐 것이라 다시 임베딩이 맞다.
확인 필요 — 청탁금지법 해설집(1,127청크)은 고친 문단이 어느 청크에도 들어가지 않아 "다시 임베딩 0" 이 나왔다. 머리글처럼 청크에서 빠지는 블록을 고른 것으로 보이며, 원인은 아직 확인하지 않았다. 실험 도구 · 결과: results/vec_reuse/reuse_sim.py · result.txt.

4-5-2. 보완안 — 내용 기준 경계 보류

경계를 "앞에서부터 128토큰씩 채운 위치"가 아니라 문단 내용으로 정하면(content-defined chunking — 문단 글의 해시 등으로 끊을 자리를 고름), 수정 지점 뒤에서 경계가 곧 원래 자리로 돌아와 연쇄가 더 짧아진다.

  • 보류 이유: 청킹 결과 자체가 바뀌어 전체 재인덱싱 · 검색 품질 재측정(골든셋)이 필요하다. 지금도 97% 이상 재사용되어 더 얻을 것이 몇 % 뿐이다.
  • 다시 볼 때: 제목 인식이 안 되는 큰 문서(절 하나짜리)를 자주 고치는 사용 패턴이 확인되면, 그런 문서에만 적용하는 방안을 검토한다.

8추후 고려 — OpenVINO iGPU 임베딩 (보류)

보류 (2026-10-30) — 측정상 전체 인덱싱을 가장 크게 줄이는 방안(벡터 생성 약 2.1배, 운영 규모 약 66분 → 약 24분)이지만 모델 파일을 하나 더 넣어야 해 배포 용량이 커져 이번에는 넣지 않는다. 아래 측정 · 설계는 재검토할 때 그대로 쓰도록 남긴다.

8-1. 보류 사유와 재검토 조건

사유내용
모델이 2개 필요지금 모델은 int8 ONNX(118MB)다. iGPU 는 int8 을 가속하지 못해(1.6 청크/초) fp16 모델(약 235MB, 추정)을 따로 넣어야 한다. 반대로 fp16 하나로 통일하면 iGPU 가 없는 PC 의 CPU 임베딩이 3~4배 느려진다(fp32 CPU 실측 약 20 청크/초). 그래서 하나로 합칠 수 없다.
배포 용량fp16 모델 약 235MB + OpenVINO DLL 약 100MB = 약 +335MB. 지금 배포의 임베딩 관련 파일(모델 118MB + onnxruntime 18MB)보다 크다.
벡터 계열이 둘로int8 과 fp16 벡터는 일치도 0.95 로 섞을 수 없다. 인덱스마다 계열을 적고, 질문도 같은 계열로 임베딩하고, 계열을 바꿀 때는 전체 재인덱싱이 필요하다.
효과가 PC 에 따라 다름인텔 GPU 전용이고(AMD iGPU 는 GPU 장치 없음), 인텔 안에서도 UHD 계열은 CPU 보다 느릴 수 있어 측정 · 판정 · 폴백 장치가 함께 필요하다.

다시 볼 때 — 다음 중 하나가 생기면 재검토한다.

  • 전체 인덱싱 시간이 운영상 문제가 될 때(예: 문서가 크게 늘어 1~2시간을 넘김), §3 두 방안으로 부족할 때.
  • 배포 용량 여유가 생길 때 — 예: "iGPU 가속 팩"을 선택 설치로 따로 내려받게 하는 배포 경로가 생길 때.
  • 임베딩 모델을 바꿀 때(어차피 전체 재인덱싱 · 새 모델 배포) — 그때 fp16 하나로 iGPU · CPU 를 함께 쓰는 구성을 다시 잰다.
  • 모델 크기를 줄일 방법이 확인될 때 — 크기의 대부분은 단어 표(약 25만 × 384)라, 단어 표만 int8 로 두고 나머지를 fp16 으로 하는 혼합 구성 등.

8-3. 원칙 — "확실히 빨라질 때만" (답변 생성 Vulkan 선택과 같은 구조)

OpenVINO 의 GPU 가속은 인텔 GPU 전용이고, 인텔 안에서도 iGPU 성능 차이가 크다 (Iris Xe 실행 유닛 80~96개 · 흔한 UHD 620/730/770 은 24~32개 · Iris Xe 도 메모리 한 채널이면 UHD 모드). 그래서 지금 generate/backend.rs 가 하듯이 PC 마다 처음 한 번 재고, 결과를 저장해 두고, 다시 쓴다.

측정 (자식 프로세스 simplerag-rs _probe-embed)

  1. OpenVINO DLL · 모델(IR fp16)이 있는지, GPU 장치가 잡히는지 먼저 본다. 없으면 측정 없이 CPU.
  2. 고정 시험 글 256개(동봉, 실제 청크 길이 분포와 비슷하게)를 CPU int8 · iGPU fp16 으로 각각 임베딩해 청크/초를 잰다. 예열 1회 뒤.
  3. 같은 글 64개를 CPU fp32 기준과 비교해 iGPU 벡터의 코사인을 잰다(DirectML 처럼 "빠르지만 틀린" 경우를 거른다).
  4. 자식 프로세스에서 재는 이유: 그래픽 드라이버 문제로 죽어도 본 프로세스는 살아야 한다(지금 _probe-backend 와 같은 이유).

판정

  • iGPU 측정 실패 → CPU (사유 기록)
  • iGPU 코사인 < 0.999 → CPU ("벡터가 맞지 않음")
  • iGPU ÷ CPU < EMBED_GPU_MIN_SPEEDUP(1.5) → CPU
  • 그 밖 → iGPU(OpenVINO)

문턱을 답변 생성(1.3배)보다 높게 1.5배로 두는 이유: 엔진을 바꾸면 전체 재인덱싱이 필요하고, CPU 측정값이 발열로 57~92 청크/초까지 흔들려 1.3배 근처는 판정이 뒤집힐 수 있다.

저장 키(이 값이 같아야 저장된 측정을 다시 쓴다): 컴퓨터 이름 · GPU 이름 · 그래픽 드라이버 버전 · OpenVINO 버전 · 모델 파일 크기·날짜 · 문턱값. 드라이버나 모델이 바뀌면 다시 잰다. backend --embed --reprobe 로 강제 재측정.

8-4. 엔진은 인덱스마다 고정 — 벡터 계열

8-7. 연결 방식

  • Rust 판: OpenVINO C API(openvino_c.dll)를 실행 시점에 적재해 쓴다 — 지금 pdfium.dll · onnxruntime.dll 을 다루는 방식과 같다. onnxruntime 의 OpenVINO EP 는 쓰지 않는다: 버전이 서로 맞아야 하고(시험 중 1.24 ↔ 2026.4 에서 Error 127), 묶음이 커진다.
  • Python 판: openvino 패키지의 Core().compile_model(..., "GPU"). 측정 · 판정 · 저장 파일 모양은 Rust 판과 같게.
  • 새 모듈: embed/openvino.rs(embed/openvino_embedder.py) — 지금 Embedder 와 같은 함수(embed_passages · embed_query · tokenizer)를 낸다. 토크나이저는 지금 것을 그대로 쓴다(tokenizer.json 같음).

8-8. 답변 생성(sLLM)과 iGPU 경합

sLLM 도 iGPU(Vulkan)를 쓴다. 인덱싱 중에 질문하면 둘이 iGPU 를 나눠 쓰게 된다 미측정.

  • 원칙: 질문이 먼저. 워커가 답변을 만드는 동안에는 인덱싱이 배치 사이에서 기다린다(배치 8개 ≈ 60ms 단위로 끊을 수 있음).
  • 시제품에서 "인덱싱 중 TTFT" 를 재서, 늘어남이 0.3초를 넘으면 위 양보를 넣는다.
