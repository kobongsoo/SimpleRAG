문서 업로드 설계서 — 올린 문서에서만 찾아 답하기

입력란의 [+] 로 문서 파일을 올리면, 그 대화의 질문은 올린 문서에서만 찾아 답한다. 올린 문서의 인덱스는 인덱싱 폴더의 인덱스(Qdrant · BM25 · 상태 파일)와 섞지 않고 대화마다 따로 두며, 대화 기록에서 그 대화를 지우면 인덱스와 올린 파일도 함께 지운다. 지금 구조를 살펴 어디에 무엇을 두는지, 두 판(Python · Rust)을 어떻게 맞추는지, 무엇을 재고 시험하는지를 정한다.

1결론

대화마다 작은 "업로드 인덱스" 폴더(<데이터 폴더>/uploads/<대화 id>/)를 따로 만든다. Qdrant · BM25 · index_state.json 은 건드리지 않는다. 올린 문서는 수백 청크 안팎이라 벡터는 파일 하나(vectors.f32)로 두고 검색할 때 전수 내적(수 ms), 키워드 검색(BM25)은 그때그때 메모리에서 만든다. 리랭커 · 관련도 문턱 · 동의어 · 이어서 묻기 · 정밀 모드는 지금 검색 함수를 그대로 쓴다. 대화에 올린 문서가 하나라도 있으면 그 대화의 질문은 업로드 인덱스만 찾는다. 대화를 지우면(한 건 · 모두 · 10개 한도에서 밀려남) 폴더째 지우고, 시작할 때 주인 없는 폴더를 정리한다.
항목정한 것이유
인덱스 위치대화별 폴더 uploads/<conv_id>/ — 원본 사본 · 청크 · 벡터 · 메타폴더째 지우면 끝 — 기존 인덱스에 흔적이 남지 않는다
벡터 검색파일 하나 + 전수 내적(Qdrant 안 씀)Qdrant 로컬은 한 프로세스만 열 수 있고(§3) 수백 청크에는 전수 계산이 더 빠르고 단순하다
키워드 검색질문 때 메모리에서 BM25 만들기(디스크 캐시 없음)수백 청크는 수 ms — 지금 BM25 캐시(bm25_index.npz)를 다시 만들 일이 없다
검색 범위업로드가 있는 대화 = 업로드 문서만요청 그대로. 섞이면 "올린 문서에 없다" 를 판단할 수 없다
누가 쓰고 지우나쓰기는 워커(/upload), 지우기는 RAGSearchBox 가 폴더를 직접(워커가 떠 있으면 알림)임베딩은 모델이 올라간 워커만 할 수 있고, 지우기는 모델이 내려가 있어도 되어야 한다
두 판같은 폴더 모양 · 같은 파일 형식 · 같은 명령지금까지처럼 근거가 두 판 같게(§12)

2요구사항 정리

#요청설계에서의 규칙
R1입력란에 [+] — 누르면 문서 파일을 올린다파일 고르기 창(여러 개 가능). 지원 확장자는 인덱싱과 같음(indexer.TEXT_EXTS: pdf · docx · pptx · xlsx · hwp(x) · txt …)
R2질문하면 올린 문서에서 찾아 답한다그 대화의 /ask 에 대화 id 를 싣고, 워커는 업로드 인덱스로 찾는다
R3인덱싱 폴더 문서는 검색하지 않는다업로드가 있는 대화는 Qdrant · BM25 · 폴더 한정 검색을 부르지 않는다
R4업로드 인덱스는 기존 인덱싱에 추가하지 않고 따로uploads/ 아래 대화별 폴더. index_state.json · 자동 인덱싱 · 폴더 감시는 이 폴더를 모른다
R5히스토리에서 지우면 업로드 인덱스도 지운다한 건 지우기(새 메뉴) · 모두 지우기 · 10개 한도로 밀려난 대화 · 주인 없는 폴더 — 모두 폴더째 삭제(§9)

3왜 별도 인덱스인가 — 지금 구조와 부딪히는 곳

올린 문서를 지금 인덱스에 "표시만 해서" 넣는 방법도 있지만, 지금 구조와 네 곳에서 부딪힌다.

지금 구조업로드를 같은 인덱스에 넣으면
상태 파일 index_state.json — 문서 경로 → 청크 id 범위 · 지문자동 인덱싱 순찰(10분)과 /index-outside 가 "인덱싱 폴더 밖 문서" 로 보고 지운다. 예외 규칙을 곳곳에 넣어야 한다
BM25 캐시 bm25_index.npz — 전체 청크로 한 번에 만듦올리고 지울 때마다 전체 BM25 를 다시 만들어야 한다(5만 청크면 수십 초) — 아니면 키워드 검색에 안 잡힌다
Qdrant 로컬 — 한 프로세스만 열 수 있음(already accessed)모델이 내려가 있을 때 지우려면 CLI 를 따로 띄워야 하고, 그동안 워커를 막아야 한다(worker.hold)
폴더 한정 검색 — 벡터 한 벌(VectorMatrix) + 폴더 마스크업로드 문서가 "지정 폴더 전체" 검색에 섞여 나온다. 반대로 업로드만 찾으려면 마스크를 대화별로 또 만들어야 한다

따로 두면 넷 다 사라진다. 대신 검색 함수가 "어느 코퍼스에서 찾나" 를 받도록 한 단계 넓히면 된다(§6). 올린 문서는 많아야 수백 청크라 Qdrant 같은 색인이 필요 없다.

4전체 흐름

올리기

[+] 누름→파일 고르기(여러 개)→RAGSearchBox: 한도 확인 · 대화 id 정함→ 워커 /upload→원본 복사 → 추출 → 청킹 → 임베딩→uploads/<conv>/ 에 저장→첨부 칩 "완료 · 128청크"

질문

질문 보냄→/ask {q, prev, conv}→업로드 인덱스 읽기(캐시)→ 전수 내적 + BM25 → RRF → 리랭커 → 문턱→근거 3건 → 1.7B 답

지우기

기록에서 대화 지움→RAGSearchBox: uploads/<conv>/ 폴더째 삭제→워커가 떠 있으면 /upload-forget(캐시 비움)

새 대화에서 올리면

  1. 아직 대화가 없으면 이때 대화를 만든다(제목: 첫 파일 이름 · 첫 질문이 오면 질문으로 바꿈)
  2. 올리는 동안 보내기 단추는 잠근다 — 반쯤 올라간 인덱스로 묻지 않게
  3. 올린 뒤 첫 질문부터 업로드 문서만 찾는다

이미 질문한 대화에서 올리면

  1. 같은 대화에 이어 붙는다. 그 뒤 질문은 업로드 문서만 찾는다
  2. 앞 질문(이어서 묻기)은 그대로 쓴다 — 폴더 문서 대화에서 업로드로 넘어가도 주제가 이어질 수 있다
  3. 앞서 폴더 문서로 받은 답·출처는 기록에 그대로 남는다

5저장 위치와 파일 형식

워커 데이터 폴더(SIMPLERAG_HOME, 없으면 실행 파일 옆) 아래. 대화 id 는 RAGSearchBox 대화 기록의 conv.id 그대로(예: 1793171456.529000).

<데이터 폴더>/uploads/
  <conv_id>/
    meta.json        { "version": 1, "conv": "…", "embed_model": "multilingual-e5-small", "dim": 384,
                       "chunk": {chunk_params()}, "files": [ { "name": "계약서.pdf", "stored": "files/1_계약서.pdf",
                       "size": 1234567, "sha1": "…", "chunks": [0, 128], "pages": 31, "added": "2026-10-28T16:20:00" } ] }
    files/           올린 원본의 사본(원본이 옮겨지거나 지워져도 기록을 다시 열면 출처를 열 수 있게)
    chunks.jsonl     청크 한 줄씩 { "id": 0, "file": 0, "text": "[계약서 > 제3조]\n…", "doc_name", "chunk_idx", "section_id" }
    vectors.f32      청크 수 × 384 float32 리틀엔디언, L2 정규화(지금 임베더 출력 그대로)
  • 두 판 같은 형식 — JSON · JSONL · 생 float32 라 Python(numpy) · Rust 모두 그대로 읽는다. 같은 데이터 폴더를 쓰면 판을 바꿔도 다시 임베딩하지 않는다.
  • 호환 확인 — 읽을 때 embed_model · dim · chunk 가 지금 설정과 다르면 그 대화의 업로드를 다시 만든다(사본이 있으므로 가능).
  • 원자적 쓰기 — *.tmp 에 쓰고 이름 바꾸기. 파일을 더하면 chunks.jsonl · vectors.f32 를 덧붙인 새 파일로 바꾸고 마지막에 meta.json 을 바꾼다(meta 가 기준).
  • 파일 이름 — 사본은 <순번>_<원래 이름>(같은 이름 두 번 올려도 겹치지 않게). 화면에는 원래 이름.

6업로드 문서 검색

지금 검색(HybridRetriever.search / retrieve.rs search)은 "1차 후보 뽑기(_search)" 와 "리랭크 · 문턱 · 동의어 덧붙임 · 이웃 청크" 로 나뉜다. 1차 후보 뽑기만 업로드용으로 하나 더 만들고, 그 뒤는 그대로 쓴다.

단계폴더 문서(지금)업로드 문서(새로)
의미 검색Qdrant / VectorMatrixvectors.f32 전수 내적(수백 × 384 — 1ms 안팎)
키워드 검색BM25 캐시(동의어로 넓힌 질의)업로드 청크로 메모리 BM25(처음 한 번 만들고 대화별 캐시) · 동의어 넓힘 그대로
합치기RRF(rrf_k 같음) → 후보 rerank.pool(10) — 청크가 그보다 적으면 전부
리랭크 · 관련도 문턱같음 — 올린 문서에 없는 질문이면 "질문에 대한 내용이 문서에 없습니다" (지어낸 답을 막는다)
이어서 묻기 · 정밀 모드(이웃 청크)같음 — 이웃 청크는 업로드 청크의 chunk_idx 로 찾는다
동의어 덧붙임(RRF 1위 4번째 근거)같음
놓친 질문 기록synonym_misses.jsonl남기지 않는다 — 올린 문서는 사전 후보 재료가 아니다(사용자 문서 낱말이 사전에 섞이지 않게)
  • 캐시 — 워커는 대화 id → (청크, 벡터 행렬, BM25) 를 메모리에 둔다(최근 3개). meta.json 수정 시각이 바뀌거나 폴더가 없어지면 다시 읽는다/버린다.
  • 근거 표시 — 출처 문서 이름은 원래 파일 이름, 경로는 사본 경로(files/…) — [문서 이름] 을 누르면 사본이 열린다.
  • 소요 줄 — 모델 뒤에 "업로드 문서" 를 덧붙여 어느 쪽에서 찾았는지 남긴다. 예) 0.05s/2.10s/6.30s , qwen3-1.7b-q4 , 업로드 문서

7워커 명령(프로토콜)

지금처럼 stdin 한 줄 · ASCII JSON. 결과는 기존 @index {json} 처럼 한 줄(@upload {json})로 돌려준다. 시작 줄 "기능:" 에 upload 를 더해 옛 워커와 섞여도 안전하게 한다(없으면 [+] 를 잠근다).

명령보냄돌려받음 / 하는 일
/upload{"conv": "…", "path": "D:\\…\\계약서.pdf"} — 파일 하나씩사본 · 추출 · 청킹 · 임베딩 · 저장. 진행은 stderr [upload] 추출 … / 임베딩 64/128(진행 막대용), 끝에 @upload {"ok": true, "conv", "name", "chunks": 128, "pages": 31, "ms": 4210} 또는 {"ok": false, "why": "…"}
/ask (넓힘){"q", "folder", "prev", "conv"}conv 의 업로드 폴더에 meta.json 이 있으면 업로드만 찾는다. 없으면 지금과 같다(폴더 문서)
/upload-remove{"conv": "…", "name": "계약서.pdf"}첨부 칩의 [×] — 그 파일만 빼고 청크 · 벡터를 다시 쓴다(남은 파일이 없으면 폴더째 지움)
/upload-forget{"conv": "…"} 또는 {"all": true}메모리 캐시만 비운다(폴더는 RAGSearchBox 가 이미 지움)
질문 중에 /upload 가 오면 지금 명령 대기열(자동 인덱싱 명령과 같은 줄)에 넣는다 — 질문이 언제나 먼저(자동인덱싱 설계서 §8). 대신 올리는 동안 그 대화의 보내기는 화면에서 잠근다.

9대화 기록과 지우기

대화 기록(history.json, 최대 10개)에 업로드 정보를 함께 남긴다: conv.uploads = [{"name", "chunks", "pages"}]. 기록을 다시 열면 첨부 칩이 그대로 보이고, 이어서 물으면 업로드 문서에서 찾는다.

언제지금바꾼 뒤
대화 한 건 지우기없음(모두 지우기만)새로 — 기록 메뉴의 대화 줄 오른쪽 [🗑] 또는 머리 ⋯ 의 "이 대화 지우기". 기록에서 빼고 uploads/<conv>/ 폴더째 삭제
기록 모두 지우기history.json 비움+ uploads/ 아래 모든 대화 폴더 삭제(확인 창 문구에 "올린 문서 n건도 지웁니다")
10개 한도로 밀려남조용히 빠짐저장할 때 빠진 대화의 업로드 폴더도 삭제(history.touch 가 빠진 id 를 돌려준다)

12시험 · 측정 계획

  • 단위 시험(두 판) — 업로드 저장소 쓰기/읽기/파일 빼기/폴더 지우기, meta 호환 확인, 같은 이름 두 번, 원자적 쓰기(중간 끊김 흉내).
  • 두 판 같은 결과 — 같은 PDF 3개를 두 판에서 올리고 골든 질문 중 그 문서 문항으로 근거 비교(지금 Rust ↔ Python 비교 스크립트 방식). 목표 근거 100% 같음.
  • 범위 지키기(R3) — 업로드 대화에서 인덱싱 폴더에만 있는 내용을 물으면 "내용이 문서에 없습니다" 가 나오는지(폴더 문서가 근거에 0건).
  • 정답 — sample_pdf 문서 3~5개를 올려 그 문서의 골든 문항으로 정답 수를 폴더 검색과 비교(업로드 쪽이 같거나 높아야 — 후보가 그 문서뿐이라 오히려 쉬워진다).
  • 시간 — 10 · 30 · 100쪽 PDF 올리기 시간, 업로드 질문 체감 TTFT(폴더 검색 대비).
  • 지우기(R5) — 한 건 · 모두 · 10개 한도 밀려남 · 고아 정리 후 uploads/ 에 남는 것이 없는지, 그리고 index_state.json · BM25 · Qdrant 가 업로드 전과 같은지(바이트 비교).
