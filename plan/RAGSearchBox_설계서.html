RAGSearchBox 설계서

사용자가 Windows 탐색기 검색창에 ? 로 시작하는 질문을 입력하고 Enter 를 누르면, 상주 프로그램 RAGSearchBox.exe 가 이를 알아채 미리 모델을 올려 둔 SimpleRAG 워커(simplerag.exe chat)에 질문을 넘기고, 근거와 AI 답변을 작은 창에 띄운다. 검색창 감지 방식은 MDriveSearchBox(C++/MFC)에서 검증된 로직을 Python 으로 옮기고, 검색어 확정 감지·워커 관리·답변 표시 부분을 새로 설계한다.

1목표와 범위

D1 확정 — ? 접두어가 있을 때만 실행?연차 이월 기준 은 질문으로 처리하고, 보고서 같은 일반 파일 검색에는 반응하지 않는다.
D2 확정 — 모델을 올려 두는 방식SimpleRAG chat 을 워커로 한 번 띄워 두고 질문마다 재사용한다. 질문당 예열(약 6.6초)이 사라진다.
D3 확정 — chat 출력 텍스트 해석SimpleRAG 는 수정하지 않는다. 구분선·프롬프트 문구를 상태 기계로 해석하고 샘플 테스트로 지킨다.
D4 확정 — SimpleRAG .venv 공유기존 .venv 에 comtypes 만 추가한다. 빌드 때 무거운 패키지가 딸려 들어가지 않게 제외 목록을 둔다.
D6 확정 — 지정한 폴더 안에서만 동작INI [Scope] Folders 에 적은 폴더(하위 폴더 포함)를 보고 있는 탐색기에서만 ? 질문을 받는다. 비어 있으면 동작하지 않는다.
D5 확정 — 로그인 시 자동 시작은 설치 때 선택HKCU Run 에 등록한다. 기본은 등록하지 않으며, 설치 명령 옵션이나 트레이 메뉴로 켜고 끈다(§12).
D7 확정 — 시작 때 예열, 60분 유휴 시 해제StartMode=boot · IdleUnloadMin=60. P0-8 실측 결과로만 조정한다.

하는 것

  • 백그라운드에 창 없이 상주하며 탐색기 검색창을 감시한다
  • 검색창에서 Enter 로 확정된 검색어가 ? 로 시작하고, 그 탐색기가 지정 폴더 안을 보고 있으면 질문으로 받는다
  • SimpleRAG chat 워커 프로세스를 콘솔 없이 띄워 모델을 올려 두고, 표준입력으로 질문을 넘긴다
  • 출력을 실시간으로 읽어 근거 → 답변 스트리밍 → 소요 시간 순서로 답변 창에 표시한다
  • 워커 수명 관리 — 시작·준비 확인·죽으면 재시작·오래 안 쓰면 내려서 메모리와 인덱스 잠금 해제
  • 트레이 아이콘으로 워커 상태 표시, "인덱싱 전 워커 내리기" 메뉴 제공

하지 않는 것 (1단계)

  • SimpleRAG 코드 수정 — 기존 chat CLI 를 그대로 워커로 쓰고 출력은 텍스트로 해석한다(D3)
  • 검색 대상을 지정 폴더로 좁히기 — 폴더 제한은 실행 조건일 뿐, 검색은 인덱스 전체에서 한다(§5-1)
  • SimpleRAG 를 RAGSearchBox 프로세스 안에 import — 이유는 §6
  • 탐색기 파일 검색을 막거나 대체하기 — 탐색기 검색은 원래대로 돈다
  • 셸 확장(DLL) 주입, 저수준 키보드 훅(WH_KEYBOARD_LL) 사용
  • 탐색기 설정 변경 — MDriveSearchBox 가 켜던 "제목 표시줄에 전체 경로 표시"는 쓰지 않는다

판정 규칙 (원본과 같음)

  • 포커스 요소 ControlType 이 Edit 또는 Button 이 아니면 제외
  • AutomationId 가 SearchEditBox / SearchBoxSearchButton 이면 검색창 (Win7/10)
  • 아니면 ControlView 부모를 최대 4단계 올라가며 FileExplorerSearchBox 를 찾는다 (Win11)
  • CabinetWClass 에 닿으면 멈춘다 — 주소창 오탐 방지

Python 이라서 조심할 점

  • WinEvent 콜백 객체를 전역 변수에 붙잡아 둔다. 가비지 수집되면 탐색기 이벤트 때 프로세스가 죽는다
  • 훅을 건 스레드에서 메시지를 펌프해야 콜백이 온다(OUTOFCONTEXT)
  • 콜백 안에서 오래 걸리는 일은 하지 않는다. UIA 조회 뒤 결과만 큐에 넣는다
  • COM 포인터는 만든 스레드 안에서만 쓴다

5검색어 확정 감지 — 신규

원본은 "포커스가 들어왔다"가 곧 트리거였다. 여기서는 ? 로 시작하는 질문을 다 쓰고 Enter 를 누른 순간이 트리거다. 모델을 올려 두어 한 번 묻는 비용은 작아졌지만, 일반 파일 검색까지 답변 창이 뜨면 탐색기를 쓰기 불편하므로 ? 접두어로 의도를 구분한다(D1).

  1. T1

    무장(armed) — 검색창에 포커스가 있음

    §4 판정으로 검색창 안이면 armed 로 바꾸고 그 탐색기 HWND 와 검색창 UIA 요소를 기억한다. 전경 창이 탐색기가 아니게 되면 즉시 해제한다(원본 D8 의 inside 상태 추적과 같은 방식).

    해제는 즉시가 아니라 0.4초 유예를 둔다 (S5 구현 중 실측으로 바뀐 부분). 설계 초안은 "포커스가 검색창 밖으로 나가면 즉시 해제"였으나, 그대로 만들었더니 Enter 를 전혀 잡지 못했다. 두 가지 이유가 겹친다. ① 글자를 치는 동안 탐색기가 제안 목록을 열며 포커스 요소가 잠깐 딴 것으로 바뀐다. ② Enter 를 누른 그 순간 Win11 은 포커스를 파일 목록으로 옮긴다(P0-1) — 즉시 해제하면 바로 그 Enter 가 사라진다. 그래서 FOCUS_GRACE_S = 0.4 동안은 무장을 유지하고, 그 시간이 지나도 돌아오지 않을 때만 해제한다. 유예를 무한정 두지 않는 이유는 파일 목록에서 누른 Enter 가 질문으로 오해되면 안 되기 때문이다.

    붙잡아 둔 요소는 낡을 수 있다 (같은 실측). 검색 결과 화면에서 검색어를 지우고 다시 치면 탐색기가 검색창 UI 를 새로 만든다. 낡은 요소는 속성이 계속 읽혀 "살아 있는 것처럼" 보이지만 더 이상 그 칸이 아니어서, 두 번째 질문을 놓쳤다. 그래서 유예 판정 때 HasKeyboardFocus 만 보지 않고, 지금 포커스를 가진 요소가 같은 창의 검색창이면 붙잡는 대상을 그것으로 바꾼다.

    이때 현재 폴더도 함께 구해 둔다(§5-1). Enter 뒤에는 탐색기 위치가 검색 결과 화면(LocationURL 빈 문자열, P0-3·P0-9)으로 바뀌어 원래 폴더를 직접 읽을 수 없기 때문이다. 범위 밖이면 armed 로 만들지 않는다 — 이후 Enter 감시도 하지 않는다.

  2. T2

    확정 — armed 인 동안에만 Enter 확인 주 신호

    감시 루프(100ms)에서 armed 일 때만 GetAsyncKeyState(VK_RETURN) 를 부른다. 키보드 훅이 아니라 상태 조회라 원본 D3 의 "훅 없이" 원칙을 지킨다. 누름 비트(0x8000)와 "지난 호출 뒤 눌렸음" 비트(0x1)를 둘 다 본다 — 누름 비트만 보면 짧은 Enter 를 대부분 놓친다(P0-2).

    값 읽기
    armed 때 붙잡아 둔 검색창 요소를 Enter 감지 약 80ms 뒤 다시 읽는다: ① ValuePattern.CurrentValue → ② LegacyIAccessiblePattern.CurrentValue → ③ 실패 시 확정 취소(로그만). "포커스 요소"를 읽으면 안 된다 — Win11 은 Enter 순간 포커스를 파일 목록으로 옮겨 파일 이름이 읽힌다(P0-1)
    조합 중 글자
    붙잡아 둔 요소를 Enter 뒤에 읽으면 조합 중이던 마지막 글자까지 들어온다(?연차휴, 유효 13/13). 입력 직후 곧바로 읽은 값은 늦어서(?연ㅊ) 쓰지 않는다
    가벼운 선검사
    armed 동안 값 앞글자가 ? 가 아니면 Enter 폴링 자체를 건너뛴다 — 일반 파일 검색 때 하는 일이 거의 없다
  3. T3

    보조 신호 — search-ms: 위치 변화 P0-3 으로 제외

    같은 질문이 DedupSec(기본 3초) 안에 다시 오면 무시 — 한 번의 Enter 가 두 비트로 두 번 읽히는 경우 포함

5-1. 범위 판정 — 지정 폴더에서만 동작 (D6)

  1. R1

    현재 폴더 구하기

    창 찾기
    IShellWindows 를 돌며 HWND 가 armed 탐색기와 같은 항목의 LocationURL 을 읽는다
    경로 변환
    file:///D:/문서/인사 → D:\문서\인사, file://server/share → \\server\share (원본 ConvertURLPathToDosPath)
    이미 검색 결과
    검색 결과 화면은 LocationURL 이 빈 문자열이고 crumb 도 없어 폴더를 읽을 수 없다(P0-9). 그래서 탐색기 창·탭별로 마지막으로 본 file: 폴더를 기억해 두고, URL 이 비었으면서 LocationName 이 지금 검색창 값과 같을 때(= 검색 결과 화면)만 그 기억을 쓴다
    가상 폴더
    내 PC · 라이브러리 · 바탕화면 등 LocationURL 이 비었는데 검색 결과 화면도 아니면 범위 밖 — 내 PC 는 빈 URL·이름 "내 PC" 로 확인(P0-9)
  2. R2

    Win11 탭 — 활성 탭 가리기

    한 탐색기 창에 탭이 여러 개면 IShellWindows 항목도 여러 개가 같은 HWND 를 가진다. 원본 GetExplorerActiveTabTitleIfMultiple 로 활성 탭 제목을 얻어 경로(전체 경로 표시가 켜진 경우) 또는 폴더 이름과 비교한다. 원본과 달리 "전체 경로 표시" 설정을 켜지 않으므로, 이름이 같은 폴더가 다른 경로의 탭에 열려 있으면 후보가 여럿 남는다.

    보수 규칙
    후보가 여럿이면 모두 범위 안일 때만 범위 안으로 본다. 하나라도 범위 밖이거나 못 가리면 실행하지 않는다 — 원치 않는 폴더에서 뜨는 것보다 안 뜨는 편이 낫다
    실측
    첫 번째 ShellTabWindowClass 자식이 항상 활성 탭이었다(Ctrl+Tab 전환 포함). 이 PC 는 전체 경로 표시가 켜져 있어 같은 이름 폴더 두 탭(A\docs · B\docs)도 경로로 정확히 가려졌다. 설정이 꺼진 PC 의 보수 규칙은 미검증
  3. R3

    포함 비교

    정규화
    양쪽 모두 os.path.normcase(os.path.abspath(…)), 끝의 \ 제거. 매핑 드라이브는 그대로 비교(드라이브 문자와 UNC 를 서로 바꾸지 않는다 — 둘 다 쓰면 INI 에 둘 다 적는다)
    경계
    같거나, 지정폴더 + "\" 로 시작할 때만 포함. D:\문서 가 D:\문서함 을 포함하지 않게 한다
    하위 폴더
    포함 (D:\문서 지정 → D:\문서\인사\2025 도 동작)
  4. R4

    설정이 비었을 때

    [Scope] Folders 가 비었거나 적힌 폴더가 모두 존재하지 않으면 아무 폴더에서도 동작하지 않는다. 트레이 툴팁에 "범위 폴더 미설정 — RAGSearchBox.ini 의 [Scope] Folders 를 지정하세요" 를 띄우고, 워커도 올리지 않는다(쓸 수 없는 모델에 메모리를 쓰지 않게). 존재하지 않는 폴더는 경고 로그만 남기고 목록에서 뺀다(네트워크 드라이브가 늦게 붙는 경우를 위해 5분마다 다시 확인).

한계: 폴더 제한은 질문을 받을지만 정한다. chat 출력(D3 텍스트 해석)에는 근거의 폴더 정보가 없어 근거를 지정 폴더 것으로 거를 수 없다 — 지정 폴더와 인덱싱 폴더를 맞춰 두는 것이 운영 규칙이다. 인덱스에 범위 밖 문서가 섞여 있으면 답변 창 근거에 그 문서가 나올 수 있다.

워커 상태 기계

STOPPED→ 시작 STARTING→ 첫 질문> READY⇄ 질문 / 프롬프트 BUSY
  • STOPPED → STARTING: 앱 시작 시(StartMode=boot, 기본) 또는 첫 질문 때(lazy) 워커를 띄운다
  • STARTING → READY: stdout 에 첫 프롬프트 질문> 가 보이면 준비 완료. 그 전의 "준비 완료 (…초) — N청크", "생성 iGPU / 리랭킹 켬" 줄은 트레이 상태에 표시. 첫 실행은 CPU/iGPU 측정이 끼어 오래 걸릴 수 있어 StartTimeoutSec 기본 180초
  • READY → BUSY: 질문 한 줄을 stdin 에 쓴다. 프롬프트가 보인 뒤에만 쓴다 — 출력이 어느 질문의 것인지 섞이지 않게
  • BUSY → READY: 다음 질문> 가 보이면 그 질문의 done 을 낸다
  • DEAD 워커가 스스로 끝나면: 대기 중 질문은 오류로 알리고, 5분에 3회까지 자동 재시작. 넘으면 STOPPED 로 두고 트레이에 경고
  • READY → STOPPED (유휴 해제): IdleUnloadMin(기본 60분) 동안 질문이 없으면 stdin 에 exit 를 보내 정상 종료 — 메모리 약 2.5GB 와 인덱스 잠금을 돌려준다(종료 약 1.8초, 직후 status 가 인덱스를 연다 — P0-8). 다음 질문 때 다시 예열

  • stderr(준비 안내·llama.cpp 로그)는 별도 스레드로 계속 비운다. 비우지 않으면 파이프가 차서 워커가 멈춘다. 마지막 50줄은 오류 표시용으로 보관

  • 배포 가이드의 설치 절차에 "자동 시작을 원하면 --autorun on" 단계를 선택 항목으로 적는다
  • 트레이 메뉴 "로그인 시 자동 시작 ✓" 로 같은 등록/해제를 한다 — 명령 옵션과 한 모듈(autorun.py)을 쓴다
  • 경로 바뀜 보정: 시작할 때 등록 값이 있는데 경로가 현재 exe 와 다르면(폴더를 옮긴 경우) 현재 경로로 고치고 INFO 로그. 등록 값이 없으면 새로 만들지 않는다 — 사용자가 끈 설정을 되살리지 않게
  • D7 의 StartMode=boot 와 함께 쓰면 로그인 직후 약 6.6초 모델 예열로 CPU 를 쓴다. 단, 범위 폴더가 미설정이면 예열하지 않는다(§5-1 R4)
  • 레지스트리 쓰기가 실패하면(그룹 정책 등) 명령은 종료 코드 2 와 오류 문구, 트레이는 알림 풍선으로 알린다. 상주 동작에는 영향 없다
  • 제거 시 --autorun off 를 먼저 실행하도록 배포 가이드에 적는다 — 지운 exe 를 가리키는 등록이 남지 않게

  • 옆에 "원래대로" 단추를 둔다. 원래 질문 글자(?연차 이월 기준)를 같은 방법으로 도로 써 넣으면 원래 검색 결과로 돌아온다(실측)
  • 실행 조건: 그 탐색기 창이 아직 살아 있고 · 최소화되지 않았고 · 검색창 요소가 유효할 때만. 하나라도 아니면 조용히 무시하고 DIAG 로그만 남긴다
  • 최소화 상태에서는 안 된다 — 창이 최소화되면 검색창 UIA 요소 자체가 사라진다(실측). 복원 뒤 요소를 다시 찾아야 한다
  • 되먹임 걱정은 없다 — 넣는 글자가 ? 로 시작하지 않아 §5 의 선검사에서 걸러진다

선행 작업과 한계

  • 지금은 파일 이름만 알고 경로를 모른다. D3(텍스트 해석)라 chat 출력에 경로가 없다. 같은 이름이 다른 폴더에 있으면 엉뚱한 파일이 잡힌다. SimpleRAG 근거 출력에 경로를 함께 내보내면 깔끔해진다(인덱스에는 이미 있다)
  • 찾는 범위를 crumb=location 대신 지금 보고 있는 폴더로 한정하므로, 근거가 그 폴더 밖 문서면 목록에 안 나온다 — 지정 폴더와 인덱싱 폴더를 맞춰 두는 §5-1 의 운영 규칙이 여기서도 전제다
  • 따옴표·특수문자 파일 이름(S7 에서 확인): 괄호·&·+·~·[]·공백은 따옴표 안이라 그대로 넣으면 된다(실제 파일로 확인). 이름 안에 큰따옴표가 있으면 감쌀 수가 없어, 따옴표로 갈린 조각 중 가장 긴 것만 넣는다 — 탐색기 검색은 이름 일부로도 찾으므로 그것으로 걸린다

17따라다니는 오른쪽 패널 신규

답변 창이 탐색기 파일 목록 위를 덮는 것이 거슬린다. 미리보기 창처럼 오른쪽에 붙어 있으면 목록을 가리지 않는다. 다만 탐색기 안으로 진짜 도킹하는 길은 없다. 아래가 그 이유이고, 그래서 "붙어 있는 것처럼 따라다니는" 방식으로 간다.

왜 진짜 도킹은 못 하나

생각해 본 길확인한 사실판정
탐색기 미리보기 창 재활용 미리보기 창은 선택된 파일의 확장자에 등록된 COM 미리보기 처리기가 그린다 (HKCR\.docx\ShellEx\{8895b1c6-…} → 처리기 CLSID, 레지스트리 확인). 임의의 답변을 밀어 넣을 자리가 없다 불가
우리 전용 확장자(.raganswer) 미리보기 처리기 등록 in-proc COM DLL 이 필요해 파이썬으로는 사실상 무리이고, 사용자가 그 파일을 골라야 떠서 질문 흐름과 맞지 않는다 제외
탐색기 사이드 패널 확장 예전 Explorer Bar(IDeskBand)는 탐색기에서 빠졌다. Win11 이 열어 둔 확장점은 컨텍스트 메뉴·명령 모음(IExplorerCommand) 정도다 없음
SetParent 로 우리 창을 탐색기 자식으로 가능은 하지만 프로세스 간 입력 큐가 묶여 탐색기가 멈추면 같이 멈춘다. Win11 탐색기는 XAML 이라 레이아웃도 충돌한다 위험
따라다니는 별도 창 탐색기 창 오른쪽에 딱 붙여 두고 이동·크기 변경을 따라간다. 겉보기는 도킹과 거의 같다 채택

동작 규칙

위치

  • 기준은 대상 탐색기 창(armed 때 기억해 둔 HWND)의 화면 사각형
  • 기본은 창 안쪽 오른쪽 가장자리에 세로로 꽉 채워 붙인다 — 목록 일부를 덮지만 화면 밖으로 나가지 않는다
  • 창이 화면 오른쪽에 여유가 있으면 창 바깥 오른쪽에 붙이는 것을 우선한다(아무것도 가리지 않는다)
  • 너비는 [Window] Width, 높이는 탐색기 창 높이에 맞추되 MaxHeight 를 넘지 않는다
  • 화면 경계·다중 모니터·DPI 는 기존 place_near 의 보정 규칙을 그대로 쓴다

따라다니기

  • 대상 창의 이동·크기 변경은 EVENT_OBJECT_LOCATIONCHANGE 로 받는다 — §4 에서 이미 쓰는 WinEvent 훅에 이벤트만 하나 더 건다(새 스레드 없음)
  • 이벤트가 몰아쳐 오므로 마지막 것만 반영한다(약 50ms 로 묶기). 드래그 중 창이 덜덜 떨리지 않게
  • 대상 창이 최소화·닫힘이면 패널을 숨긴다. 복원되면 다시 보인다
  • 대상 창이 뒤로 가면 패널도 같이 뒤로 보낸다 — 다른 프로그램 위에 혼자 떠 있지 않게
  • 다른 탭·다른 창으로 옮겨 가면 패널은 그 답변이 나온 창을 계속 따라간다

설정

[Window]
Dock             = right   ; off = 지금처럼 검색창 아래 뜨는 창 / right = 탐색기 오른쪽에 붙어 따라다님
