1결론

"적용은 실시간·기계적으로, 판단은 사람이" — 동의어는 확정된 사전을 글자 그대로 찾아 키워드 검색(BM25)만 넓힌다.

비슷한 말인지 판단하는 일(임베딩·LLM)은 질문 속도와 무관한 후보 제안 단계로 보내고, 사용자가 [맞음]/[아님] 버튼으로 승인한 것만 사전에 들어간다. 멀티쿼리는 질문마다 2.5~5.1초가 더해지고(첫 글자 약 3초 → 6~8초) 1.7B 의 재작성 품질도 불안정해 기본으로 쓰지 않는다 — 검색 점수가 낮을 때만 쓰는 선택 옵션으로 둔다.

2문제 — 실제로 놓치는 모습

같은 내용을 낱말만 바꿔 simplerag.exe search 로 검색했다(2026-10-27, 근거 상위 3건).

질문근거 상위 3건정답 "조부모/외조부모 사망 : 3일"
"할아버지 돌아가시면 유급휴가는 며칠"취업규칙 32조 앞부분(본인 결혼 등) · 28조 유급휴일 · 29조 연차휴가못 찾음
"조부모 사망 시 유급휴가는 며칠"경조사지원규정 표(조부모 사망 3일) · 취업규칙 32조 7호 · 32조 앞부분찾음
  • 정답이 근거에 없으니 모델은 엉뚱한 항목(배우자 부모 사망 5일)을 섞어 답했고, 그 혼란이 반복 루프·답 잘림으로 이어졌다(사용자 보고 사례).
  • 왜 못 찾나 — 키워드 검색(BM25)은 글자가 같아야 맞는다('할아버지' ≠ '조부모'). 의미 검색(e5-small)은 작은 모델이라 구어↔규정 용어 연결이 약해, '유급휴가'·'돌아가시면' 같은 다른 낱말에 끌려 연차·유급휴일 조항을 가져온다.
  • 골든셋이 못 잡은 이유 — 골든셋 100문항은 문서 용어로 질문을 만들어 정답 문서 적중이 100/100 이다. 실제 사용자 질문은 일상어가 많다.

5질문할 때 — 검색어 넓히기

  1. 낱말 나누기 — 공백으로 나눈 뒤 조사·어미를 떼어 낸다("할아버지가" → "할아버지", "와이프한테" → "와이프"). 사전의 키는 기본형으로 적고, 낱말이 키로 시작하면 맞는 것으로 본다(조사 목록 없이도 대부분 맞는다). 두 낱말 키("유급 휴가")는 공백을 뺀 글자로도 비교한다.
  2. 사전 찾기 — 사용자 사전이 기본 사전보다 앞선다. 사용자가 [아님] 한 짝은 기본 사전에 있어도 쓰지 않는다.
  3. 필터 — 넓힐 용어가 문서 용어 목록에 없으면 버린다(문서에 '조부모'가 없으면 넓히지 않음).
  4. BM25 에만 더한다 — 지금 BM25 는 질문 글을 e5 토크나이저 조각(subword)으로 나눠 찾으므로, 넓힌 용어를 질문 끝에 덧붙이면 된다. 의미 검색·리랭커에는 원래 질문을 그대로 쓴다 — 리랭커가 질문 뜻으로 최종 판정하므로 넓힌 용어 때문에 엉뚱한 근거가 올라와도 걸러진다. 인덱스는 그대로 — 재인덱싱이 필요 없다.
  5. 기록 — 넓힌 내역을 소요 블록에 한 줄로 남긴다: 검색어 넓힘: 할아버지→조부모 (RAGSearchBox 가 읽어 보여 줄 수 있다).
  6. 설정 — config.yaml retrieval.synonyms: true(기본 켬), 끄면 이전과 글자까지 같은 동작.

6사전 파일과 문서 용어 목록

사전 파일 (사람이 읽고 고칠 수 있게 YAML)

# synonyms.yaml — 사용자 사전 (승인한 것 · 직접 추가한 것). synonyms.default.yaml 보다 앞선다
synonyms:
  조부모: [할아버지, 할머니, 외할아버지, 외할머니]
  배우자: [와이프, 아내, 남편, 집사람]
  여비: [출장비]
  유류비: [기름값, 주유비]
  학자금: [등록금]
  자녀: [애기, 아이, 아들, 딸]
rejected:            # [아님] 을 누른 짝 — 다시 제안하지 않는다
  - [와이프, 여비]
  • 기본 사전 범위 — 사내 규정 문서는 회사가 달라도 어휘가 한정적이다: 가족관계(조부모·배우자·자녀·형제자매), 비용(여비·일비·숙박비·유류비·의료비·학자금), 휴가·휴직(연차휴가·경조휴가·리프레시), 직급(대표이사·본부장·부서장), 결재(전결·품의). 처음 버전은 이 범위로 50~100항목.
  • 공유 — 개인 PC 는 그 사용자가 승인한 것이 그 PC 에만. 여러 사람이 같은 사전을 쓰려면 관리자가 승인한 synonyms.yaml 을 배포한다 (빌드 스크립트는 이미 배포 폴더의 이 파일을 보존한다 — 설계서 ①).

문서 용어 목록 (자동)

  • 인덱싱할 때 청크 본문에서 한글 낱말(2~10자, 조사 뗀 꼴)과 그 수를 모아 doc_terms.json 에 둔다. 문서를 추가·삭제·이동하면 그 문서의 몫만 더하고 뺀다(증분 인덱싱과 같은 흐름).
  • 후보 제안에 쓰려고 용어별 e5 벡터도 함께 둔다(용어 수천 개 × 384차원 — 수 MB). 새 용어만 임베딩하므로 인덱싱 시간 증가는 작다.

7후보 자동 제안 — 사전을 미리 다 몰라도 되게

  1. 놓친 질문 기록 — 답이 "관련 근거 없음"(RelevanceMin)으로 끝났거나, 리랭커 최고 점수가 문턱보다 낮은 질문을 기록한다. 사용자가 패널에서 "도움 안 됨"을 누른 질문도 넣을 수 있다.
  2. 낱말 고르기 — 그 질문의 낱말 가운데 문서 용어 목록에 없는 것(예: '할아버지')만 대상으로 한다 — 문서에 있는 낱말은 넓힐 필요가 없다.
  3. 후보 뽑기 — 그 낱말을 e5 로 문서 용어 벡터에 대어 상위 3개를 후보로(실험상 정답이 1위가 아닐 수 있어 3개를 함께 보여 준다).
  4. (선택) LLM 확인 — 앱이 한가할 때 1.7B 에 "'할아버지'와 '조부모'는 같은 뜻인가?" 를 물어 아니라는 후보는 뒤로 미룬다. 질문 속도와 무관하다.
  5. 순서 정하기 — 여러 번 놓친 낱말부터. 한 번에 보여 주는 후보는 5개 이내 — 많으면 사용자가 보지 않는다.

점수가 아주 높고 다음 후보와 차이가 큰 경우(예: 병원비→의료비 0.744 대 0.596)만 승인 없이 자동 적용하는 옵션은 가능하다. 다만 그 문턱이 안전한지는 §10 의 질문 세트로 재고 정한다 — 처음에는 끈다.

놓친 질문: "할아버지 돌아가시면 유급휴가는 며칠" · '조부모'가 나오는 문서: 취업규칙 32조, 경조사지원규정

와이프 → 여비✓ 맞음✕ 아님

놓친 질문: "와이프 출산하면 휴가 며칠 줘?" · 다른 후보: 배우자

기름값 → 유류비✓ 맞음✕ 아님

놓친 질문: "기름값 지원돼?" · '유류비'가 나오는 문서: 프로젝트 교통비 지원

일상어 (예: 애기) → 문서 용어 (예: 자녀)+ 직접 추가

승인한 동의어 12개 · 저장 위치: synonyms.yaml (exe 옆)

사용자가 하는 일

  1. 알림 — 후보가 쌓이면 트레이 메뉴 "정보·설정" 에 "동의어 (3)" 처럼 개수가 붙는다. 급하지 않으니 아무 때나 연다.
  2. 판단 — 후보마다 ① 일상어 → 문서 용어 ② 놓친 질문 ③ 그 용어가 나오는 문서가 보인다. 맞으면 [맞음], 틀리면 [아님]. [아님]은 기록돼 다시 묻지 않는다. 다른 후보가 있으면 함께 보여 줘 고를 수 있다(와이프 → 여비 ✕, 배우자 ✓).
  3. 직접 추가 — 아래 칸에 "애기 → 자녀" 처럼 적고 [직접 추가].

승인하면 synonyms.yaml 에 저장되고 워커가 다시 읽어 다음 질문부터 바로 적용된다(앱 재시작 불필요). Python 판은 정보 창(info_window.py, tkinter)에, Rust 판은 설정 창(ui/info.html)에 같은 칸을 둔다.

함께 고민할 점

  • 답변 화면에서 바로 승인 — 패널에 "관련 근거 없음"이 뜬 직후 "'할아버지'를 '조부모'로 찾아볼까요? [예]" 한 줄을 띄우는 방법. 사용자가 맥락을 가장 잘 아는 순간이라 효과가 크지만 답변 화면이 복잡해진다 — 1차는 정보·설정 창만, 사용 반응을 보고 결정.
  • 누가 승인하나 — 여러 사람이 쓰는 배포라면 개인 승인은 그 PC 에만, 회사 공용 사전은 관리자 배포.

9선택 — 조건부 멀티쿼리

  • 검색 결과의 리랭커 최고 점수가 문턱보다 낮을 때(= 못 찾았을 가능성이 높을 때)만 LLM 이 검색어를 한 번 다시 쓰고 다시 검색한다.
  • 그 질문만 +3~5초. config.yaml retrieval.rewrite_on_miss: false(기본 끔). 켤지는 §10 질문 세트에서 사전만으로 남는 놓침이 얼마인지 보고 정한다.
  • 다시 쓴 검색어에서 나온 낱말은 그대로 후보 제안(§7)에 넣는다 — 멀티쿼리가 사전을 키우는 재료가 된다.

10검증 방법

  1. 바꿔 말한 질문 세트(30~50문항)를 먼저 만든다 — 일상어 질문 + 정답 문서·쪽. 예: 할아버지 돌아가시면 휴가 며칠→조부모 사망 3일 · 와이프 출산하면 휴가→배우자 출산 · 출장비 하루 얼마→여비·일비 · 기름값 지원→유류비 · 애기 대학 등록금→학자금. sample_pdf 30건 기준, 골든셋과 같은 검증기(발췌가 원문에 글자 그대로 있는지)를 쓴다.
  2. 지금 상태부터 잰다 — 정답 문서·쪽이 근거 3건에 드는 비율. 이 값이 낮지 않으면 이 설계의 우선순위를 낮춘다.
  3. 완료 기준
    • 바꿔 말한 질문 세트의 정답 문서·쪽 적중이 좋아질 것
    • 기존 골든셋 100문항 적중 100/100 과 정답 핵심어 50 이 떨어지지 않을 것
    • 검색 시간 증가 10ms 미만, 두 판(Python·Rust) 근거·답 일치 유지
    • 넓힘을 끄면(retrieval.synonyms: false) 이전과 글자까지 같은 결과
  4. 후보 제안 품질 — 질문 세트의 놓친 낱말로 후보를 뽑아, 정답 용어가 상위 3 안에 드는 비율을 잰다(임베딩 단독 / LLM 확인 포함).

위험과 대응

  • 너무 넓은 동의어('휴가'에 '휴직'을 넣는 등)는 엉뚱한 문서를 끌어온다 → 사전은 좁게 시작, 문서 용어 필터, 리랭커가 원래 질문으로 최종 판정.
