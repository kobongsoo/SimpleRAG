1결정 사항과 요약

항목결정
추출기 소유SimpleRAG 전용 추출기를 새로 만든다. MpowerClassify(csoclassify.extract)는 참고·이식 대상일 뿐 공유하지 않는다. 분류 엔진에 영향을 주지 않고, 청킹에 필요한 구조 정보를 자유롭게 뽑기 위해서다.
추출 결과 형태문자열 → 블록 목록 {종류, 제목 수준, 제목 경로, 쪽, 텍스트, 표 행렬, 출처}
구조를 얻는 방법1순위 파일 안의 구조를 그대로 읽기(DOCX 스타일·HWPX 개요 수준·표 요소) → 2순위 글자 크기 등 서식 추정(PDF) → 3순위 기존 정규식 추측(structure.py) → 선택 레이아웃 모델·OCR
청킹 규칙기존 SimpleRAG 규칙을 유지한다(절 경계 · 토큰 예산 패킹 · 큰 절만 겹침 · 표 머리글 재부착 · 경로 접두). Newploy 의 300자·쪽 단위 끊기는 가져오지 않는다.
LLM 입력Parent-Child — 부모는 페이지가 아니라 절. 첫 실험은 자식(검색 단위)을 128토큰 그대로 두고 LLM 입력만 절로 키운다. 자식 축소(64·96)는 그 뒤 별도 실험(§12).
전환 방식설정 스위치로 새 추출기/기존 경로를 고를 수 있게 두고, 포맷 단위로 하나씩 넘긴다. 구조 파서가 없는 포맷은 기존 텍스트 경로를 블록으로 감싸 같은 청킹기를 탄다.

가장 중요한 발견 — 골든셋 100문항의 정답 문서가 DOC 58 · DOCX 42 다. 측정 기준이 되는 질문의 절반 이상이 구 바이너리 DOC 에 있으므로, DOCX 파서만 잘 만들어서는 점수가 크게 오르지 않는다. DOC 의 구조(제목 스타일)를 읽는 일이 이 재설계의 성패를 가른다(§8). 동시에, 지금 골든셋에는 PDF·HWP·PPTX 질문이 없어 그 포맷의 개선은 측정조차 안 된다 — 평가셋 보강이 선행 과제다(§15).

2왜 재설계하나

현재 SimpleRAG 는 글자 수로만 자르지 않는다. structure.py 가 조문·번호절·마크다운·부속서 경계를 찾아 절로 나누고, chunk.py 가 128토큰 예산 안에서 절을 묶는다. 문제는 자르는 규칙이 아니라 구조를 얻는 방법에 있다.

현재   : 파서가 구조를 버림 → 평문 문자열 → 정규식으로 구조를 '다시 추측' → 청킹
재설계 : 파서가 구조를 남김 → 블록 목록 {종류, 수준, 쪽 …}           → 청킹
현재 경로에서 버려지는 정보어디서결과
문단 스타일(제목 1·2·3)DOCX 추출기가 <w:t> 글자만 모으고 pStyle 은 읽지 않음제목을 정규식으로 추측. 조문(제N조) 문서는 표본의 6% 뿐이라 나머지는 번호 형식·폴백에 의존
표의 행·열·병합셀 구분이 탭·줄바꿈으로 흩어짐normalize_tables 가 '눕힌 행/셀 안 줄바꿈'을 추측해 복원(§20.6 붕괴 사례). 머리글 판정도 추측이라 목차 필드가 머리글로 잡힌 사고(§35)
머리말·꼬리말 구분본문 뒤에 이어 붙임청크에 문서명·쪽번호 잡음이 섞임
목차본문과 구분 없음번호절 문법이 목차 줄을 제목으로 잡아 목차가 짧은 절 수십 개로 쪼개질 수 있음
PDF 쪽 경계쪽 텍스트를 "\n".join출처 쪽번호를 못 보여 줌

워드 파일 안에는 "이 문단은 제목 2단계"라는 정답이 들어 있다. 그것을 버리고 정규식으로 다시 맞히는 구조를 바꾸자는 것이 이 재설계다.

3Newploy 는 실제로 어떻게 했나

Newploy 보고서(2026-10-20)를 다시 보면, "영역 목록으로 청킹"이라는 장점은 OCR 파이프라인을 탈 때만 작동한다.

입력Newploy 처리 경로구조 분석
텍스트층 PDF (일반 PDF)뷰어 모드 — OCR 생략, 텍스트층 그대로(282쪽 1초)사실상 없음 영역 전부 text, 글자 길이로만 끊김, 이미지 속 글자 미색인
텍스트층 PDF + "문서 전체 이해"모든 쪽을 OCR 파이프라인으로 재처리(사용자가 누를 때만)있음 레이아웃 모델 20종 분류
스캔 PDF · 이미지OCR 파이프라인있음
DOCX · HWPX전용 파서보고서에 상세 없음
DOC · HWP(구) · PPT—지원 목록에 없음 (PDF·DOCX·HWPX·PNG·JPG 만)

OCR 파이프라인에서 구조가 나오는 곳

① 쪽을 이미지로 렌더링 (200dpi)
② 레이아웃 모델 PP-DocLayout_plus-L — 이미지를 보고 영역 박스와 종류를 추정   ← 구조는 여기서
③ 줄 검출 PP-OCRv5_det                                                         ← 여기부터 OCR
④ 글자 인식 (자체 CTC 모델)
⑤ 표 구조 (Table Transformer + 자체 랭커)

구조를 알아내는 것은 OCR(글자 인식)이 아니라 그 앞의 레이아웃 모델이다. 사람이 종이를 보고 "큰 글씨는 제목, 격자는 표"라고 판단하듯 생김새로 추정한다. 포맷과 무관하게 동작하지만 추측이라 틀릴 수 있고(보고서: "레이아웃이 영역을 잘못 나누면 청크도 어긋난다") 쪽당 수 초가 든다. 게다가 Newploy 는 그렇게 얻은 영역을 300자 누적·쪽 단위로 단순하게 끊어 정답 쪽 적중률이 약 55% 였다 — 측정도 구조 분석이 없는 뷰어 모드 문서로 이뤄졌다.

가져올 것 — '청킹기는 문자열이 아니라 종류가 붙은 블록을 받는다'는 입력 형태. 가져오지 않을 것 — 디지털 문서까지 그림으로 추측하는 방식, 300자·쪽 단위 끊기. DOCX·HWPX·PPTX·XLSX 는 파일 안 구조를 읽으면 레이아웃 모델보다 정확하고 빠르다. 그림 기반 분석은 PDF·스캔에만 선택적으로 쓴다(§9).

4코퍼스 구성과 기대 효과

구조화 추출은 파일 안에 구조 정보가 들어 있는 포맷에서만 효과가 난다. 같은 "제5조(지급 금액)"도 포맷마다 저장 방식이 다르다.

포맷파일에 저장된 모습구조 획득
DOCX · HWPX<w:pStyle w:val="Heading2"/> — "이 문단은 제목 2단계"라고 직접 표시읽기만 하면 정답
PDF"맑은고딕 14pt 굵게, 좌표 (72,540)에 '제5조(지급 금액)'을 그려라" — 제목이라는 표시 없음쪽 경계만 확실, 제목·표는 추측
DOC · HWP5구조 정보는 있으나 XML 이 아닌 바이너리 레코드가능하지만 어려움
TXT글자뿐없음 (정규식 추측만)

5목표 구조

파일
 │
 ├─ 포맷 감지 (OLE 매직 보정 포함 — 기존 extract.make_detector 로직 이식)
 │
 ├─ 포맷별 블록 추출기 ───────────────────────────────────────────────
 │    DOCX · HWPX · PPTX · XLSX · HTML · MD · IPYNB   → 구조를 그대로 읽음     (source=parser)
 │    DOC · HWP5                                      → 바이너리 레코드에서 읽음 (source=parser)
 │    PDF                                             → 쪽 + 서식 추정          (source=inferred)
 │    TXT · PY · 구조 파서 실패                        → 기존 텍스트 + 정규식 추측 (source=regex)
 │    (선택) 스캔 쪽                                   → OCR                     (source=ocr)
 │
 ├─ 블록 후처리 : 머리말·꼬리말·쪽번호 제거 · 목차 표시 · 정제(sanitize) · 표 정리
 │
 ├─ 절 조립   : 제목 블록의 수준으로 제목 경로 스택을 만들고, 다음 같은/상위 제목까지를 한 절로
 │
 ├─ 청킹      : 기존 규칙 — 토큰 예산 패킹 · 큰 절은 블록 경계 → 줄 → 토큰 순 분할(이때만 겹침)
 │              표 행 조각에 표 블록의 머리글 행 재부착 · [문서 > 경로] 접두 · 쪽 범위 기록
 │
 └─ 색인      : 청크(128토큰) — payload 에 section_id · path · page_from/to · source
                (Phase 3 실험 A: 같은 section_id 청크를 모아 부모로 / 실험 B: 작은 자식 + parent_id)

핵심은 모든 포맷이 같은 블록 형태로 모인 뒤 하나의 청킹기를 탄다는 점이다. 구조 파서가 없는 포맷도 기존 정규식 추측 결과를 블록으로 바꿔 넣으므로, 청킹 코드가 두 벌로 갈라지지 않는다.

6블록 모델

Document
  format    : "docx" | "hwpx" | "pdf" | …
  title     : 문서 제목(파일명 또는 문서 속성 제목)
  pages     : 쪽 수 (쪽 개념이 없는 포맷은 None)
  blocks    : [Block, …]               ← 읽기 순서
  warnings  : ["표 3개 병합 셀 해석 실패", …]

Block
  type      : heading | paragraph | list_item | table | caption | code
              | header | footer | page_number | toc | note | figure_text
  level     : 제목 수준 1~9 (heading 만) · 목록 깊이 (list_item)
  text      : 블록 글자 (표는 행렬을 평문으로 편 것)
  rows      : 표만 — [[셀, …], …], 병합 셀은 펼쳐 채움
  header_rows: 표만 — 머리글 행 수 (파일이 표시한 값, 없으면 추정)
  page      : 시작 쪽 (PDF·PPTX 슬라이드·XLSX 시트 번호, 없으면 None)
  path      : 이 블록이 속한 제목 경로 ["제3장 근무", "제12조(근로시간)"]  ← 절 조립 단계가 채움
  source    : parser | inferred | regex | ocr     ← 진단·평가에서 출처별 성능을 가르기 위해
블록 종류청킹에서의 처리
heading절 경계 + 제목 경로. 청크 본문에도 남긴다(내용이 있는 긴 제목 대응 — 기존 _label 규칙 유지)
paragraph · list_item · caption · code본문. 큰 절 분할 시 블록 경계를 1순위 절단점으로
table행 단위로 분할 가능. 조각마다 header_rows 를 재부착(추측이 아니라 파일 값)
header · footer · page_number청크에서 제외 (원문 보존용으로만 기록)
toc청크에서 제외 — 목차가 근거로 끌려오는 문제 차단
note (PPTX 발표자 노트 · 각주)본문 뒤 별도 절로. 검색은 되되 본문과 섞이지 않게
figure_text (그림 속 글자, OCR 시)본문으로 취급하되 source=ocr 로 표시

디버깅을 위해 문서별 블록 목록을 JSON 으로 남길 수 있게 한다(Newploy 의 document_result.json 에 해당). 기본은 끄고, 진단 명령(python -m simplerag extract --blocks <파일> 형태)으로 확인한다.

7포맷별 추출기

원칙: MpowerClassify 처럼 표준 라이브러리(zipfile + ElementTree)만 쓴다(python-docx 등 미사용 → exe 크기 유지). MpowerClassify 의 검증된 처리(텍스트 상자 중복 방지, 탭 정의 오인 방지, 페이지·시간 상한 등)는 코드째 이식해 출발점으로 삼는다.

포맷제목표머리말·목차 등난이도단계
DOCXstyles.xml 의 w:outlineLvl 또는 스타일 이름(Heading N · 제목 N · 개요 N) → 수준. 문단 직접 지정 outlineLvl 도 반영w:tbl → 행렬. gridSpan(가로 병합) · vMerge(세로 병합) 펼침. tblHeader 행 = 머리글header*.xml/footer*.xml 은 header/footer 블록. TOC 필드·docPartGallery="Table of Contents" → toc낮음1
HWPXheader.xml 문단 모양의 개요 수준(heading type OUTLINE + level), 스타일 이름(개요 1~7)hp:tbl → 행렬. cellSpan colSpan/rowSpan 펼침hp:header/hp:footer, 쪽번호 컨트롤 제외낮음~중간1

9PDF 처리 단계

PDF 에는 '제목'이라는 표시가 없다. 가볍고 확실한 것부터 쌓는다.

P-1 쪽 경계 · 머리말/꼬리말 · 목차 Phase 2

  • pypdfium2 로 쪽마다 읽어 블록에 page 를 단다(기존 페이지·시간 상한 이식).
  • 쪽마다 첫·마지막 2줄을 모아 숫자를 # 로 정규화한 뒤, 전체 쪽의 50% 이상에서 반복되는 줄을 header/footer/page_number 로 표시.
  • 점선·가운데점 리더 뒤 쪽번호로 끝나는 줄(…{3,}\s*\d+$)이 연속되면 toc 로 표시.
  • 제목은 아직 정규식 추측(source=regex).

P-2 서식으로 제목 추정 · 표 영역 추출 Phase 3

  • pdfium 글자 정보(글꼴 크기·굵기)로 줄마다 서식을 얻고, 본문보다 확연히 큰/굵은 짧은 줄을 제목으로, 크기 순위로 수준을 매긴다(source=inferred).
  • 표는 선·글자 배치로 표 영역을 찾는 라이브러리(pdfplumber, MIT)를 검토한다. PyMuPDF 는 AGPL 이라 exe 배포 시 제외. 의존이 늘어나므로 PDF 표 질문의 실패 비중을 먼저 잰 뒤 결정.

P-3 (선택) 레이아웃 모델 + 텍스트층 결합 Phase 4

Newploy 에서 힌트를 얻되 OCR 은 뺀 조합이다.

쪽 이미지 → 레이아웃 모델(PP-DocLayout 계열, ONNX) → 영역 박스 + 종류 (제목·본문·표·그림·머리말…)
          + 글자는 OCR 하지 않고 PDF 텍스트층에서 박스 좌표 안의 글자를 꺼냄
  • 장점: 글자 인식 오류 0(텍스트층은 정확), OCR 모델 두 개(검출·인식) 불필요, 기존 ONNX Runtime 재사용.
  • 비용: 모델 약 129MB, CPU 에서 쪽당 수백 ms~수 초. 별도 설치 옵션으로 두고 P-1·P-2 로 부족할 때만.

P-4 (선택) 스캔 쪽 OCR Phase 4

  • 현재 스캔 PDF 는 "추출 텍스트 없음"으로 건너뛴다. 텍스트층이 거의 없는 쪽만 골라 OCR(줄 검출 + 인식, ONNX 변환 PP-OCRv5 계열).
  • Newploy 의 한국어 인식기·표 모델은 암호화된 자체 모델이라 사용 불가 — 공개 모델의 한국어 품질을 별도 검증해야 한다.
  • 스캔 문서 비율과 수요가 확인될 때만 진행.

10블록 후처리

  1. 정제 — 기존 sanitize(비문자·사용자정의영역·짝 없는 서로게이트 제거)를 블록마다 적용. 토크나이저 방어는 그대로 필수.
  2. 제외 블록 표시 — header · footer · page_number · toc. 지우지 않고 표시만 해서 진단 JSON 에는 남긴다.
  3. 표 정리 — 병합 셀을 펼친 행렬을 마크다운 표 줄(| 셀 | 셀 |)로 렌더링. 지금의 normalize_tables(탭 추측 복원)는 DOC 0x07 경로와 regex 폴백에만 남는다. 생성 단계의 tableflat("머리글: 값" 평문화)은 그대로 쓴다.
  4. 무손실 검사 — 제외 블록을 뺀 본문 글자 수가 원문 대비 비정상적으로 줄면(예: 30% 이상) 경고하고 해당 문서는 regex 폴백으로 처리한다. normalize_tables 의 93% 손실 사고(ARIA-WISC.pdf)에서 얻은 원칙을 이어 간다.

분할 규칙 — 128토큰은 '자르는 길이'가 아니라 '상한'

chunk.tokens: 128 은 글자 수가 아니라 e5 토크나이저 토큰 수이고, [문서 > 경로] 접두를 포함한다 (실측 근거 청크 중앙값 약 223자). 128 에 맞춰 기계적으로 자르지 않는다 — 블록을 온전히 담는 것이 1순위다.

① 블록(또는 절) ≤ 128            → 통째로. 작은 블록 여러 개는 128 까지 묶는다
② 절 > 128                       → 블록 경계에서 끊는다 (문단 사이 · 표 행 사이)
③ 블록 하나 > 128                → 그 블록 안에서만 쪼갠다: 줄 → 문장 → 토큰, 이때만 겹침(16토큰)
   (약한 초과 허용 — 실험 설정)  → 128 < 블록 ≤ 128 × α 이면 쪼개지 않고 통째로 둔다
④ 표 조각                         → 머리글 행 재부착 (최대 64토큰 초과 허용 — 현행)
⑤ 절대 상한 512                   → 어떤 경우에도 넘지 않는다 (e5 최대 입력 길이)

예 — 절 "제12조(근로시간)" = 문단A 40 + 문단B 60 + 표C 300토큰

청크1: [취업규칙 > 제12조] 문단A + 문단B             (~110토큰 · 블록 2개를 온전히 묶음)
청크2: [취업규칙 > 제12조] 표 머리글 + 표 행 1~6     (~128)
청크3: [취업규칙 > 제12조] 표 머리글 + 표 행 7~12    (~128)   ← 표는 행 경계에서 끊고 머리글을 다시 붙임

블록 중간을 자르는 일은 블록 하나가 상한보다 클 때만 일어난다. 현재 문서에서 절의 85% 가 128 안에 들어가므로(chunk.py 주석) 대부분의 블록은 잘리지 않는다.

결정이유
큰 블록에 맞춰 청크를 무한정 키우지 않는다 ① e5 는 최대 512토큰만 본다 — 넘는 뒷부분은 벡터에 반영되지 않아 그 내용으로는 검색이 안 된다
② 긴 청크는 벡터가 여러 주제의 평균이 되어 흐려진다
③ 그런 청크 하나가 근거로 뽑히면 생성 컨텍스트 2048 을 혼자 차지한다 — 실제로 2,768토큰 청크 때문에 파이프라인이 죽었다(REPORT §35)
약한 초과 허용 α 를 설정값으로 둔다 (기본 1.0 = 현행, 실험 후보 1.5)128 에서 칼같이 자르면 블록의 마지막 몇 토큰만 다음 청크로 넘어가는 어색한 분할이 생긴다. 이전 128/192/256 비교에서 정답률은 평평하고 TTFT 만 늘었으므로 소폭 허용은 손해가 작을 가능성이 크다. 단 그 실험은 고정 크기 분할이었으므로 이 방식에서 다시 잰다
큰 블록 분할에 문장 경계(. ! ? 다. 등)를 줄과 토큰 사이에 추가블록 모델에서는 문단이 한 줄인 경우가 많아, 현행(줄 → 토큰)으로는 곧바로 토큰 중간에서 잘리기 쉽다
 
# config.yaml (추가 예정)
chunk:
  tokens: 128          # 상한 (현행 유지)
  overflow_ratio: 1.0  # 약한 초과 허용 α — 1.0 이면 현행과 같음. 실험 후보 1.5
  hard_max: 512        # 절대 상한 (e5 최대 입력)

회귀 기준 — regex 폴백 경로(TXT 등)는 현재 split_structured 와 글자까지 같은 청크를 내야 한다. 이것을 테스트로 고정하면 블록 경로 도입이 기존 포맷 결과를 흔들지 않았음을 증명할 수 있다. 이 비교는 overflow_ratio: 1.0 · 문장 경계 분할 끔 상태에서 한다 — 두 변경은 회귀 확인 뒤 각각 켜서 효과를 따로 잰다.

12Parent-Child 결합

블록 모델이 생기면 '작게 찾고 크게 읽히기'(검색 단위와 LLM 입력 단위를 나누기)가 자연스럽게 된다. 다만 자식(검색 단위)을 바로 줄이지 않는다. 먼저 검색은 그대로 두고 LLM 입력만 키워 본 뒤, 자식 크기는 따로 실험한다.

실험 B (A 효과 확인 후)64 · 96토큰 (경로 접두 포함)절 전체필요 — 자식 색인 + parent_id

왜 자식을 바로 32~64토큰으로 줄이지 않나

SimpleRAG 에 이미 반대 증거가 있다. 실측한 절 413개의 길이 중앙값이 36토큰이었고, 그대로 청크로 쓰면 "변별력 없는 조각이 쏟아진다"는 이유로 절을 묶어 128토큰으로 만들었다(chunk.py 구조 인식 청킹 주석). 그 판단은 바로 '검색 단위로서의 짧은 조각'에 대한 것이고, Parent-Child 에서 자식이 하는 일이 정확히 검색이다.

  • 임베딩 — e5 는 너무 짧은 글에서 의미가 흐려진다. "다만 3만원을 넘으면 안 된다"만으로는 무엇에 관한 문장인지 벡터에 실리지 않는다.
  • BM25 — 짧은 조각은 핵심어 한두 개에 점수가 좌우된다.
  • 완화 수단 — 자식에도 [문서 > 경로] 접두를 붙이면 짧은 조각에 문맥이 실린다. 효과는 실험 B 에서 잰다.

실험 A 를 먼저 하는 이유

  • 검색이 전혀 바뀌지 않는다. 색인·임베딩·리랭크가 지금과 같으므로 점수 변화는 순수하게 'LLM 에 문맥을 더 줬을 때'의 효과다.
  • 재색인이 필요 없다. 이전 검토의 '이웃 청크 ±1 확장'을 절 단위로 정리한 형태다.
  • 비용 확인이 쉽다. 근거 토큰이 늘어난 만큼 TTFT 가 얼마나 느는지를 같이 잰다.

실험 A 에서 Context Recall · Faithfulness 가 오르면, 실험 B 로 '작게 찾으면 검색 정밀도가 더 오르는가'를 따로 확인한다. 크기 비교에는 기존 bench/sweep_chunk.py 를 확장해 쓴다. 자식 크기는 실험 결과로 정하고, 이 문서에서 미리 고정하지 않는다.

공통 규칙

  • 검색·리랭크는 자식으로, 상위 자식의 부모를 중복 없이 모아 최대 3개를 LLM 에 넣는다(같은 절의 자식이 여러 개 오르면 부모는 한 번만).
  • 예산: 생성 컨텍스트 2048 − 답변 200 − 특수토큰 16 = 프롬프트 1,832토큰(지시문·질문 포함). 절 3개(400~1,200토큰)는 들어가고, 페이지 3장은 안 들어간다. 부모가 상한(~400토큰)을 넘는 큰 절은 자식 청크와 그 앞뒤 청크만 넣는다. 그래도 넘치면 기존 _fit_prompt 가 가장 긴 근거를 깎는다.
  • 부모가 커질수록 prefill 이 늘어 TTFT 가 늘어난다(이 비용은 n_ctx 값이 아니라 실제 근거 토큰 수에서 온다).
  • Parent-Child 는 블록 경로가 안정된 뒤(Phase 3) 별도 실험으로 다룬다 — 추출 변경과 검색 변경을 한꺼번에 하면 어느 쪽 효과인지 가를 수 없다.

전환 스위치

# config.yaml
extract:
  engine: blocks        # blocks | legacy   — legacy 는 현재 csoclassify 경로
  formats: [docx, pptx, xlsx, hwpx, html, md, ipynb]   # 블록 경로로 처리할 포맷. 나머지는 legacy
  dump_blocks: false    # 문서별 블록 JSON 저장(진단용)
  • 포맷 단위로 블록 경로로 옮기고, 각 단계에서 골든셋으로 비교한 뒤 목록에 추가한다.
  • 블록 추출이 예외를 내면 그 문서만 legacy 경로로 처리하고 이유를 기록한다(인덱싱 전체가 멈추지 않게 — 현 indexer 의 실패 기록 방식과 동일).
  • CHUNKER_VERSION 을 올려 재색인을 유도한다. 포맷별로 넘어갈 때마다 해당 포맷 문서만 재색인되면 이상적(청크 파라미터에 엔진·포맷 목록을 포함).
  • 마지막 단계에서 모든 포맷이 블록 경로로 넘어오면 csoclassify 의존을 제거한다. 이때 사이냅 외부 실행 폴백을 유지할지 결정한다.

새 모듈은 프로젝트 공통 규칙에 따라 모든 함수·클래스에 한글 헤더 주석(제목 · 설명 · -in · -out · error)을 단다. 이식 코드도 출처(MpowerClassify 파일·함수)를 헤더에 남겨 이후 양쪽 수정 이력을 추적할 수 있게 한다.

15측정과 평가

  • 정답 근거 적중률 — 상위 3 근거에 정답 문서·정답 절이 들어가는 비율. 추출 변경의 1차 지표.

  • 모든 지표를 포맷별 · source 별(parser / inferred / regex)로 나눠 본다.
