chat 워커 메모리 줄이기

MoAI-S만 실행해도 램 사용률이 56%에서 89%로 올라갑니다. chat 워커가 쓰는 메모리 4.8GB를 세 갈래로 줄입니다.

  • A안: payload를 원문 JSON으로 보관합니다.
  • B안: 벡터를 반 정밀도(f16)로 보관합니다.
  • C안: 쉬는 동안 생성 모델과 리랭커를 내립니다.

A·B안은 상주하는 저장소를 1,565MB에서 약 650MB로 줄이고, C안은 쉬는 동안 2.3GB와 공유 GPU 1.6GB를 비웁니다. 디스크 형식은 그대로라 인덱스를 다시 만들 필요가 없습니다.

1. 배경 — 무엇이 메모리를 쓰나

사용자 노트북(램 16GB, Iris Xe)에서 MoAI-S만 실행해도 램 사용률이 89%였습니다. 작업 관리자의 "공유 GPU 메모리"는 Iris Xe에서는 따로 있는 메모리가 아니라 램의 일부입니다. 실제로 재 보니 프로세스 전용 메모리 안에 그대로 잡혀 있었습니다. chat 워커가 구성요소를 동시에 올리므로, 하나씩 차례로 올리며 잰 결과는 다음과 같습니다(examples/mem_profile.rs, 설치본 282,953청크).

2. 원인 — 1.56GB의 내역

지금 저장소(src/store.rs)는 시작할 때 points.sqlite를 모두 읽습니다. 점마다 Point { vec: Vec<f32>, payload: serde_json::Map } 모양으로 BTreeMap에 들고 있습니다. 디스크 내용을 필드별로 재 보면 다음과 같습니다.

필드디스크 크기성격
벡터 (384 × f32)414 MB청크마다
text 본문106.5 MB청크마다
doc_path · doc_name · folder · path55.0 MB문서 단위 — 같은 문서의 청크가 똑같은 값을 반복
gen · content_hash · mtime · source27.3 MB문서 단위
chunk_hash · chunk_idx · section_id · page*13.3 MB청크마다
payload 합242 MB

디스크에서 242MB인 payload가 메모리에서는 약 1,110MB(1,565 − 벡터 456)가 됩니다. 청크 하나에 필드가 14개 안팎이고, serde_json::Map(preserve_order 켬 = IndexMap)은 필드마다 다음을 따로 만듭니다.

  • 이름 문자열(String 24바이트 + 힙 할당)
  • 값(Value 32바이트 + 문자열이면 힙 할당)
  • 해시 색인 칸

28만 청크 × 14필드 ≈ 400만 개 항목이라, 내용보다 그릇이 4.5배 큽니다.

앞선 대화에서 "1.1GB는 본문"이라고 했던 것은 틀린 설명입니다. 본문은 107MB뿐입니다. 본문을 디스크에서 그때그때 읽는 방식(지연 읽기)으로 바꿔도 100MB 남짓밖에 줄지 않습니다.

A+B안 수치는 hybrid 실측(853)에서 벡터 절반(282,953 × 384 × 2B = 207MB)을 뺀 계산값입니다. 구현 뒤 다시 잽니다.

raw · compact를 고르지 않은 이유는 다음과 같습니다.

  • raw: 모두 찾기와 폴더 한정 검색이 질문마다 28만 개 payload를 전부 풀어야 해서 수 초씩 걸립니다. JSON 하나 푸는 데 15µs이므로 28만 × 15µs ≈ 4초입니다.
  • compact: 230MB를 더 줄이지만, 필드마다 값 ↔ JSON 변환 규칙을 새로 짜야 합니다. 숫자 형식, 필드 순서, 메타데이터 훅처럼 나중에 덧붙는 필드까지 챙겨야 합니다. 바깥 코드가 받는 payload가 지금과 한 글자도 다르지 않다는 보장이 깨지기 쉽습니다.

4. A안: payload 원문 보관 (hybrid)

4-1. 자료 구조

// 문서 단위 열쇠 — 같은 문서의 청크가 한 벌을 나눠 가진다(Arc)
struct DocKey {
    path: Box<str>,          // doc_path 원래 글자
    norm: Box<str>,          // pyutil::normcase(doc_path) — 질문마다 다시 계산하지 않게 미리
    content_hash: Box<str>,  // doc_by_hash 훑기용
}

struct Point {
    vec: Vectors 안의 칸 번호 또는 Vec<f32>/Vec<u16>,  // B안 참고
    raw: Box<str>,           // 디스크 payload JSON 글자 그대로
    text: Box<str>,          // 본문 — 모두 찾기·BM25 재구축·대기 청크 채우기가 훑는다
    doc: Arc<DocKey>,
    chunk_idx: i32,          // 없으면 -1 (정렬 기본값 0 으로 읽는다 — 지금과 같게)
    section_id: Option<i64>,
}
  • 돌려줄 때만 풉니다. payloads() · search() · doc_points() · section_chunks() · points_of()는 지금처럼 Payload(Map)를 돌려줍니다. 돌려줄 점의 raw만 serde_json::from_str로 풉니다. 실측으로 1개에 15µs이고, 검색 후보 수십 개면 1ms가 안 됩니다.
  • 원문 JSON을 그대로 들고 있어서 돌려주는 Map이 지금과 같습니다(필드 순서, 숫자 표기까지). 바깥 코드(retrieve, find, similar, brief, indexer, overview, uploads, cli)는 고치지 않습니다.
  • 본문은 raw 안에도 있고 text에도 있어 두 벌입니다(약 107MB). 이 몫을 없애는 방법(원문을 본문 앞뒤 두 토막으로 잘라 들기)은 복잡도에 비해 이득이 작아 이번 범위에서는 뺍니다(결정할 것 ③).

4-2. 쓰기 경로

  • upsert: 지금도 Value::Object(p).to_string()을 디스크에 씁니다. 같은 글자를 raw로 들고, 훑기 필드는 p에서 꺼냅니다.
  • set_payload_ids(문서 이동): raw를 풀고, 덮어쓴 뒤, 다시 글자로 만들어 디스크와 메모리에 같이 넣습니다. 그리고 doc를 새 경로의 DocKey로 바꿉니다.
  • DocKey 공유 표 HashMap<(path, content_hash), Arc<DocKey>>는 적재·삽입 때만 씁니다. 문서가 지워지면 Arc가 저절로 풀리므로 따로 청소할 필요가 없습니다(표에서 떼는 것은 delete_doc 때).

  • 칸 하나의 변환 오차는 최대 1.2 × 10⁻⁴, 상위 50 점수 차는 최대 5.1 × 10⁻⁵입니다.
  • 상위 10 묶음이 달라진 5문항은 10위와 11위 점수가 거의 같은 경우로, 경계에서 한 개가 바뀐 것입니다(평균 겹침 9.98). "순서까지 같음"이 182인 까닭도 상위 안에서 점수가 거의 같은 청크끼리 자리가 바뀐 경우입니다. 코퍼스의 절반이 완전 동일 사본이어서 이런 접전이 흔합니다.
  • dense 후보는 다음 단계에서 한 번 더 걸러집니다. RRF가 BM25 후보와 섞고, 리랭커가 다시 순위를 매긴 뒤 3개만 남깁니다. 그래서 최종 근거가 바뀌는 문항은 이보다 적을 것으로 봅니다. 다만 이것은 추정이고, 골든셋으로 확인합니다(검증).

5-2. 속도 — 질문당 전체 훑기 (28만 × 384)

내적 방식질문당설명
f32 지금 (store::dot, 8칸 묶음)68.7 ms빌드에 AVX가 켜져 있지 않아 SSE 4칸만 씀
f32 + AVX·FMA 명령28.8 ms명령만 바꾼 몫: −40 ms
f16 + F16C·AVX·FMA 명령22.2 ms읽는 양이 절반이 된 몫: −6.6 ms
f16 때문에 느려지는 일은 없습니다. 속도 이득은 대부분 AVX 내적 덕분이고, 이것은 f16과 무관하게 f32에도 적용할 수 있습니다. 비슷한 문서 찾기(doc_max_scan, 질의 벡터 32개 × 전체)는 같은 내적을 32번 하므로 이득이 그만큼 커집니다. 참고로 search()는 지금 dot()도 쓰지 않고 한 칸씩 더하는 반복자를 써서, 68.7ms보다 더 느릴 수 있습니다.

5-2-1. AVX 내적 구현 결과 (2026-11-13, 작업 순서 3단계)

AVX 내적을 구현했습니다(store.rs의 dot). CPU에 AVX·FMA가 있으면 쓰고, 없으면 예전 8칸 묶음으로 계산합니다. SIMPLERAG_NO_AVX=1로 끌 수 있습니다(비교 측정용). search()도 한 칸씩 더하던 계산을 같은 dot으로 바꿨습니다. 함께 28만 개 전체를 정렬하던 것을 상위 k개만 골라 정렬하도록 바꿨는데, 비교에 id가 들어가 동점이 없으므로 결과가 전체 정렬과 똑같습니다.

순위 비교(골든 v2 204문항): 예전 search(한 칸씩 더하기)와 비교하면 상위 10이 순서까지 같은 문항이 199/204, 묶음이 같은 문항이 202/204였습니다. 상위 50은 순서까지 같음 167/204, 묶음 같음 200/204입니다. AVX를 끄고 8칸 묶음만 써도 201/204·203/204로 비슷하게 갈립니다. 그러니 달라지는 곳은 점수가 1e-7 안팎으로 붙은 접전 청크이고, 더하는 순서가 바뀌면 생기는 차이입니다. 비슷한 문서 상위 20 문서는 AVX 켬·끔에서 순서가 같았습니다(점수 끝자리 15.97097 ↔ 15.97098만 다름). dense 검색 71ms 가운데 내적은 약 25ms이고, 나머지는 BTreeMap을 훑으며 (점수, id) 28만 개를 모으는 몫입니다. B안에서 벡터를 한 덩어리 배열로 옮기면 이 몫도 줄일 수 있습니다.

5-3. 설계

  • 메모리에서만 f16입니다. 디스크 vec BLOB은 지금처럼 f32로 씁니다. 적재할 때 정규화 → f16으로 바꿉니다.
  • 질의 벡터는 f32로 둡니다. 내적은 f16 칸을 f32로 풀면서 f32로 더합니다(F16C _mm256_cvtph_ps + FMA).
  • 명령이 없는 CPU에서는 한 칸씩 풀어서 계산합니다. F16C는 Intel 3세대(Ivy Bridge, 2012), AMD Piledriver 이후 모두 있어서, 대체 경로는 사실상 안전장치입니다. 고르는 일은 is_x86_feature_detected!로 시작할 때 한 번만 합니다.
  • 변환 코드는 half 크레이트를 쓰지 않고 작은 모듈(src/vecf16.rs)로 둡니다. f16_check.rs에서 검증한 반올림(가장 가까운 짝수)과 내적을 그대로 옮깁니다. 의존성이 늘지 않습니다.
  • 벡터를 덩어리 하나에 몰아 둡니다(선택). 점마다 Vec<u16>를 두면 머리 24바이트와 할당 단위가 붙습니다(28만 × 약 40B ≈ 11MB). 큰 배열 하나에 두면 이 몫이 없고 훑기도 연속 메모리라 더 빠릅니다. 다만 삭제와 삽입 때 칸 관리가 필요하므로, 1차는 점마다 Vec<u16>로 하고 2차 과제로 둡니다.

5-4. 정밀도가 흘러나가지 않게 — 벡터를 다시 쓰는 경로

메모리 벡터를 디스크에 다시 쓰는 경로가 두 곳 있습니다. 여기서 f16 값을 쓰면 디스크 벡터가 조금씩 깎입니다(재구축을 거칠 때마다 누적).

5-5. 스위치

config.yaml에 index.vector_f16: true(기본 켬)와 환경변수 SIMPLERAG_VECTOR_F16=0을 둡니다. 골든셋을 비교할 때와 Python 판과 결과를 맞대 볼 때(Python 판은 Qdrant f32) 끌 수 있게 하려는 것입니다. A안은 결과가 바뀌지 않으므로 스위치를 두지 않습니다.

6-4. 동작 설계

  1. 내리는 때: 마지막으로 생성 모델이나 리랭커를 쓴 뒤 generation.idle_unload_min분(기본 10, 0이면 끔) 동안 다시 쓰지 않으면 내립니다. chat 워커 안에 1분마다 시각을 확인하는 스레드 하나를 둡니다.
  2. 내리는 방법: Generator::unload()와 Reranker::unload()를 새로 만듭니다. 각자 load_lock을 잡고 상태를 None으로 바꾸면, 지금 있는 Drop이 llama_free·model_free와 ONNX 세션 해제를 해 줍니다. 답을 만드는 중이면 내리지 않도록, 사용 중 표시(원자 카운터)를 두고 0일 때만 내립니다.
  3. 다시 올리는 때 ① 미리: RAGSearchBox가 채팅 창을 열 때(open_panel·open_panel_window)나 입력칸에 첫 글자를 칠 때 워커에 /warm 한 줄을 보냅니다. 워커는 지금의 리랭커 백그라운드 적재(start_rerank_load)처럼 두 모델을 뒤에서 올리고 예열합니다. 질문을 치는 몇 초 동안 끝나므로 대부분 가려집니다.
  4. 다시 올리는 때 ② 그냥 질문이 올 때: 따로 할 일이 없습니다. Generator::stream·generate·warm과 Reranker::score가 이미 ensure_loaded()를 부르므로, 내려가 있으면 그 자리에서 올립니다. 이때는 첫 글자가 2~3.5초 늦어집니다.
  5. 상태 표시: 워커 상태 줄에 "쉬는 중(모델 내림)"을 더해 설정 창이나 트레이 툴팁에서 보이게 합니다(선택).
  6. 바뀌지 않는 것: 검색, 모두 찾기, 비슷한 문서, 자동 인덱싱은 내린 상태에서도 그대로 동작합니다. 이 기능들은 두 모델을 쓰지 않습니다.

7. ONNX 최적화 저장본 검토 (채택 안 함)

9. 바뀌지 않는 것

  • 디스크 형식: points.sqlite의 points(id, vec f32 BLOB, payload JSON)와 bm25_tf. 인덱스를 다시 만들 필요가 없고, 이전 판으로 되돌려도 그대로 열립니다.
  • 저장소 밖의 API: 함수 이름, 인자, 돌려주는 Payload.
  • Python 판(src/simplerag, Qdrant local): 손대지 않습니다.
  • BM25, 리랭커, 생성 모델, 임베딩 모델 파일과 그 계산 방식(C안은 언제 올리고 내리는지만 바꿉니다).

10. 위험과 대응

위험정도대응
f16 때문에 dense 상위 10 경계 청크가 바뀜(5/204)작음골든 v2로 검색 적중·근거를 비교해 떨어지지 않으면 기본 켬. 떨어지면 스위치를 끄고 A안만 냄
f16 벡터가 디스크로 새어 정밀도가 누적 손실막아야 함5-4: 복사·재사용은 sqlite f32에서 읽음. 단위 시험으로 "upsert한 BLOB = 원래 BLOB" 확인
A안의 raw와 text·doc가 어긋남(문서 이동 뒤 등)중간쓰기 경로를 Point::from_payload(&Payload) 하나로 모아, raw와 훑기 필드를 항상 함께 만듦
돌려주는 Map이 지금과 달라짐낮음원문 JSON을 그대로 풀기 때문. 전체 28만 점을 old/new로 비교하는 일회성 검사로 확인
AVX가 없는 CPU낮음시작할 때 감지해서 대체 경로로. 대체 경로로도 결과가 같은지 시험
Python 판과 맞대 보는 시험(bench/rust_vs_py)에서 dense 점수 차이낮음맞대 볼 때는 SIMPLERAG_VECTOR_F16=0
C안: 답을 만드는 중에 감시 스레드가 모델을 내림막아야 함사용 중 카운터가 0이고 load_lock을 잡았을 때만 내림. 스트리밍 중 내리기 시험 추가
C안: 미리 올리기 없이 질문하면 첫 글자가 2~3.5초 늦음중간창 열기·첫 입력 때 /warm. 오래 쉰 뒤 차가운 디스크 몫(1초 안팎 추정)은 실측 뒤 판단
C안: 내린 뒤 남는 몫(최대 약 405MB)낮음더 늘지 않음을 8회 되풀이로 확인. 필요하면 HeapCompact(약 300MB로)
C안: 백엔드 재선택·프로브가 다시 돎낮음내릴 때 backend 값은 남겨 두고 모델만 버림. 다시 올릴 때 프로브를 하지 않음

11. 검증 계획·합격 기준

  1. payload 동일성(A안): 설치본 인덱스 28만 점 전체에 대해 payloads(all)의 old와 new가 같아야 합니다. 합격: 28만/28만 같음
  2. 검색 결과(A안만): 골든 v2 204문항의 근거 id 목록이 지금과 완전히 같아야 합니다. 합격: 204/204
  3. 검색 품질(A+B안): 골든 v2 검색 적중(근거에 정답 출처)과 핵심어 점수를 f32와 비교합니다. 기존 측정 관례대로 McNemar로 판정합니다. 합격: 적중 감소 0문항, 또는 유의하지 않은 ±1문항 이내
  4. 모두 찾기·폴더 한정: 표본 질의 20개 결과가 같아야 합니다. 벡터를 쓰지 않으므로 완전히 같아야 합니다.
  5. 비슷한 문서: 표본 문서 20개의 상위 10 목록을 비교합니다. 합격: 평균 겹침 9.5/10 이상, 사본·다른 판 판정은 같음
  6. 메모리: mem_profile로 다시 쟀을 때 저장소 단계가 +700MB 이하여야 합니다(목표 약 650MB).
  7. 재구축 벡터 재사용: 작은 폴더로 --rebuild를 한 뒤 재사용된 청크의 BLOB이 재구축 전 BLOB과 바이트까지 같아야 합니다.
  8. 속도: dense 검색 시간과 비슷한 문서 찾기 시간이 지금보다 짧거나 같아야 합니다.
  9. C안 메모리: 설치본에서 idle_unload_min: 1로 두고 질문 → 1분 대기 → 질문을 5번 되풀이합니다. 작업 관리자와 카운터로 쉬는 동안의 전용 메모리와 공유 GPU를 봅니다. 합격: 쉬는 동안 공유 GPU 50MB 이하, 전용 메모리가 되풀이할수록 늘지 않음
  10. C안 첫 글자 시간: 내린 상태에서 (가) 창을 열고 5초 뒤 질문할 때와 (나) 바로 질문할 때의 TTFT를, 모델이 올라와 있을 때와 비교합니다. 합격: (가) +1초 이내, (나) +4초 이내
  11. C안 안전: 긴 답을 스트리밍하는 중에 감시 주기를 강제로 돌려도 답이 끊기지 않아야 합니다. 내린 상태에서 검색·모두 찾기·자동 인덱싱이 그대로 돼야 합니다.

측정할 때는 기억해 둔 관례대로 벡터 지연을 끄고, 실행 중인 MoAI-S는 닫은 뒤 잽니다(램 압박으로 시간이 부풀지 않게).

12. 작업 순서

  1. A안: store.rs의 Point와 DocKey, 쓰기 경로 통일, 함수별 필드 접근 교체. 검증 1·2·4·6(A안만).
  2. AVX 내적(f32): search와 scan_part를 dot으로 통일하고 AVX·FMA 경로를 추가합니다. 결과가 순서까지 그대로인지 확인합니다(부동소수 덧셈 순서가 바뀌므로 점수 끝자리 차이는 허용).
  3. B안: vecf16.rs, 적재 변환, points_of·take_vectors sqlite 읽기, 스위치. 검증 3·5·6·7·8.
  4. C안: unload()·사용 중 카운터·감시 스레드·/warm(워커), 창 열기·첫 입력 때 /warm 보내기(RAGSearchBox), 설정값. 검증 9·10·11.
  5. 버전을 올릴 때 docs/changelog.html과 릴리스 설명에 "쉬는 동안 메모리 약 3GB 절감(공유 GPU 포함), 인덱스 다시 만들 필요 없음"을 적습니다.

각 단계는 따로 커밋합니다. B안의 품질 검증이 기준에 못 미치면 B안만 빼고 냅니다. C안은 A·B안과 겹치는 파일이 없어(store.rs 밖) 순서를 바꾸거나 따로 낼 수 있습니다. 쉬는 동안 효과가 가장 크므로 C안을 먼저 하는 것도 방법입니다(결정할 것 ⑦).

13. 결정할 것

① f16 기본값골든 v2에서 적중 감소가 0이면 기본 켬을 권합니다. ±1문항(유의하지 않음)이면 어떻게 할지 정해야 합니다. 제안: 켬. 경계 접전 청크라서 리랭커가 흡수할 것으로 봅니다.
② AVX 내적을 A안과 같이 낼지f16과 무관하게 dense 검색이 질문당 약 40ms 빨라집니다. 결과 순서가 끝자리 반올림 때문에 아주 드물게 바뀔 수 있습니다. 제안: 같이 내고, 검증 2를 "id 목록 같음"으로 확인합니다.
③ 본문 두 벌(약 107MB) 없애기원문 JSON을 본문 앞뒤 토막으로 잘라 들면 107MB를 더 줄일 수 있습니다. 대신 풀 때 이어 붙이는 코드와 따옴표 처리(escape)를 신경 써야 합니다. 제안: 이번에는 하지 않습니다. 메모리가 더 필요해지면 다음 과제로 합니다.
④ int8 벡터f16 대신 int8로 하면 벡터가 약 104MB가 되어 103MB를 더 줄입니다. 대신 순위 변화가 f16보다 커질 수 있고 따로 실측해야 합니다. 제안: 이번 범위 밖입니다.
⑤ 내린 뒤 HeapCompact남는 몫이 405MB에서 약 300MB로 줄어듭니다. Win32 호출 한 줄이면 됩니다. 제안: 넣습니다. 내릴 때 한 번만 부르므로 부담이 없습니다.
⑥ 리랭커 토크나이저는 남겨 두기다시 올리는 시간이 약 0.6초 줄어듭니다. 대신 토크나이저 메모리(재 보지 않았으며 수십 MB로 추정)가 상주합니다. 제안: 토크나이저 메모리를 잰 뒤 정합니다.
⑦ C안 기본값과 순서기본 10분 켬을 권합니다. 0이면 끕니다. 쉬는 동안 효과가 가장 크므로 C안을 A·B안보다 먼저 하는 것도 방법입니다. 제안: C안 먼저 → A안 → AVX 내적 → B안 순서로 합니다.

14. 부록 — 측정 재현

측정 예제 다섯 개는 rust/simplerag/examples/에 있습니다(mem_profile · store_mem · f16_check · unload_check · onnx_cache). 설치본 데이터로 돌리려면 환경변수를 설치 폴더로 맞춥니다.

$d = "$env:LOCALAPPDATA\Programs\MoAISearch"
$env:SIMPLERAG_HOME = $d

$env:SIMPLERAG_CPU_LIB = "$d\runtime\llama_cpu"

# chat 워커 구성요소별 메모리
cargo run --release --example mem_profile -- "연차 휴가는 며칠인가요?"
# 저장소 보관 방식별 메모리 (방식마다 따로 실행)
cargo run --release --example store_mem -- "$d\rag_index\points.sqlite" hybrid
# f16 순위·속도 (질문 파일 = 골든 v2 q 한 줄씩)
cargo run --release --example f16_check -- "$d\rag_index\points.sqlite" golden_q.txt
# 생성 모델·리랭커 내렸다 올리기 (both | rr | gen), TRIM=1 이면 내린 뒤 HeapCompact
cargo run --release --example unload_check -- 8 both
# ONNX 최적화 저장본 적재 시간 (모델 폴더, onnx 파일, 저장 폴더, 스레드, inter1)
cargo run --release --example onnx_cache -- "$d\models\bge-reranker-base-int8" model_int8.onnx $env:TEMP 4 1
