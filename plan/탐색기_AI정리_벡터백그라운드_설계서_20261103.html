3AI 역할 전환 — 실측

큰 위험은 Qwen3-1.7B 처럼 작은 모델이 여러 문서를 제대로 요약하느냐였다. 실제 인덱스 사본(217개 문서)에서 키워드 6개의 찾기 결과를 뽑아 시험했다. 1차에서 정리 지시문의 문제를 찾고, 2차에서 고친 두 방식을 같은 조건으로 비교했다.

4AI 역할 전환 — 설계

채팅 모드 — 그대로

  • 질문 → 다시 검색 → 근거로 답변(/ask)
  • 지시문 · 관련도 문턱 · 멀티턴 · 업로드 변경 없음
  • 골든셋 결과에 영향 없음

탐색기 모드 — 새 동작

  • 검색어 + 화면 목록의 상위 최대 3건 → 문서별 한 줄(/brief)
  • 다시 검색하지 않음 · 조건 칩이 자연히 반영됨
  • 이름은 "AI 참고 답변"

4-1. 처리 흐름

목록 상위 후보 최대 8건→제외: 관련도 낮음 · 본문 없음→거의 같은 본문 제거→ 상위 최대 3건 — 문서마다 한 줄→창에 조립
  • 입력 글 — 문서별 최고 점수 쪽의 text 를 450자까지 쓴다.
  • 겹침 제거 — 글자 2개 조각의 겹침이 0.8 이상이면 뒤 문서를 뺀다(버전만 다른 사본 대응). 제외 수는 창에 표시한다.
  • 조건만 있는 찾기 — 쪽 줄이 없으므로 워커가 해당 문서의 앞쪽 청크를 가져온다(docs_scope + payloads).
  • 안전 대체 — 줄이 너무 짧거나, 되뱉기이거나, 근거에 없는 숫자가 있으면 그 줄은 생성문 대신 찾기 발췌를 "원문 발췌"로 보여 준다.
  • 모델 — 지금 쓰는 답변 모델을 그대로 쓴다. config.yaml 의 모델 · 지시문은 건드리지 않고, 새 지시문은 prompts.rs 상수로 둔다.

4-2. 정리 문서 수 — 상위 최대 3건

목록의 모든 문서를 요약하지 않고, 걸러 낸 뒤 관련도 순 상위 최대 3건만 정리한다. 나머지는 목록에서 직접 본다.

근거내용
네 번째 줄의 가치2차 시험 6개 검색어 중 새 내용이 분명한 경우 1건, 일부 겹침 1건이고, 나머지 4건은 앞 줄과 겹치거나 일반 정의 · 지시문 되뱉기였다.
시간생성이 5회 → 4회로 줄어 전체 시간이 약 20% 짧아진다(4건 실측 34.7초 기준 약 27.8초, 계산값). 첫 줄 시간은 변하지 않는다.
읽기 부담목록 아래 창의 기본 높이에서 스크롤 없이 읽기 쉽다.
  • 순서 기준 — 화면 정렬이 이름 · 날짜여도 항상 관련도 순으로 고른다. 그래서 정렬을 바꿔도 정리는 다시 만들지 않는다.
  • 겹침 제거 뒤 3건 — 후보를 최대 8건 보내 사본을 빼도 3건이 채워지게 한다. 원본 상위 3건이 사본이면 다른 문서가 올라온다.
  • 3건 미만 — 있는 만큼만 정리한다. 문서당 생성 1회다.
  • 건수 고정 — 설정 · [더 정리] 버튼은 두지 않는다. 창 머리에 "찾은 문서 14건 중 상위 3건"을 표시해 나머지가 있음을 알린다.

4-3. 워커 명령 /brief

/brief {"q":"AI 에이전트 보안","items":[{"no":1,"doc":"…pdf","path":"C:\\…","page":12,"text":"…"},…],"skipped":3}
  • 출력은 기존 ── 근거 · @ev · ── 답변 · ── 소요 블록을 재사용해 워커 파서 · 사건을 새로 만들지 않는다. 답변 본문은 [n] … 줄을 흘리고, 공통 요약은 [요약] … 줄로 마지막에 낸다. 화면이 맨 위에 놓는다.
  • generator.stream 은 사용자 메시지가 [근거]/[질문] 고정이므로 사용자 메시지를 직접 받는 함수를 나눈다.
  • 시작 줄 기능 목록에 brief 를 추가하고, 없으면 화면에 새 빌드 안내를 표시한다. /find 와 같은 Rust 전용 기능이라 Python 워커는 바꾸지 않는다.

4-4. 취소 — 이 설계의 필수 조건

AI 가 쓰는 동안 워커가 BUSY 라서 다음 찾기가 기다린다. 입력 줄을 별도 스레드에서 읽고, /cancel 이 오면 생성 루프가 이미 보고 있는 INTERRUPT 를 세운다. 문서 사이에서도 확인한다. 새 찾기 · 창 닫기 · [중지] 버튼이 취소를 보낸다. 채팅 패널에도 나중에 [중지] 버튼을 붙일 수 있는 기반이 된다.

답변 시간 한도 주의 — BUSY 가 AnswerTimeoutSec(기본 60초)를 넘으면 워커를 죽이고 다시 올린다. 느린 PC · 정밀 모드에서는 문서별 생성 합계가 이를 넘을 수 있다. 토큰이 나올 때마다 BUSY 시작 시각을 갱신하거나, 문서별 생성에는 별도 한도를 둔다.

4-5. 좋아지는 점과 잃는 점

좋아지는 점

  • 목록과 AI 답이 항상 같은 문서를 말한다
  • 조건 칩이 그대로 반영된다
  • 줄마다 문서가 묶여 어느 문서 이야기인지 분명하다
  • 첫 줄이 빨리 나온다

잃는 점 · 주의

  • "출장비 얼마야?" 같은 질문의 직답은 약해진다 → 창에서 채팅 모드로 이어 묻기 제공
  • 문서당 앞쪽 근거 하나만 보므로 문서 전체 요약은 아니다 → "검색된 부분 기준" 표시
  • 상위 3건 밖 문서는 정리에 나오지 않는다 → 건수를 창 머리에 표시

6전체 벡터 백그라운드 — 검토

판단 — 제안대로 진행한다. 단계형 인덱싱의 저장 · 채우기 · 재개 기능이 이미 있어 기준만 넓히면 된다. 다만 "텍스트 추출 · 청킹"만이 아니라 메타데이터 · BM25 까지 앞 단계에 포함해야 벡터 없이 바로 검색된다.

6-1. 왜 지금은 효과가 안 나는가

명령줄 전체 인덱싱은 새 청크를 누적해 500을 넘으면 미룬다. 앱은 /index-doc 를 문서마다 보내고 누적값이 매번 0이다(commands.rs:139). 그래서 문서 하나가 500청크를 넘을 때만 미뤄진다. 작은 문서가 많은 폴더는 전부 그 자리에서 임베딩하며, 그동안 워커가 묶여 찾기도 기다린다.

6-2. 기대 효과 (기존 실측값으로 계산, 구현 뒤 재측정)

구간 (1쪽 기준)지금변경 후
파싱 · 청킹 · 메타 · 저장7.8ms7.8ms

전체 일의 양은 줄지 않는다. 뒤에서 도는 시간까지 합하면 쉬는 조건만큼 조금 더 걸린다. 얻는 것은 화면 체감과 인덱싱 중 찾기 응답이다. 문서별 워커 점유가 짧아져 찾기 대기도 줄어든다. 파싱이 오래 걸리는 큰 문서의 대기는 남는다.

6-3. 그대로 두면 생기는 문제

위험지금 코드대책
검색 공백 라운드 도중 새 문서가 안 찾아짐지금은 벡터로 바로 찾힌다. BM25 는 문서 대기열이 끝나고 10초 쉰 뒤에야 돈다(jobs.rs:357). 벡터까지 미루면 그동안 어느 쪽으로도 찾을 수 없다.라운드 중 20건 또는 30초마다 BM25 덧붙이기(§7-2)
채우기 중단 60분 뒤 워커가 내려감유휴 판단은 마지막 질문 기준이고(worker.rs:1085), 채우기 명령은 이 시각을 갱신하지 않는다. 명령 사이에 내려가면 다음 사용 때까지 멈춘다.대기 청크가 있으면 내리지 않는다(§7-3)
병합 비용 반복/bm25 는 변경이 5%를 넘으면 전체 재구축을 한다(운영 규모 36~49초). 중간 반영이 잦으면 초기 인덱싱 때 반복된다.중간 반영은 병합 금지, 라운드 끝에만 병합
알림 소음채우기가 끝나면 항상 "벡터 채우기가 끝났습니다" 알림(jobs.rs:587). 저장할 때마다 뜨게 된다.대상이 500청크 이상일 때만 알림
일시적 정확도 저하벡터 없는 청크는 BM25 · 동의어로만 찾는다. 기존 측정: 골든 차이 없음, 일상어 CR 0.76 → 0.62(전부 벡터 없는 경우).수용. 소량은 몇 초~수십 초면 채워지고, 대량은 상태 줄에 표시
측정 재현성명령줄 인덱싱 직후 측정하는 벤치가 있다.명령줄 동작은 유지하고 앱 워커에만 적용

6-4. 그대로 재사용되는 것

  • 길이 0 벡터로 대기 표시, fill_pending · /embed-pending — 64개씩, 질문 뒤 2초 쉬면 진행, 약 1초마다 비켜 줌
  • 워커 재시작 뒤 이어 채우기, 수정 문서의 벡터 재사용, 진행 글 "벡터 채우는 중 N / M"
  • 채우기는 앱 워커의 4스레드로 돌아 뒤에서 도는 동안 부담이 더 작다

7전체 벡터 백그라운드 — 설계

문서 추출 · 청킹 · 메타 · 저장→BM25 중간 덧붙이기→검색 가능 · 화면 "완료"→쉴 때 벡터 채우기→하이브리드 검색 완성

7-1. 기준 변경

설정 index.vectors_background(기본 true)를 추가한다. 켜지면 /index-doc 에서 defer_over: Some(0) 으로 다시 쓸 벡터가 없는 새 청크를 모두 미룬다. 작은 문서 예외는 두지 않는다. 경로가 하나여야 단순하고, 1건이면 2초 뒤 어차피 채워진다. Python · Rust 같은 키로 넣는다(config.py 의 DEFER_VECTORS_OVER 와 같은 위치).

경로벡터이유
앱 자동 · 수동 인덱싱(/index-doc)전부 미룸이번 변경 대상
명령줄 index · --rebuild지금대로(누적 500 초과 시 미룬 뒤 채움)측정 재현성
채팅 업로드 문서즉시 임베딩올린 직후 그 문서로 답해야 한다

7-2. BM25 중간 반영

  • jobs.rs — 라운드 도중 20건 또는 30초마다 대기열을 잠시 멈추고 /bm25 {"merge":false} 를 보낸다. 덧붙임을 저장할 때 쌓인 전체를 다시 쓰므로, 지난 반영 시간의 20배는 쉬어 부담을 약 5% 안으로 묶는다.
  • refresh_bm25 — 병합 금지 옵션을 받는다. 메타 마무리(hook::finish)도 라운드 끝에만 한다.
  • 마지막 /bm25 는 지금처럼 병합 · 메타 마무리를 한다.
  • 중간 반영은 고아 청소를 건너뛴다. 라운드 끝 반영에서 청소한다.

7-3. 채우기 유지

  • 워커에 "최근 작업 시각"을 따로 두고 유휴 내리기 판단에 쓴다. t_last_ask 는 질문 우선 판단용이라 건드리지 않는다.
  • 대기 청크를 채우는 동안에는 내리지 않는다. 워커가 죽으면 기존 재시작이 다시 띄우고 대기 청크를 이어 채우므로 따로 넓히지 않았다. 트레이에서 일부러 내린 경우는 다음 시작 때 이어 간다.
  • 채우기 실패 시 이번 워커에서는 멈추는 현재 동작을 유지한다.
