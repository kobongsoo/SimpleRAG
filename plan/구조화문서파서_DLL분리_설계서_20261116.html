구조화 문서 파서 DLL 분리 설계서

SimpleRAG Rust 판 안에 있는 구조화 추출기(docmodel)와 스캔 문서 OCR(ocr)을 별도 저장소 D:\Project\Struct-DocParse-OCR-rust 의 DLL 하나로 떼어 낸다. DLL 은 파일을 받아 블록 단위 글 + 라벨(heading · paragraph · header · footer · table 등)을 돌려주고, OCR 은 켜고 끌 수 있다(기본 켬). SimpleRAG 는 이 DLL 을 실행 시점에 적재해 쓴다.

1. 요약

무엇을 옮기나docmodel 파서 12개 파일 · ocr 6개 · pdfium · 폴백 추출기(legacy · extract) · 보조(xmldom · htmlparse · xlsdate · structure 복사). 약 7,300줄.
어떻게 부르나C ABI DLL struct_docparse.dll. 입력은 UTF-8 경로 + 옵션 JSON, 출력은 문서 JSON(블록 목록). 언어 무관하게 쓸 수 있다.
OCR 스위치열 때 옵션 · 실행 중 바꾸기 · 호출마다 덮어쓰기 3단. 기본 켬. 모델이 없으면 꺼진 것처럼 동작하고 이유를 알려 준다.
SimpleRAG 쪽새 docparse.rs 가 DLL 을 적재해 지금의 Document·Block 으로 바꿔 준다. 절 조립·청킹·OCR 대기열은 그대로 SimpleRAG 에 남는다.
핵심 원칙: 분리 전후 블록 JSON 이 글자 하나까지 같아야 한다. 그러면 다시 인덱싱할 필요가 없고, OCR 캐시(내용 해시 · 엔진 이름)도 그대로 쓴다. 기능 추가·개선은 분리가 끝난 뒤 DLL 쪽에서 따로 한다.

3. 목표와 범위

목표

  • 문서 파서를 SimpleRAG 와 따로 버전 관리·빌드·시험할 수 있다(다른 프로그램에서도 쓸 수 있다).
  • 입력 파일 하나 → 블록 목록(글 + 라벨 + 제목 수준 + 쪽 + 표 칸 + 출처)을 돌려준다.
  • OCR 을 켜고 끌 수 있다. 기본은 켬.
  • SimpleRAG 는 DLL 을 적재해 지금과 똑같은 결과를 얻는다.

범위 밖 (이번에 하지 않음)

  • 파서 품질 개선·새 형식 추가 — 분리 뒤 DLL 저장소에서 따로.
  • 절 조립·청킹·임베딩 — SimpleRAG 에 남는다.
  • OCR 대기열·진행 표시·실패 목록 같은 운영 정책 — SimpleRAG 에 남는다. DLL 은 "이 쪽을 OCR 해라" 만 한다.
  • Python 판 docmodel 교체 — 측정용으로 그대로 둔다(§15-4).

4. 전체 구조

DLL 은 pdfium.dll 의 유일한 주인이 되고, onnxruntime.dll 은 SimpleRAG(임베딩·리랭커)와 DLL(OCR)이 함께 쓴다. 두 DLL 모두 지금처럼 프로그램 폴더에 하나씩만 둔다.

5. 새 저장소 구성 — D:\Project\Struct-DocParse-OCR-rust

sdp-core 와 sdp-ffi 를 나누는 이유: 파서 시험은 FFI 없이 Rust 단위 시험으로 빠르게 돌리고, DLL 껍데기는 얇게 유지해 ABI 를 바꿀 일을 줄인다. 모든 함수에는 D:\Project 공통 규칙의 한글 헤더 주석을 단다(Rust 도 같은 형식 — 지금 코드와 같음).

6. 출력: 블록과 라벨

요청에 적힌 "head" 는 두 가지로 나뉜다 — heading(본문의 제목·절 이름)과 header(쪽마다 반복되는 머리글). 지금 코드도 이 둘을 구분하고, 검색에서는 header 를 빼고 heading 은 절 경로로 쓴다. 이름은 지금 값을 그대로 쓴다.

모든 블록에 공통: text, page(쪽·슬라이드·시트, 1부터), source(parser · inferred · regex · ocr), synthetic(문서에 없는 글, 예: "슬라이드 3"). path(제목 경로)는 DLL 이 채우지 않는다 — 절 조립은 SimpleRAG 몫이다.

결과 JSON (지금 *.blocks.json 에 버전·OCR 정보를 더한 모양)

{
  "schema": 1,                       // 이 JSON 모양의 버전
  "blocks_version": 5,               // 추출 결과가 바뀌는 코드 변경마다 올림 → 호스트가 재인덱싱 판정
  "parser": "struct_docparse 0.1.0",
  "format": "pdf",                   // docx | pptx | xlsx | hwpx | doc | pdf | html | md | ipynb | image | legacy
  "title": "2026 사업계획",
  "pages": 12,
  "warnings": ["OCR 부분 100/140쪽 (상한)"],
  "raw_text": null,                  // 폴백(legacy) 이면 평문, 블록 경로면 null
  "ocr": {                           // OCR 상태 — 지금의 DocOcr (note/take_note 를 대신)
    "enabled": true, "reason": null, // 꺼졌으면 reason: "off" | "models_missing" | ...
    "pending": [7, 8],               // 아직 OCR 하지 않은 쪽(deferred 모드)
    "done": [3, 4, 5],               // OCR 글이 들어간 쪽
    "whole": false                   // 그림 파일처럼 전부 OCR 글인가
  },
  "blocks": [
    {"type": "header", "text": "대외비", "page": 1},
    {"type": "heading", "text": "1. 개요", "level": 1, "page": 1},
    {"type": "paragraph", "text": "본 계획은 …", "page": 1},
    {"type": "table", "text": "| 항목 | 금액 |\n…", "rows": [["항목","금액"],["인건비","3억"]], "header_rows": 1, "page": 2},
    {"type": "paragraph", "text": "스캔된 쪽의 글", "page": 3, "source": "ocr"},
    {"type": "footer", "text": "㈜회사", "page": 1}

기본값 필드는 지금처럼 뺀다(level:0, source:"parser" 등). 글 위치 좌표는 이번에 내보내지 않는다 — 지금 SimpleRAG 는 쓰지 않는다. 마스킹·원본 강조 같은 쓰임새를 위한 좌표 출력은 §16-2 추후 검토에 정리했다.

왜 C 구조체가 아니라 JSON 인가: 블록 수·필드가 문서마다 다르고 앞으로 늘어난다. JSON 이면 필드를 더해도 ABI 가 그대로이고, Rust·Python(ctypes)·C# 어디서든 바로 읽힌다. 지금 진단 덤프와 같은 모양이라 같음 검증도 쉽다. 비용(직렬화·해석)은 §11 에서 잰다.

7. DLL 함수 (C ABI)

문자열은 모두 UTF-8, NUL 끝. DLL 이 돌려준 문자열은 반드시 sdp_free 로 돌려준다(할당자가 다르기 때문). 반환값은 상태 코드, 결과는 out 포인터로.

8. OCR 켜기·끄기

세 단계 스위치 (뒤가 앞을 덮는다)

  1. 열 때 — sdp_open 의 ocr.enabled (기본 true).
  2. 실행 중 — sdp_set_option(h, "ocr.enabled", "false"). 설정 창에서 OCR 을 끄면 SimpleRAG 가 이걸 부른다. 끄는 순간 엔진도 내린다.
  3. 호출마다 — sdp_parse 의 call_opts.ocr.enabled. 예: 비슷한 문서 찾기처럼 OCR 이 필요 없는 빠른 추출.

켜져 있어도 모델 파일이 없으면 꺼진 것처럼 동작하고 ocr.reason = "models_missing" 과 로그 경고(한 번)를 남긴다 — 지금 ocr::enabled() 와 같다.

왜 두 모드인가

SimpleRAG 는 OCR 을 나중에 천천히 한다 — 먼저 글자층만으로 색인하고, 쉬는 동안 OCR 대기열을 돌린 뒤 다시 반영한다 (indexer::run_ocr_queue). 이 정책은 SimpleRAG 에 남기고, DLL 은 deferred 로 "어느 쪽이 남았는지" 만 알려 주고 sdp_ocr_pages 로 "이 쪽을 OCR 해 캐시에 넣어라" 를 받는다. 반면 처음 쓰는 다른 프로그램은 한 번 부르면 다 되는 inline 이 편하므로 DLL 기본값은 inline 으로 둔다(§15-3).

OCR 캐시는 지금과 같은 자리·이름을 쓴다: <root>/ocr_cache/<해시 앞 2자>/<SHA-1>.json, 엔진 문자열 ppocrv6-tiny-det+ko-ppocrv5-mobile-rec/1. 그래서 분리 뒤에도 다시 OCR 하지 않는다.

9. 스레드·메모리·오류

주제설계
스레드핸들 하나를 여러 스레드가 같이 쓴다(SimpleRAG 는 준비 스레드 여러 개가 동시에 추출). 파서는 상태가 없고, pdfium 은 DLL 안 전역 Mutex 하나, OCR 엔진도 Mutex 하나 — 지금과 같다.
pdfium 주인은 하나pdfium 은 스레드 안전하지 않고 FPDF_InitLibrary 를 프로세스에서 한 번만 해야 한다. SimpleRAG 와 DLL 이 각자 적재해 각자 Mutex 를 걸면 같은 pdfium.dll 에 동시 호출이 생긴다. 그래서 SimpleRAG 의 pdfium.rs 를 없애고 find.rs · meta/extract.rs · cli.rs 의 PDF 호출을 DLL 함수(sdp_pdf_*)로 바꾼다.
onnxruntime 공유둘 다 ort load-dynamic 으로 같은 onnxruntime.dll 을 적재한다. 같은 모듈을 가리키므로 버전은 자동으로 같다. 두 쪽이 각자 OrtEnv 를 만들 때 문제가 없는지 시험으로 확인한다(§14). ort 버전은 두 저장소에서 같은 값(=2.0.0-rc.10)으로 묶는다.
panic모든 extern "C" 함수 몸통을 catch_unwind 로 감싸 SDP_EPANIC 로 바꾼다(FFI 경계를 넘는 unwind 는 정의되지 않은 동작). 형식 파서 안의 panic 은 지금처럼 폴백으로 넘긴다.
메모리결과 문자열은 DLL 이 만들고 sdp_free 로 돌려받는다. 메모리 주인은 DLL 하나로 명확하다. OCR 엔진은 지금처럼 쓰고 나면 sdp_ocr_unload.
오류문스레드별 마지막 오류문(sdp_last_error). 오류문 앞머리는 지금과 같게(OCRError: 등) — SimpleRAG 의 why_of 와 설정 > 로그 탭이 그 앞머리로 분류한다.
경로UTF-8 로 받아 Rust Path 로 연다(Windows 와이드 API). 한글·긴 경로 시험 포함.

11. 같음 검증·성능

  1. 기준 만들기 — 분리 전 simplerag-rs extract --blocks --dump 로 시험 묶음 전부의 *.blocks.json 을 남긴다: sample/, sample_pdf/, 골든셋 v2 원문, 운영 폴더(3,532건, 50분 걸린 그 목록 — 본문은 저장소에 넣지 않고 해시만).
  2. DLL 판 비교 — sdp.exe compare <폴더> tests/golden: 블록 JSON 을 필드 단위로 비교해 다른 문서·블록을 보여 준다. 목표 차이 0건.
  3. OCR — 캐시를 지운 상태로 스캔 PDF · 그림 묶음(bench/bench_ocr.py 의 것)을 inline 으로 돌려 지금 캐시 JSON 과 줄·점수 비교. 그리고 캐시를 둔 상태로 다시 OCR 하지 않는지 확인.
  4. 끝단 — SimpleRAG 로 골든셋 색인 → 청크 수·청크 ID 가 같고 검색 @1 · 근거 수가 그대로인지(규칙 지표만. RAGAS 판정 서버는 요청 때만).
  5. 성능 — 문서당 추출 시간과 메모리를 전후 비교. JSON 직렬화·해석 비용이 추출 시간의 2% 를 넘으면 큰 표 문서부터 원인을 본다. (인덱싱 시간의 92.6% 는 임베딩이라 추출 쪽 변화는 작을 것으로 본다 — 2026-10-30 실측.)
  6. 동시성 — 준비 스레드 4개 동시 추출 + OCR 대기열 + 임베딩을 한 프로세스에서 30분 돌려 충돌·메모리 증가가 없는지.

15. 정할 것 (권장안 포함)

15-1. 출력 형식 — JSON 문자열 / C 구조체 배열권장: JSON. 필드가 늘어도 ABI 가 그대로이고 지금 진단 덤프와 같다. 성능은 §11-5 에서 확인.
15-2. 폴백 평문 추출(.hwp .ppt .xls .txt .csv, 파서 실패 시)도 DLL 로 옮길까권장: 옮긴다. 그래야 SimpleRAG 의 "문서 → 글" 입구가 하나가 되고, 폴백 PDF 도 pdfium 을 쓰므로 pdfium 주인을 하나로 만들 수 있다. 결과는 format:"legacy" + raw_text(라벨 없음).
15-3. DLL 의 OCR 기본 모드 — inline / deferred권장: DLL 기본은 inline(다른 프로그램이 한 번 불러 끝나게), SimpleRAG 는 항상 deferred 를 넘긴다. OCR 켬/끔 기본값은 요청대로 켬.
15-4. Python 판도 DLL 을 쓰게 할까권장: 이번엔 ctypes 래퍼만 만들고 Python 판 docmodel 은 그대로. Python 판은 측정·비교용 기준이라 바꾸면 기존 측정과 이어지지 않는다. 래퍼는 bench 스크립트에서 DLL 결과를 재는 데 쓴다.
15-5. 이름권장: DLL struct_docparse.dll, 함수 접두 sdp_, crate sdp-core/sdp-ffi/sdp-cli. 저장소 이름(Struct-DocParse-OCR-rust)과 맞춘다.
15-6. docx·pptx·hwpx 안에 든 그림도 OCR 할까현재 코드도 OCR 하지 않는다 — OCR 은 PDF 스캔 쪽과 그림 파일(.png .jpg .tif .bmp)만 한다(docx·pptx·hwpx·xlsx·doc 파서는 XML 글자만 읽음).
권장: 이번엔 안 한다(동작이 바뀌어 같음 검증이 깨진다). 분리 뒤 DLL 0.2 에서 옵션 ocr.embedded_images(기본 끔)로 따로 실측해 결정 — §16-1 추후 검토.

16. 추후 검토 (분리 이후)

이번 분리 범위에는 넣지 않고, DLL 이 자리 잡은 뒤 DLL 저장소에서 따로 검토한다.

16-1. 문서 속 그림 OCR (docx · pptx · hwpx · xlsx)

지금은 PDF 스캔 쪽과 그림 파일만 OCR 한다. 문서 안에 붙여 넣은 화면 캡처·스캔 이미지·표 그림의 글은 검색되지 않는다.

항목검토 내용
그림 위치docx word/media/*(본문 a:blip r:embed), pptx ppt/media/*(슬라이드별 관계), hwpx BinData/*(hp:pic 참조), xlsx xl/media/*(그리기 개체). 본문 어디에 있었는지 알아야 블록 순서에 끼울 수 있다.
결과 블록그림 자리에 paragraph + source:"ocr" 로 넣는다. 바로 앞뒤 caption 과 묶을지, 그림 대체 글(alt text)과 겹치면 뺄지 정한다.
거르기로고·아이콘·서명 같은 작은 그림, 문서마다 반복되는 같은 그림(머리글 로고)은 건너뛴다. 기준은 PDF 스캔 쪽 판정의 "짧은 변 · 반복 그림" 규칙을 재사용.
캐시·대기열캐시 열쇠를 그림 바이트의 해시로 하면 같은 그림이 든 여러 문서가 한 번만 OCR 된다. SimpleRAG 는 지금 대기열(deferred)에 "문서 + 그림 번호" 를 넣는 방식으로 확장.
스위치ocr.embedded_images (기본 끔), ocr.enabled 가 꺼지면 함께 꺼짐. 켜면 blocks_version 을 올려 재인덱싱 판정에 반영.
실측할 것운영 폴더에서 그림이 든 문서 비율·문서당 그림 수, 그림 OCR 이 늘리는 시간(쪽당 시간 × 그림 수), 골든셋 검색 @1 · 근거 수 변화, 잡음 청크(무의미한 OCR 글) 비율.
판단 기준: 검색 지표가 오르거나 같고, 인덱싱 뒤 OCR 대기열 시간이 감당할 수준일 때만 기본값을 켬으로 바꾼다. 그 전까지는 옵션으로만 둔다.

16-2. 글 위치 좌표 출력 (마스킹 · 원본 강조)

이번 분리에서는 좌표를 내보내지 않는다(결과가 커지고 SimpleRAG 검색·답변은 글만 쓴다). 아래 쓰임새가 실제 계획에 오르면 검토한다.

쓰임새좌표가 필요한 이유
마스킹(가리기)주민번호·전화번호를 글에서 찾아도 그림 어디인지 알아야 덮을 수 있다. 스캔 문서를 외부에 낼 때.
원본 위 강조검색어·답변 근거가 쪽 어디에 있는지 원본 위에 칠해 보여 준다.
근거 미리보기답변 출처를 해당 영역만 잘라 보여 준다("3쪽 오른쪽 위 표").
배치 분석두 단 읽기 순서, 줄 맞춤으로 표 칸 되살리기, 양식의 "항목: 값" 짝 찾기.

지금 코드에 이미 있는 것

  • OCR 줄 상자는 이미 계산·저장한다 — group_rows(줄 묶기), drop_overlapping(글자층과 겹치는 OCR 줄 제거), OCR 캐시의 줄마다 b.
  • PDF 글자층의 글자 위치도 표 검출(pdftable::CharPos)에서 이미 읽는다.

그래서 새로 계산할 것은 거의 없고, 결과에 실어 보내는 모양을 정하는 일이 대부분이다.

정해야 할 것

항목검토 내용
스위치호출 옵션 geometry: none(기본) · lines(줄 상자) · words(단어 상자). 기본 결과 크기는 그대로 유지.
좌표 단위지금 OCR 상자는 200dpi 로 그린 그림의 픽셀 기준이다. 원본 PDF 에 덮으려면 pt 단위 + 쪽 회전 반영으로 바꿔 내보낸다. 그림 파일은 픽셀 그대로. 결과에 unit(pt | px)과 쪽 크기를 함께 적는다.
블록과 줄의 대응블록 하나는 여러 OCR 줄을 합친 것이라 블록 상자 하나로는 마스킹이 안 된다. 블록에 lines: [{text, quad, score}] 를 달고, 블록 글의 몇 번째 글자가 어느 줄인지(글자 오프셋) 함께 준다 — 정규식으로 찾은 위치를 상자로 되돌리기 위해.
단어 상자인식 모델은 줄 단위로 읽는다. 단어·글자 상자는 CTC 출력의 글자 위치로 나눠 근사해야 하므로 정확도를 실측해야 한다(마스킹은 조금 넓게 덮는 쪽이 안전).
글자층 PDFOCR 이 아닌 쪽의 글도 마스킹하려면 글자층 글자 위치를 같은 모양으로 내보낸다(source:"parser" 블록에도 lines).
docx · hwpx 등쪽 배치가 파일에 없어 좌표를 낼 수 없다. 이런 형식의 마스킹은 좌표가 아니라 글자 치환(원본 XML 수정)으로 따로 다룬다 — 범위 밖.
캐시지금 캐시가 줄 상자를 이미 갖고 있으므로 lines 는 다시 OCR 없이 낼 수 있다. 단어 상자를 넣으면 캐시 모양이 바뀌어 엔진 문자열을 올려야 한다(전체 다시 OCR) — 신중히.
실측할 것스캔 문서 결과 JSON 크기 증가(lines · words 각각), 단어 상자 정확도(마스킹 누락률), 회전·기울어진 스캔에서 좌표 오차.
마스킹은 하나라도 빠지면 개인정보가 새는 기능이다. 쓰려면 "찾기(정규식·사람 이름) → 좌표 → 덮기 → 덮은 결과 재OCR 로 남은 글 확인"까지 한 흐름으로 설계하고, 누락률 0 을 목표로 실측해야 한다.

설계와 달라진 점

  • sdp_ocr_image_file → sdp_ocr_file(PDF · 그림 · 그림 폴더, 쪽 고르기). SimpleRAG ocr <파일> 명령이 PDF 도 그려 OCR 하므로 넓혔다.
  • sdp_extract_text 추가 — 업로드 · extract_engine: legacy · extract 명령이 블록 없이 평문을 쓴다.
  • 기능 플래그(builtin-parser)는 두지 않았다. 옛 코드와의 비교는 분리 전 커밋(1bf068a)으로 빌드한 기준 exe 로 대신했고, 아래처럼 결과가 같아 두 벌을 유지할 이유가 없었다. 되돌리려면 그 커밋을 쓴다.
  • 전부 스캔인 PDF + OCR 끔 → 빈 문서가 아니라 SDP_EPARSE(지금 SimpleRAG 와 같은 "텍스트층 없음" 실패). §8 표를 고쳤다.
  • 기본 런타임 · 모델 위치를 DLL 옆 우선으로. 처음엔 exe 옆을 봐서 python.exe 에서 부르면 시스템 폴더의 onnxruntime 1.17 을 집어 OCR 이 실패했다(파이썬 래퍼 시험에서 발견, 오류로 처리되어 죽지는 않음).
  • OCR 상태 전역 표: DLL 바깥으로는 결과 JSON ocr 로만 준다. SimpleRAG 는 그 값을 자기 표(ocr::note)에 남겨 색인 흐름(준비 스레드 → sync_doc)을 그대로 뒀다.
  • 고른 쪽만 읽기(비슷한 문서 찾기): 쪽 수를 sdp_pdf_info 로 먼저 알아 keep 함수를 쪽 번호 목록으로 바꿔 넘긴다.
  • 옵션은 프로세스에 한 벌(핸들 여러 개는 마지막 옵션을 함께 씀).
