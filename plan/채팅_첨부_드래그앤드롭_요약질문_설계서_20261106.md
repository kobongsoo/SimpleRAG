## 1. 지금 구조 (조사 결과)

### 1-1. 업로드 흐름

```
panel.html [+] 클릭
  → send({type:"upload_pick", conv, have})
  → main.rs handle PanelIpc "upload_pick" → App::upload_pick(conv, have)
       1) rfd::FileDialog ... .pick_files()            ← 여러 개 선택 이미 가능
       2) 파일마다 확장자(UPLOAD_EXTS) · 크기(30MB) · 개수(대화당 5개) 검사
       3) 통과한 파일은 워커에 "/upload {conv, path}" 를 차례로 맡김
       4) panel.call("uploadQueued", [{name, ok, why}])  → 칩 표시
  → 워커 stderr "[upload] 임베딩 n/m" → pump_uploads → uploadProgress
  → 결과 → uploadDone → 칩 "n청크"
```

- 관련 코드: `rust/ragsearchbox/src/main.rs:117-121`(한도·확장자), `:1024-1083`(`upload_pick`), `:1381`(IPC 분기),
  `rust/ragsearchbox/ui/panel.html:333-339`(`[+]`), `:550-568`(`uploadQueued/Progress/Done`).
- 패널 WebView 생성: `main.rs:2390` — `WebViewBuilder::...with_html(html).with_ipc_handler(...)` 뿐,
  **끌어 놓기 처리기가 없다.**

### 1-2. 업로드 대화의 질문 흐름

```
App::answer (simplerag/src/app.rs:201)
  corpus = uploads::corpus(conv)           ← 이 대화에 올린 문서만
  retriever.search_with(q, top_k, None, Some(corpus))   (retrieve.rs:263)
     RRF(dense + BM25) 로 pool 개 후보
     리랭커 점수 → 관련도 문턱:
        top < RELEVANCE_MIN(-6)  또는
        (top < RELEVANCE_SOFT(1.0) 이고 keyword_overlap == 0)
        → no_relevant = true, 근거 0건
  근거 0건 + no_relevant → NO_RELEVANT "질문에 대한 내용이 문서에 없습니다. 답변할 수 없습니다."
```

"이문서는 무슨내용인가?" 의 경우:

- `keywords()` 가 뽑는 낱말은 "이문서", "무슨내용" 정도 → 영어 PDF 본문에 하나도 없다 → **겹침 0.0**
- 한국어 질문 ↔ 영어 계약서 청크라 리랭커 최고점도 SOFT(1.0) 를 넘기 어렵다
- 그래서 두 번째 조건에 걸려 근거가 전부 버려진다. 11청크짜리 문서인데도 모델에 아무것도 넘어가지 않는다.

> 확인 단계(구현 0단계): 같은 질문을 다시 던지고 워커 로그의 소요 블록에서 `rerank_top`, `keyword_overlap`,
> `no_relevant` 값을 적어 둔다. 위 추정이 맞는지 숫자로 확정한 뒤 고친다.

또, 요약형 질문은 문턱을 통과하더라도 **검색 자체가 맞지 않는다** — "무슨 내용" 과 가까운 청크가 따로 있는 게 아니라
문서 전체가 답이다. top_k 3개를 아무거나 뽑으면 문서 중간 조각 요약이 된다. 그래서 문턱만 끄는 것으로는 부족하다.

## 2. 개선 1 — 입력창 끌어 놓기 · 여러 파일

### 2-1. 동작 (사용자 관점)

1. 탐색기에서 파일 하나 또는 여러 개를 끌어 MoAI-S 채팅 창 위로 가져오면 입력창 테두리가 강조되고
   "여기에 놓으면 문서를 올립니다" 안내가 뜬다.
2. 놓으면 `[+]` 로 고른 것과 **똑같이** 칩이 생기고 차례로 올라간다(같은 한도·같은 실패 사유).
3. 창 밖으로 다시 끌어내면 강조가 사라진다.
4. 답변 중 · 올리는 중이면 놓아도 올리지 않고 상태줄에 이유를 보인다(`[+]` 와 같은 문구).
5. 폴더를 끌어 놓으면 올리지 않고 "폴더는 올릴 수 없습니다 — 검색 폴더로 추가하세요" 실패 칩.
6. 탐색기 모드(browse.html 이 패널에 떠 있을 때)에서는 아무 것도 하지 않는다(기본 동작만 막는다).

### 2-2. 왜 HTML `drop` 이벤트가 아닌가

WebView2 의 `drop` 이벤트로 받는 `File` 객체에는 **로컬 경로가 없다**. 업로드는 워커가 원본 경로를 읽어
사본을 만드는 구조(`/upload {conv, path}`)라 경로가 꼭 필요하다. 파일 내용을 JS 로 읽어 IPC 로 넘기면
30MB 파일이 base64 로 부풀어 IPC 를 타야 해서 느리고 낭비다. → **wry 의 네이티브 끌어 놓기 처리기**로 경로를 받는다.

### 2-3. Rust 쪽 (`rust/ragsearchbox/src/main.rs`)

```rust
// 패널 WebView 생성부(main.rs:2390 근처)
let p1d = proxy.clone();
let pview = WebViewBuilder::with_web_context(ctx).with_html(html)
    .with_ipc_handler(move |req| post(&p1, UserEvent::PanelIpc(req.into_body())))
    // 끌어 놓기 — 경로를 이벤트 루프로 넘기고, WebView2 기본 동작(파일 열기로 화면 이동)은 막는다
    .with_drag_drop_handler(move |ev| { post(&p1d, UserEvent::PanelDrop(ev)); true })
    .build(&pwin)
```

- `UserEvent::PanelDrop(wry::DragDropEvent)` 를 새로 둔다.
  `Enter{paths, ..}` / `Over{..}` / `Drop{paths, ..}` / `Leave` 네 가지.
- 처리기는 늘 `true` 를 돌려 기본 동작을 막는다 — 막지 않으면 WebView2 가 놓은 파일로 화면을 이동해 채팅 화면이 사라진다.
- `handle()` 에서:
  - 채팅 모드가 아니면(`settings.ui_mode` 가 탐색기) 무시.
  - `Enter` → `panel.call("dropHint", {on:true, n:paths.len()})`
  - `Leave` → `panel.call("dropHint", {on:false})`
  - `Drop` → `panel.call("dropHint", {on:false})` 후 `panel.call("dropFiles", [경로들])`
    — 대화 id 와 이미 올린 개수(`have`)는 **패널 JS 가 알고 있으므로** 패널에서 한 번 되돌려 받는다.

### 2-4. 공통 업로드 함수로 정리

`upload_pick` 을 둘로 나눈다(로직은 그대로, 파일 목록 출처만 다르게):

```
upload_pick(conv, have)              — 대화상자로 고른 뒤 upload_paths 호출
upload_paths(conv, have, paths)      — 지금 upload_pick 의 2)~4) 부분 그대로
                                       + 폴더면 "폴더는 올릴 수 없습니다" 실패
                                       + 같은 경로 중복 제거
```

IPC 분기 추가(`main.rs:1381` 옆):

```
"upload_paths" => self.upload_paths(&conv, have, paths)
```

### 2-5. 패널 JS (`rust/ragsearchbox/ui/panel.html`)

```js
rsb.dropHint = ({on, n}) => { $("box").classList.toggle("dropping", !!on); if (on) setState(`놓으면 문서 ${n}개를 올립니다`); else setState(""); };
rsb.dropFiles = (paths) => {
  if (busy) { setState("답변이 끝난 뒤에 올릴 수 있습니다"); return; }
  if (uploading()) { setState("올리는 중입니다 — 끝난 뒤에 더 올릴 수 있습니다"); return; }
  ensureConv();
  send({ type: "upload_paths", conv: conv.id, have: ups.filter((u) => u.state === "done").length, paths });
};
```

- `[+]` 의 검사 문구를 함수 하나(`canUpload()`)로 묶어 두 곳에서 같이 쓴다.
- CSS: 입력 상자 `.dropping` — 점선 테두리 + 옅은 강조 배경. 다크 모드 변수 그대로 사용.
- 입력창 placeholder 를 "올린 문서에 대해 물어보세요 · 파일을 끌어 놓아도 됩니다" 로(업로드 없을 때 문구에도 반영).

### 2-6. 여러 파일

- 대화상자: 이미 `pick_files()` — 여러 개 선택 가능(제목에도 "여러 개 가능"). **변경 없음**.
- 끌어 놓기: `paths` 전부를 `upload_paths` 로 → 파일마다 칩 · 워커 명령 큐에 차례로.
- 한도는 그대로: 대화당 5개, 파일당 30MB. 넘는 것은 칩에 사유를 보이고 나머지는 올린다(지금 동작과 같음).
- 확인할 점: `uploadDone` 이 이름으로 칩을 찾는다(`panel.html:563`). 같은 이름 파일 두 개를 동시에 놓으면
  첫 칩만 맞춰지므로, 같은 이름은 `upload_paths` 에서 "같은 이름의 문서가 이미 있습니다" 로 막는다
  (워커 사본 이름도 `<순번>_<원래 이름>` 이라 빼기 `[×]` 가 이름 기준이다).

### 2-7. 업로드 한도를 화면에 미리 보이기

지금은 한도를 넘겨야만 실패 칩으로 알 수 있다. 올리기 **전에** 보이게 한다.

> **한도 값(확정 2026-11-06)**: 대화당 **5개** · 파일당 **30MB 이하** — 지금 코드 값 그대로 유지한다
> (`UPLOAD_MAX_FILES = 5` · `UPLOAD_MAX_MB = 30`, `rust/ragsearchbox/src/main.rs:118-119`, 문서 업로드 설계서 §10).
> 아래 화면 글은 상수에서 가져오므로 나중에 값을 바꿔도 화면 문구를 고칠 곳이 없다.

**값을 한 곳에서만 정한다** — 화면 글에 숫자를 직접 쓰지 않는다.

- `panel_html()`(`main.rs:262`)에서 `PANEL_HTML` 치환에 `__UP_MAX_FILES__` · `__UP_MAX_MB__` 를 더한다
  (`__FONT_PX__` 와 같은 방식). 패널 JS 는 `const UP_MAX = __UP_MAX_FILES__, UP_MB = __UP_MAX_MB__;`.

**보이는 곳**

| 위치 | 지금 | 바뀐 뒤 (5개 기준 예) |
|------|------|----------------------|
| `[+]` 말풍선(`panel.html:208` `data-tip`) | 문서 올리기 — 올린 문서에서만 찾아 답합니다 | 문서 올리기 · 끌어 놓기 가능 — **최대 5개 · 파일당 30MB 이하** |
| 업로드 범위 칩(`#chip`, `panel.html:315`) | 📎 업로드 문서 2건에서 찾기 | 📎 업로드 문서 **2/5**건에서 찾기 |
| 첨부 칩 줄 아래 작은 안내(업로드가 1건 이상일 때) | 없음 | 남은 자리 3개 · 파일당 30MB 이하 |
| 끌어 놓기 중 안내(`dropHint`) | — | 놓으면 문서 3개를 올립니다 (남은 자리 3개 · 30MB 이하) |
| 끌어 놓기 개수 초과 | — | 놓으면 문서 4개 중 **3개만** 올립니다 — 최대 5개 (강조색) |
| 파일 대화상자 제목(`main.rs:1041`) | 질문할 문서 고르기 (여러 개 가능) | 질문할 문서 고르기 — 최대 5개 · 파일당 30MB 이하 (남은 자리 3개) |
| 자리가 꽉 찼을 때 `[+]` | 눌러야 실패 칩 | 흐리게 · 말풍선 "대화 하나에 5개까지 올릴 수 있습니다 — 문서를 빼면 다시 올릴 수 있습니다" |
| 업로드 없을 때 입력창 placeholder | 무엇이든 물어보세요 … | 그대로 (한도는 `[+]` 말풍선으로 충분 — 입력창을 길게 만들지 않는다) |

**실패 칩 문구**는 지금 것을 유지한다(이미 한도 숫자가 들어 있음): "30MB 를 넘습니다 — 검색 폴더에 넣어 쓰세요",
"대화 하나에 5개까지 올릴 수 있습니다". 실패 칩에는 파일 크기를 함께 보인다(예: "42.3MB — 30MB 를 넘습니다").

**검사는 그대로 Rust 가 한다** — 화면 안내는 미리 알려 주는 용도이고, 실제로 막는 곳은 `upload_paths` 하나다
(JS 와 Rust 가 따로 판정하면 어긋날 수 있다).

## 3. 개선 2 — "이 문서는 무슨 내용?" 에 답하기

### 3-1. 방향

| 질문 종류 | 예 | 처리 |
|-----------|----|------|
| **개요형** (업로드 대화 한정) | "이 문서는 무슨 내용인가?", "요약해줘", "핵심만 정리", "어떤 문서야", "summary" | 검색하지 않고 **문서 앞부분 청크**로 개요 답 생성 |
| 일반 질문 (업로드 대화) | "갱신 금액은?" | 지금처럼 검색. 단 관련도 문턱을 완화(§3-4) |
| 일반 질문 (폴더 검색) | — | 변경 없음 |

### 3-2. 질문 가르기(라우터) — LLM 을 쓰지 않는다

개요형인지 검색형인지 가르는 일은 일종의 프롬프트 라우터다. 하지만 **LLM 라우터는 쓰지 않는다.**

| 방식 | 추가 시간 | 정확도 | 판단 |
|------|-----------|--------|------|
| 규칙(낱말 패턴) | 1ms 미만 | 정해진 표현은 정확, 바꿔 말한 표현은 놓침 | **1단계로 채택** |
| 임베딩 유사도 | 사실상 0 (검색용 질문 임베딩을 어차피 만든다) | 바꿔 말한 표현도 어느 정도 잡음 · 기준값 조정 필요 | 실측으로 필요할 때만 2단계 |
| 작은 분류 모델 | 수 ms | 학습 데이터 필요 | 과함 |
| LLM 라우터 | 모델 호출 한 번 더 | 큰 모델은 좋고 1~4B 는 들쭉날쭉 | **쓰지 않음** |

LLM 라우터를 쓰지 않는 이유:

- **TTFT** — 판단용 프롬프트를 모델에 한 번 더 읽혀야 한다. 온디바이스 CPU · iGPU 에서는 질문마다
  수백 ms~1초 이상 첫 글자가 늦어질 수 있다(이 값은 아직 실측하지 않음).
- **정확도** — 작은 모델은 두 가지 중 하나만 골라도 형식을 어기거나 같은 질문에 다른 답을 낸다
  (탐색기 AI 정리 실측 2026-11-03 에서도 작은 모델은 형식이 쉽게 무너졌다).
- **범위가 좁다** — 올린 문서가 있는 대화에서만, 개요 / 검색 두 가지를 가르면 된다.

잘못 갈랐을 때 손해가 양쪽이 다르다:

- 개요 질문 → 검색: 지금 동작과 같고, §3-4 의 "검색 실패 → 개요로 넘기기"가 받아 준다.
- 본문 질문 → 개요: "갱신 금액은?" 에 문서 요약이 나온다. **이쪽이 더 나쁘다.**
  → 개요로 보내는 규칙은 **보수적으로** 잡는다(남는 본문 낱말이 없을 때만).

전체 흐름(LLM 호출 0회):

```
업로드 대화의 질문
 ├─ 규칙상 확실한 개요형 → 개요 답(§3-3)
 └─ 그 밖 → 지금처럼 검색(문턱은 §3-4 처럼 완화)
       └─ 문턱에 걸려 근거 0건 → "답변할 수 없습니다" 대신 개요 답
             + "질문과 딱 맞는 부분은 찾지 못해 문서 개요를 보여 드립니다" 한 줄
```

규칙이 놓친 개요 질문(예: "이거 뭐에 관한 계약이야?")도 검색 실패 → 개요로 넘기기가 받아 주므로
라우터가 완벽하지 않아도 된다.

#### 개요형 규칙 (`simplerag/src/overview.rs`)

규칙(정규식) — 모델 호출 없이:

- `(이|그|첨부|올린|업로드)\s*(문서|파일|자료)` + `(무슨|어떤|뭐|무엇)` 조합
- `요약|정리해|개요|핵심만|한눈에|간추려|summar(y|ize)|overview`
- 질문에서 위 낱말·조사·문서 지칭어를 뺐을 때 **남는 본문 낱말이 없을 때만** 개요형으로 본다
  ("이 문서에서 갱신 금액 요약해줘" 는 "갱신 금액" 이 남으므로 일반 질문 → 검색).
- 업로드 대화(`corpus.is_some()`)에서만 켠다. 폴더 검색에는 쓰지 않는다(문서가 정해지지 않았으므로).

#### 2단계(조건부) — 임베딩 유사도

시험 세트(§5-3)에서 규칙 + 넘기기로도 개요 질문을 놓치는 일이 많을 때만 붙인다.
개요형 질문 예시 약 20개의 평균 벡터를 미리 만들어 두고, 검색용 질문 벡터와 코사인 유사도가 기준값을 넘으면 개요형으로 본다.
기준값은 본문 질문이 개요로 잘못 가는 일이 0건이 되도록 잡는다.

### 3-3. 개요 답 만들기

`n_ctx 2048` 한계(config.yaml 119줄 주석) 때문에 문서 전체를 넣을 수 없다. 탐색기 AI 정리(`brief.rs`)에서
실측으로 정한 방식을 따른다:

1. 올린 문서마다 `chunk_idx` 순으로 앞 청크를 모아 글자 상한(`OVERVIEW_CAP_CHARS`, 문서 1건이면 ~1200자,
   여러 건이면 문서당 ~450자 — brief.rs `CAP_CHARS` 와 같은 값에서 시작)까지 자른다.
   - 앞부분이 표지·목차뿐일 수 있으니, 앞 2청크 + 문서 가운데·끝에서 1청크씩(최대 4청크)을 고른다.
2. 근거 이벤트(`Event::Evidence`)는 이 청크들로 보낸다 → 화면 출처 카드가 그대로 동작.
3. 생성 프롬프트는 새 시스템 프롬프트 `OVERVIEW_SYSTEM`(prompts.rs):
   "아래 [근거] 는 사용자가 올린 문서의 일부입니다. 이 문서가 어떤 문서인지(종류·당사자·목적)와 핵심 내용을
   한국어 3~5문장으로 설명하세요. 근거에 없는 내용은 쓰지 마세요. 근거가 영어여도 한국어로 답하세요. 끝에 [1] 형식 근거 번호."
4. 문서가 여러 건이면 brief.rs 처럼 **문서마다 한 번씩** 생성해 "▸ 문서이름 — 요약" 줄로 잇는다
   (작은 모델은 한 번에 묶으면 형식이 무너진다 — 2026-11-03 실측). 상한 5건(업로드 한도와 같다).
5. 되뱉기·근거 없는 숫자 거르기는 brief.rs 의 `line_ok` 를 재사용.
6. 소요 블록에 `overview: true` 를 넣어 화면·로그에서 구분.

### 3-4. 업로드 대화의 관련도 문턱 완화

업로드 대화는 사용자가 **이 문서에 대해 묻겠다**고 이미 정한 상황이라, "문서에 없는 질문을 막는" 문턱의 이득이 작고
교차 언어(한국어 질문 · 영어 문서)에서 잘못 막는 손해가 크다.

- `keyword_overlap == 0` 조건(SOFT 문턱)은 업로드 대화에서 **끈다** — 교차 언어면 늘 0 이다.
- ~~하드 문턱을 업로드 전용 값(-9)으로 낮춘다~~ → **낮추지 않는다**(2026-11-06 실측). 대신 질문 낱말이 근거에 있으면 하드 문턱에 걸려도 통과시킨다.

  0단계 실측(설치본 워커, 영어 견적서 PDF 11청크 · 한국어 지침 docx):

  | 질문 | 막힌 조건 | 결과 |
  |------|-----------|------|
  | "이문서는 무슨내용인가?" (영어 PDF) | 하드 문턱(top < -6) | SOFT 만 끄면 여전히 막힘 → 개요 경로 필요 |
  | "갱신 금액은 얼마인가?" (영어 PDF) | SOFT(겹침 0) | SOFT 를 끄면 정답 |
  | "리프레시 휴가는 며칠인가?" (한국어) | 하드 문턱 | -8 · -10 에서도 막힘, 문턱을 끄면 답함 |
  | "연차 이월 기준은?" (영어 PDF, 문서에 없음) | — | **-8 로 낮추면 지어서 답함** → 하드 문턱을 낮추면 안 됨 |

  그래서 업로드 대화 규칙: `막음 = top < -6 && 낱말 겹침 == 0` (겹침이 없거나 질문 낱말이 없으면 막음).
  폴더 검색 규칙은 그대로(`top < -6 || (top < 1.0 && 겹침 == 0)`).
- 그래도 막히면(근거 0건) "답변할 수 없습니다" 대신 **개요 답(§3-3)으로 넘긴다**. 답 앞에 한 줄을 붙인다:
  "질문과 딱 맞는 부분은 찾지 못해 문서 개요를 보여 드립니다."
  소요 블록에는 `overview: "fallback"` 으로 남겨 규칙으로 간 개요(`overview: "rule"`)와 구분한다.

### 3-5. 출처 줄 쉼표 (panel.html `finish`)

```js
const ml = metaLine(info, !!t.answer);
const meta = hasUploads() ? (ml ? ml + " · 업로드 문서" : "업로드 문서") : ml;
```

## 5. 검증

1. **끌어 놓기**: 1개 / 3개 / 6개(한도 초과 1개 실패 칩) / 지원 안 하는 확장자 / 30MB 초과 / 폴더 / 같은 이름 2개 /
   답변 중에 놓기 / 탐색기 모드에서 놓기(아무 일 없고 화면 이동도 없음).
2. **대화상자 여러 개 선택**: 기존 동작 회귀 없음.
2-1. **한도 표시**: 0건 · 3건 · 꽉 참에서 칩(n/최대) · 남은 자리 안내 · `[+]` 말풍선 · 대화상자 제목이 맞는지.
   상수를 바꿔 빌드했을 때 화면 숫자가 모두 따라 바뀌는지.
3. **개요형 질문**: 스크린샷의 영어 PDF(Innotena Renewal, 11청크)로 "이문서는 무슨내용인가?" · "요약해줘" ·
   "핵심만" → 한국어 개요, 출처 카드 표시, `overview: true`.
   한국어 문서 1건 · 문서 3건(문서별 줄)도 확인.
4. **일반 질문 회귀**: 업로드 대화에서 "갱신 금액은?" 같은 본문 질문은 여전히 검색 경로. 폴더 검색 골든셋(골든 100)은
   문턱 변경이 업로드 대화에만 걸리므로 점수 변화 없어야 한다.
5. 단위 테스트: 개요형 판별 규칙(맞는 예 10 · 아닌 예 10), `upload_paths` 검사(폴더·중복·한도).
6. **라우팅 시험 세트** — 질문 40개(개요형 20 · 본문 질문 20, 한국어 문서와 영어 문서 섞음):
   - 셀 것: 규칙 오분류 수, 넘기기 뒤 최종으로 답을 못 한 수, 개요로 넘어간 질문의 TTFT
   - **합격 기준: 본문 질문이 개요로 잘못 가는 일 0건**
   - 개요 질문을 놓친 것이 많으면 §3-2 의 2단계(임베딩 유사도)를 붙이고 다시 잰다

   **결과(2026-11-06, Qwen3-1.7B · iGPU, 한국어 지침 docx 1건 · 영어 견적서 PDF 1건)**

   | 묶음 | 규칙 개요 | 검색 | 검색 실패 → 개요 |
   |------|-----------|------|------------------|
   | 개요 질문 · 한국어 문서 10 | 8 | 1 | 1 |
   | 개요 질문 · 영어 문서 10 | 10 | 0 | 0 |
   | 본문 질문 · 한국어 문서 10 | **0** | 10 | 0 |
   | 본문 질문 · 영어 문서 10 | **0** | 5 | 5 |

   - 합격 기준(본문 질문이 개요로 잘못 감 0건) 통과. 놓친 개요 2건("이거 뭐에 관한 문서야?", "간단히 설명해줘")은 규칙에 더해 단위 테스트로 고정.
   - 영어 문서 본문 질문 5건은 한국어 질문 ↔ 영어 근거라 리랭커 점수가 낮아 개요로 넘어갔다. 그중 3건(만료일 · 견적 번호 등)은 개요 조각에 답이 있어 답이 나왔다. 교차 언어 검색은 남은 과제.
   - 첫 글자: 규칙 개요 약 0.3초(검색 없음), 검색 2~3초, 검색 실패 → 개요 3~4초.
   - 임베딩 유사도(2단계)는 붙이지 않는다 — 규칙 + 넘기기로 충분했다.
   - 모델 품질 한계: 1.7B 모델이 파일 이름의 날짜를 작성일로 쓰거나("2026년 11월 11일 작성"), 지침의 "5일"을 "7일"로 답한 일이 있었다(검색 경로는 맞음).
