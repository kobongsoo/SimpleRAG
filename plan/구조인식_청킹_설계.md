# 구조 인식 청킹 설계서

> 대상: `src/simplerag/chunk.py` (고정 크기 128토큰 → 구조 인식 패킹)
> 근거 측정: 2026-08-21, 코퍼스 `D:\분류함` 367건 / 회사규정 18건 / 평가 45문항
> 관련: [설계서.md](설계서.md) 결정3, [REPORT.md](../results/REPORT.md) §17

---

## 1. 문제 — 무엇이 실제로 깨져 있는가

현재 청킹은 **문서 구조를 전혀 보지 않는다.** 토큰 128개를 세어 자르고 16개를
겹친다. 그 결과를 실측했다.

| 측정 | 값 |
|---|---:|
| 회사규정 조문 총수 | 123개 |
| **청크 경계에 걸려 쪼개진 조문** | **89개 (72%)** |
| 표 행 40개가 흩어진 청크 수 | 15개 |

조문의 72%가 두 청크에 나뉘어 들어간다. 검색이 그중 한쪽만 가져오면 모델은
**조문의 절반만 보고 답한다.**

### 이것이 실패로 이어진 증거

45문항 중 "검색은 성공했는데 답이 틀린" 9건은 **전부 인접한 다른 값을 집어온
형태**다.

| 질문 | 정답 | 모델 답 |
|---|---|---|
| 주택자금 대출 한도 | 3천만원 | 8억 원 |
| 상환 기간 | 5년 | 3년 |
| 원격지 지원 한도 | 10만원 | 25만원 |
| 본인 결혼 휴가 | 5일 | 1개월 |

§17의 청크 256 실험에서 **이 중 6건이 정답으로 바뀌었다.** 조문·표가 잘리지
않고 통째로 들어가면 해결되는 종류임을 보여준다. 다만 256은 무관한 내용까지
끌어들여 다른 문항 5건을 깨뜨렸고 TTFT가 2.1배가 됐다.

> **고정 크기를 키우는 것은 답이 아니다. 필요한 것은 "경계를 지키는 것"이지
> "크게 자르는 것"이 아니다.**

## 2. 제약 — 조문 구조는 코퍼스의 6%뿐이다

"조문 단위로 자르자"는 발상은 매력적이지만, 코퍼스 표본 77건을 조사한 결과
그대로는 성립하지 않는다.

| 구조 표지 | 보유 문서 |
|---|---:|
| 번호절 (`1.` `1.2`) | 38% |
| 표 행 (`\| … \|`) | 25% |
| 마크다운 제목 (`#`) | 19% |
| **조문 (`제N조`)** | **6%** |
| 장 (`제N장`) | 0% |

회사규정 18건으로 좁혀도 조문 보유는 **6건(33%)** 뿐이다. 경조사지원규정과
출장여비규정은 `제N조`가 하나도 없고 `1. 적용대상` 형태를 쓴다.

```
경조사 지원 규정
1. 적용대상
2. 경조사 지원기준
| 내역 | 휴가(일) | 금액(원) | 기타 |
| 본인 결혼 | 5 | 500,000 |
```

⚠️ **따라서 조문 전용 설계는 실패한다.** 여러 제목 문법을 함께 다루고, 어느
것도 없을 때의 폴백을 갖추는 것이 설계의 본체다.

## 3. 절 길이 분포가 크기 설계를 결정한다

회사규정 14건에서 절 413개의 토큰 길이를 쟀다.

| 통계 | 값 |
|---|---:|
| 중앙값 | **36토큰** |
| p75 | 81토큰 |
| p90 | 174토큰 |
| 최대 | 6,519토큰 |

| 상한 | 이하 비율 |
|---|---:|
| 128토큰 | **85%** |
| 192토큰 | 91% |
| 256토큰 | 95% |

두 가지가 따라 나온다.

1. **"절 = 청크"는 성립하지 않는다.** 중앙값 36토큰짜리 청크를 4만 개 만들면
   검색 변별력이 떨어지고 청크 수가 폭증한다.
2. **절의 85%가 128토큰 안에 들어간다.** 즉 크기를 키우지 않고도 대부분의
   절을 온전히 담을 수 있다.

> **핵심 설계 판단: 크기를 키우는 대신 "자르는 위치"만 바꾼다.**
> 목표 크기는 현행 128을 유지한다. §17이 보여줬듯 크기를 키우면 TTFT만 잃는다.

## 4. 설계

### 4.1 3단 파이프라인

```
텍스트 ──▶ ① 제목 문법 감지 ──▶ ② 절 분할 ──▶ ③ 예산 패킹 ──▶ 청크
            (문서마다 1개)        (경계만 결정)     (제목 접두 포함)
```

### 4.2 ① 제목 문법 감지 — 문서마다 하나만 고른다

문서 전체를 훑어 아래 순서로 **가장 먼저 3개 이상 발견되는 문법 하나만** 채택한다.

| 우선 | 문법 | 예 |
|:--:|---|---|
| L1 | 조문 | `제5조(지급 금액)` |
| L2 | 마크다운 제목 | `## 설치 방법` |
| L3 | 번호절 | `1. 적용대상`, `1.2 정의` |
| L4 | (없음) | → **현행 고정 크기로 폴백** |

🔴 **하나만 고르는 것이 핵심이다.** 조문 문서 안의 `1.` `2.` 는 조문의 **하위
항목**이지 절이 아니다. 둘을 함께 경계로 쓰면 조문이 오히려 더 잘게 부서진다.
실제로 두 문법을 동시에 적용해 세어 보니 취업규칙이 조문 77개 대신 절 119개로
쪼개졌다.

### 4.3 ② 절 분할 — 경계만 정하고 자르지 않는다

절 시작 위치 목록만 만든다. 이 단계에서는 길이를 보지 않는다.

### 4.4 ③ 예산 패킹 — 설계의 심장

```
budget = CHUNK_TOKENS (128)

작은 절들은 예산이 허락하는 만큼 묶는다.
절 하나가 예산을 넘으면 그 절만 따로, 내부에서 다시 쪼갠다.
절 경계를 가로질러 자르는 일은 없다.
```

| 상황 | 처리 |
|---|---|
| 절 ≤ 남은 예산 | 현재 청크에 이어 붙인다 |
| 절 > 남은 예산, 절 ≤ 예산 | 청크를 끊고 새 청크에서 시작 |
| 절 > 예산 (15%) | 그 절만 단독 처리 — 문단 → 문장 → 토큰 순으로 물러서며 분할, 이때만 겹침 적용 |

**겹침 정책이 바뀐다.** 절 경계에서 끊을 때는 겹침이 필요 없다(의미가 끊기지
않는 지점이므로). 큰 절을 내부 분할할 때만 겹침을 준다. 현행은 모든 경계에
16토큰을 겹쳐 그만큼 낭비하고 있다.

### 4.5 제목 접두 — 청크가 자기 위치를 알게 한다

각 청크 앞에 출처 경로를 붙인다.

```
[리프레시 휴가 지원 지침 > 제5조(지급 금액)]
리프레시 휴가비는 100만원으로 한다. 해당 금액은 상여처리한다.
```

약 10~15토큰을 쓰지만 세 가지를 동시에 얻는다.

- **BM25**: 제목의 단어가 색인에 들어가 `"휴가비"` 같은 짧은 질의가 걸린다
  (§15.5의 "며칠" 류 검색 실패에 직접 대응)
- **dense**: 임베딩에 문맥이 실린다
- **생성**: 모델이 "지금 보는 것이 제5조(지급 금액)"임을 안다 — 인접한 다른
  조문의 숫자를 집는 오류에 직접 대응

### 4.6 표 헤더 반복

표 행을 담은 청크에는 **헤더 행을 항상 함께 넣는다.**

```
| 내역 | 휴가(일) | 금액(원) | 기타 |     ← 반복 삽입
| 본인 결혼 | 5 | 500,000 |
```

헤더가 다른 청크에 있으면 `| 본인 결혼 | 5 | 500,000 |` 만 보고는 5가 일수인지
금액인지 알 수 없다. 경조사 카테고리(현재 50%)가 정확히 이 실패를 겪고 있다.

## 5. 구현 범위

| 파일 | 변경 |
|---|---|
| `src/simplerag/structure.py` | **신규** — 문법 감지, 절 분할, 표 헤더 탐지 |
| `src/simplerag/chunk.py` | `split_structured()` 추가. 기존 `split_text()` 는 폴백으로 유지 |
| `src/simplerag/index/indexer.py` | payload 에 `section` 추가 |
| `src/simplerag/index/bm25.py` | `CACHE_VERSION` 2 → 3 |
| `src/simplerag/config.py` | `CHUNK_MODE = "structured" \| "fixed"` |

### 되돌릴 수 있게 만든다

```
SIMPLERAG_CHUNK_MODE=fixed      # 현행 동작으로 즉시 복귀
```

§17에서 겪었듯 청킹 변경은 **전체 재인덱싱(약 20분)** 을 요구한다. 스위치를
남겨 두면 비교와 롤백이 재인덱싱 한 번으로 끝난다.

### 단계

| 단계 | 내용 | 검증 |
|:--:|---|---|
| M1 | 문법 감지 + 절 분할 + 패킹 | 45문항 측정 |
| M2 | 제목 접두 + `section` 메타 | 45문항 측정 |
| M3 | 표 헤더 반복 | 45문항 측정, **경조사 집중** |

⚠️ **단계마다 측정한다.** 한꺼번에 넣고 결과가 나빠지면 어느 것이 원인인지
알 수 없다. §16에서 같은 실수를 피해 이득을 봤다.

## 6. 위험과 완화

| 위험 | 근거 | 완화 |
|---|---|---|
| 🔴 **제목 오탐** | 본문의 `1.` 을 절로 오인 | 문법 하나만 채택(4.2). 절 최소 길이 하한 |
| 🔴 **추출이 개행을 잃은 문서** | 일부 PDF·PPT | 문법 미검출 → L4 폴백 |
| 🟡 청크 수 증가 | 절 경계로 끊으면 평균 충전율이 낮아짐 | 실측 후 판단. 겹침을 없애는 이득이 상쇄 |
| 🟡 제목 접두의 토큰 비용 | 청크당 10~15토큰 | TTFT 실측으로 확인 |
| 🔴 **개선이 없을 수 있음** | §17에서 256은 6건 고치고 5건 깨뜨렸다 | 스위치로 롤백 |

### 기대 이득의 상한을 정직하게 적어 둔다

§17에서 청크 256이 고친 6문항이 **현실적 상한**이다. 6/45 = 13%p.
그러나 256은 동시에 5문항을 깨뜨렸다. 구조 인식이 "무관한 내용을 끌어들이지
않으면서" 경계만 고치는 것이 목표이므로 파괴는 적어야 하지만, **보장할 수
없다.** 측정으로만 판단한다.

## 7. 검증 계획

| 항목 | 방법 |
|---|---|
| 비교 | 같은 45문항, 같은 모델(0.6B), `CHUNK_MODE` 만 교체 |
| 1차 지표 | 최종 정답률, **경조사·복리후생** 카테고리 |
| 2차 지표 | Recall@1/@3, 청크 수, TTFT |
| 유의성 | McNemar 대응표본 (n=45에서 1문항 = 2.2%p) |
| 기준선 | `results/baseline128/` (§17.8에서 확보) |

**채택 기준**: 정답률이 오르고 TTFT 상승이 0.3초 이내일 것. 정답률이 같으면
채택하지 않는다 — 복잡도만 늘어난다.

## 8. 이 설계가 기대는 사실 (전부 실측)

- 조문 123개 중 72%가 청크 경계에 걸림
- 절 길이 중앙값 36토큰, 85%가 128토큰 이하
- 조문 문법 보유 문서는 코퍼스의 6%, 회사규정으로 좁혀도 33%
- 청크 256에서 9건 중 6건이 정답 전환, 동시에 5건 파괴 (§17)
- 생성 실패 9건 전부 "인접한 값 오독" 형태
