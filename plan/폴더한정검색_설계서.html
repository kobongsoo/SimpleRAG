폴더 한정 검색 설계서

폴더 패널에서 질문하면 패널이 보고 있는 폴더(하위 포함)의 문서만 근거로 쓴다. 지금은 어느 폴더에서 묻든 인덱스 전체에서 찾기 때문에, 인덱스에 여러 폴더가 섞이면 다른 폴더 문서가 근거로 나온다. 사전 측정에서 Qdrant 의 필터가 5만 청크 규모에서 검색을 8배 느리게 만든다는 것을 확인해, 필터 대신 벡터 행렬 한 벌을 메모리에 두고, 폴더는 "이 청크를 쓸지" 표시(마스크)만 바꾸는 방식으로 설계했다. 폴더를 몇 개 오가도 메모리는 늘지 않는다(§5 — 처음 안인 "폴더마다 묶음" 을 메모리 걱정으로 바꿨다).

0인덱싱 폴더 = 패널 폴더 결정 2026-09-18

설계 뒤 사용자 결정: 하위 폴더 단위로 좁혀 찾는다, 그리고 인덱싱 폴더와 패널이 뜨는 폴더는 무조건 같다 — 설정도 하나로.

  • INI 는 [Scope] Folders 하나. 자동 인덱싱의 [AutoIndex] Folders 는 없앴다(남아 있으면 쓰지 않고 트레이로 알린다)
  • 지정 폴더 밖 문서는 인덱스에서 뺀다 — 누가 다른 폴더를 직접 인덱싱했거나 지정 폴더에서 하나를 뺐을 때. 워커가 뜰 때마다 /index-outside 로 찾고 /remove-doc {"outside_of": …} 로 뺀다(파일이 있어도). 한꺼번에 많으면(30%·50건) 트레이로 묻는다. 폴더 목록이 비면 아무것도 빼지 않는다
  • 그래서 범위 선택은 이 폴더 / 지정 폴더 전체 둘뿐이다 — "인덱스 전체" 는 "모든 지정 폴더" 와 같아 뺐다

1목표와 범위

한다

  • 패널에서 한 질문은 그 폴더와 하위 폴더 문서에서만 근거를 찾는다
  • 범위를 패널에서 바꿀 수 있다 — 이 폴더 / 지정 폴더 전체 / 인덱스 전체
  • 답마다 어느 범위에서 찾았는지 보여 준다
  • 그 폴더에 인덱싱된 문서가 없으면 모델을 부르지 않고 곧바로 알린다
  • CLI 에서도 쓸 수 있다(ask --folder, chat /folder)

하지 않는다

  • 폴더마다 인덱스를 따로 만들기 — 인덱스는 지금처럼 하나다(자동 인덱싱과 잠금 설계가 그대로 유지된다)
  • 재인덱싱 — 청크에 이미 doc_path 가 있어 그것으로 가른다. 새 필드를 넣지 않는다
  • 파일 형식·날짜 같은 다른 조건으로 거르기
핵심 1 — Qdrant 필터를 쓰지 않는다local 모드의 필터는 점마다 파이썬으로 검사해 6만 청크에서 114ms → 730~920ms 가 됐다(§4). 대신 벡터 행렬 한 벌을 두고 numpy 로 직접 찾는다 — 6만 청크 전체 내적이 2.7ms, 폴더 마스크를 씌워도 2.9ms.
핵심 2 — 질문 한 줄에 폴더를 싣는다/ask {"q": …, "folder": …}. 폴더를 따로 먼저 보내면 "질문이 먼저" 규칙과 부딪치고 출력 해석이 어긋난다(§6). 한 줄이면 출력 모양이 그대로라 해석기를 안 고친다.
핵심 3 — 기본은 "지금 보고 있는 폴더 + 하위"패널 머리에 보이는 폴더가 곧 범위다. 넓히고 싶으면 머리의 선택으로 바꾼다(결정 B1).
핵심 4 — 없으면 없다고 말한다범위 안에 문서가 없는데 인덱스 전체로 슬쩍 넓히면 사용자가 속는다. 넓히지 않고 알린다.

2지금 흐름 — 폴더 정보가 어디에도 없다

패널RAGSearchBox
입력 칸의 글→app._on_panel_ask(text)→worker.ask(question) — 질문만
워커simplerag chat
stdin 한 줄→render_answer→pipeline.answer(query)
검색hybrid.py
dense — Qdrant 전체+BM25 전체→RRF→리랭커→근거 3건

패널은 지금 보고 있는 폴더(panel.folder)를 알고 있지만 워커에 넘기지 않는다. 옛 검색창 방식(_on_query)도 폴더를 로그에만 쓴다. 청크의 payload 에는 doc_path(절대 경로)가 이미 있으므로, 폴더로 가르는 데 필요한 정보는 인덱스에 다 있다.

3범위를 무엇으로 볼까

범위예 — D:\분류함\규정\인사 를 보는 중좋은 점아쉬운 점
이 폴더(하위 포함) 기본…\규정\인사 와 그 아래눈앞의 폴더와 근거가 일치한다. 가장 좁고 정확하다하위 폴더로 한 단계 들어가면 범위가 좁아진다 — 그 사실을 화면에 보여 줘야 한다
지정 폴더 전체이 폴더가 속한 [Scope] Folders 항목 — D:\분류함 전체하위 폴더를 오가도 범위가 그대로다지정 폴더가 하나뿐이면 "인덱스 전체" 와 거의 같다
인덱스 전체§0 결정으로 뺐다 — 인덱스 = 지정 폴더들이므로

패널 머리의 폴더 이름 옆에 범위를 고르는 칸을 둔다. 고른 값은 패널을 닫았다 열어도 유지하고 INI 에 적는다([Panel] SearchScope).

결론: local 모드는 필터를 걸면 점마다 조건을 파이썬으로 검사해 8배 느려진다(서버 모드라면 payload 색인을 쓸 수 있지만 SimpleRAG 는 local 모드다 — 설계서 결정5). 그래서 매 질문마다 필터를 거는 대신, 전체 벡터 행렬 한 벌을 두고 폴더 마스크를 씌워 직접 찾는다. 6만 청크에서 2.9ms — 필터 없는 지금(114ms)보다도 빠르다.

지금 운영 인덱스(sample 20문서 · 498청크)에서는 어느 방식이든 수 ms 다. 위 수치는 인덱스가 커졌을 때를 위한 것이다.

5검색 구현 — 벡터 한 벌 + 폴더 마스크

처음 안을 바꾼 이유

처음에는 폴더마다 {벡터, 본문} 묶음을 만들어 최근 4개까지 두려 했다. 그러면 (1) 폴더를 오갈 때마다 묶음이 쌓이고(큰 폴더 넷이면 같은 청크가 여러 벌), (2) 본문까지 들고 있어 청크가 많을수록 커지고, (3) 폴더를 떠나도 곧바로 풀리지 않는다. 측정해 보니 6만 청크 전체를 내적해도 2.7ms 라 폴더마다 따로 모을 까닭이 없었다.

바꾼 안

한 벌만 — 벡터 행렬

  • 인덱스의 모든 청크 벡터를 float32 행렬 하나로 둔다(+ 행 → 점 id 표)
  • 본문은 들고 있지 않는다 — 마지막 후보 20개쯤만 id 로 Qdrant 에서 가져온다(지금도 BM25 후보를 이렇게 가져온다)
  • 크기는 청크 수 × 1.5KB로 정해져 있다 — 폴더를 몇 번 오가든 늘지 않는다

폴더마다 — 표시(마스크)만

  • "이 청크가 그 폴더 것인가" 참/거짓 배열 — 청크 하나에 1바이트(6만 청크 = 58KB)
  • dense 와 BM25 가 같은 마스크를 쓴다(BM25 는 이미 행 → 점 id 표가 있다)
  • 최근 폴더 8개 마스크만 두고 나머지는 버린다 — 다 합쳐도 0.5MB 안팎

얼마나 드나

인덱스 크기벡터 행렬폴더 마스크(개당)
지금 sample — 498청크0.7 MB0.5 KB
6만 청크(예전 368문서, 실측)92 MB58 KB
15만 청크(local 모드 전환 기준 — 설계서 결정5)약 230 MB146 KB

워커는 이미 생성 모델 등으로 약 2.5GB 를 쓴다. 15만 청크를 넘으면 SimpleRAG 자체가 Qdrant 서버 모드로 옮기기로 한 규모이고, 서버 모드는 payload 색인으로 필터가 빠르므로 그때는 행렬을 두지 않고 Qdrant 필터를 쓴다. 안전장치: 행렬이 [retrieval] folder_matrix_max_mb(기본 300MB)를 넘으면 만들지 않고 Qdrant 필터로 찾는다(느리지만 메모리는 안 쓴다) — 로그로 알린다.

언제 만들고 언제 풀리나

때처리
워커가 준비된 뒤뒤에서 행렬을 만든다(6만 청크 3.2초). 다 되기 전에 폴더 질문이 오면 Qdrant 필터로 찾는다(그 한 번만 느리다)
폴더를 처음 볼 때마스크만 만든다 — 상태 파일에서 그 폴더 문서의 id 범위를 모아 표시(수 ms). id 범위가 없는 옛 문서만 doc_path 로 찾아 표시
인덱스가 바뀌었을 때(자동 인덱싱)바뀐 문서의 행만 고친다 — 지운 청크의 행은 "없음" 표시, 새 청크는 행을 덧붙인다. 행이 20% 넘게 "없음" 이 되면 뒤에서 새로 만든다. 마스크는 버리고 다음 질문 때 다시 만든다
다른 폴더로 갈 때풀 것이 없다 — 행렬은 공용이고, 마스크는 수십 KB 라 최근 8개만 남기고 버린다
모델을 내릴 때(쉬어서·트레이)워커 프로세스가 끝나므로 행렬까지 전부 풀린다

질문할 때

  • dense: 행렬 · 질의벡터 → 마스크 밖은 뺌 → 상위 dense_top_k(6만 청크 2.9ms)
  • BM25: 지금처럼 점수 → 마스크 밖 0 → 상위 bm25_top_k
  • 후보의 본문만 id 로 가져온 뒤 RRF · 중복 제거 · 리랭커 · 근거 3건은 그대로
  • 범위가 "인덱스 전체" 면 마스크 없이 같은 행렬을 쓴다

덤: 이 행렬은 폴더가 없는 보통 질문에서도 Qdrant 검색(114ms)보다 빠르다(2.7ms). 다만 이번 설계의 범위는 폴더 한정이므로, 보통 질문을 바꿀지는 따로 정한다(결정 B5).

6폴더를 워커에 전달하기

질문 한 줄에 폴더를 함께 싣는다.

# 지금
연차 이월 기준은?
# 바뀜 — ASCII JSON 한 줄
/ask {"q": "연차 이월 기준은?", "folder": "D:\\분류함\\규정\\인사", "scope": "folder"}
  • 출력 모양은 지금과 똑같다(근거 → 답변 → 소요 → 프롬프트). 그래서 RAGSearchBox 의 출력 해석기(chat_parser)를 고치지 않는다. 근거 머리에만 범위를 덧붙인다: ── 근거 3건 (12ms) · 범위 인사(문서 7건)
  • 덤: 질문도 ASCII JSON 이 되어 cp949 로 못 쓰는 글자(이모지 등)가 든 질문도 깨지지 않는다
  • 왜 폴더를 따로 먼저 보내지 않나(/scope 폴더 다음 질문): 워커는 명령마다 프롬프트를 내므로 질문의 출력과 섞이고, RAGSearchBox 는 "질문이 먼저" 라 폴더 명령이 질문 뒤로 밀릴 수 있다. 한 줄이면 둘 다 없다
  • 옛 워커(/ask 를 모름): 워커가 시작할 때 내는 줄에 기능: ask-folder 를 더하고, RAGSearchBox 는 그 줄이 있을 때만 /ask 를 쓴다. 없으면 지금처럼 질문만 보내고 패널에 "이 SimpleRAG 는 폴더 한정을 모릅니다 — 전체에서 찾았습니다" 를 한 번 보인다
  • 옛 검색창 방식([Trigger] SearchBox=1)도 같은 길을 쓴다 — 감시가 이미 폴더를 알고 있다

7범위 안에 문서가 없을 때

상황처리
그 폴더(하위 포함)에 인덱싱된 문서가 0건모델을 부르지 않고 "이 폴더에는 인덱싱된 문서가 없습니다" + 범위를 넓히는 방법. 몰래 전체로 넓히지 않는다
자동 인덱싱이 허락을 기다리는 중(새 문서가 많음)위 문구에 "새 문서 N건이 인덱싱을 기다립니다 — 트레이 '지금 인덱싱'" 을 덧붙인다(RAGSearchBox 가 안다)
문서는 있는데 관련 내용이 없음지금과 같다 — dense 는 늘 가장 가까운 것을 돌려주므로 근거는 나오고, 모델이 "근거에 없다" 고 답한다
폴더 청크가 근거 개수(3)보다 적음있는 만큼만 쓴다

  • 머리: 폴더 옆에 범위 선택과 그 범위의 문서 수. 하위 폴더로 들어가 범위가 좁아지면 문서 수가 바로 줄어 보인다
  • 답마다 근거 머리에 범위를 적는다 — 나중에 스크롤해 보아도 어느 범위의 답이었는지 안다
  • 범위를 바꾸면 다음 질문부터 적용한다(이미 한 답은 그대로)

9CLI 에서

simplerag ask --folder "D:\분류함\규정" "연차 이월 기준은?"
simplerag search --folder "D:\분류함\규정" "연차"
simplerag chat
질문> /folder D:\분류함\규정      # 이후 질문은 이 폴더에서만. /folder 만 치면 해제

RAGSearchBox 없이 SimpleRAG 만 쓰는 사람도 같은 기능을 쓰게 한다. 몸통(FolderSlice)은 하나다.

12결정 사항 — 2026-09-18 확정(전부 권장안)

  • B1
    기본 범위

    이 폴더(하위 포함) / 지정 폴더 전체 / 인덱스 전체.

    결정: 이 폴더. 요청하신 "패널 폴더 문서만" 그대로이고, 머리에 문서 수가 보여 좁아진 것을 바로 알 수 있다.

  • B2
    범위 안에 문서가 없을 때 넓힐 것인가

    자동으로 넓히면 편하지만, "이 폴더 문서만" 이라 믿은 답이 다른 폴더에서 나온다.

    결정: 넓히지 않고 알린다(§7).

  • B3
    행렬을 워커가 준비된 뒤 뒤에서 미리 만들 것인가

    안 만들어 두면 첫 폴더 질문이 행렬을 만드느라 늦어진다(6만 청크 3.2초, 지금 규모는 수 ms). 마스크는 수 ms 라 미리 만들 필요가 없다 — 처음 안의 /scope-warm 명령은 뺐다.

    결정: 뒤에서 미리 만든다.

  • B4
    범위 선택을 INI 에 저장할 것인가

    결정: 저장한다([Panel] SearchScope) — 너비처럼 주석을 지키며 그 줄만 바꾼다.

  • B5
    폴더가 없는 보통 질문도 이 행렬로 찾을 것인가

    114ms → 3ms 로 빨라지지만, 검색 결과가 Qdrant 와 같은지(정렬·동점 처리) 확인이 필요하다.

    결정: 이번에는 하지 않는다. FS1 에서 두 방식의 결과가 같은지 먼저 재어 보고 따로 정한다.
