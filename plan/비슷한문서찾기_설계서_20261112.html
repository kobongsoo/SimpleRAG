탐색기 모드 비슷한 문서 찾기 설계서

탐색기 모드에서 문서 하나를 넣으면(입력란 [+] · 입력란에 끌어 놓기 · 결과 줄 메뉴) 그 문서와 비슷한 문서를 찾아 목록으로 보여 준다. 답을 짓지 않고, 지금 찾기와 같은 문서 줄 화면에 사본 · 같은 문서의 다른 판 · 내용이 비슷한 문서를 나눠 보여 준다. 넣은 문서는 청크를 문서 전체에서 고른 간격으로 32개만 써서 빠르게 비교한다.

1검토 결론

만든다. 필요한 재료(메모리에 올라 있는 청크 벡터, 내용 해시 · 청크 본문, BM25, 찾기 결과 화면)는 이미 있다. 새로 만들 것은 입구(입력란 [+] · 입력란 끌어 놓기 · 결과 줄 메뉴), 워커 명령 /similar, 저장소의 문서별 최고 점수 훑기 세 가지다.

7주 입구는 입력란 [+](지원 확장자만 고르는 파일 창), 같은 입력란에 끌어 놓기도 받는다채팅 [+] 와 같은 방식이라 익숙하고, 파일 창 · 확장자 거르기 코드가 이미 있다
8인덱스에 있는 문서(A)와 바깥 문서(B)를 1단계에 함께[+] · 끌어 놓기로는 바깥 문서도 흔하다. A 는 임베딩 0번, B 는 32청크만 임베딩(~0.5초)

4입구 — 문서를 넣는 길

문서를 넣는 길은 세 가지다. 셋 모두 파일 경로 하나 → 같은 검사 → /similar 로 모인다.

입구어디서무엇을
① 입력란 [+] 주 입구탐색기 모드 입력란, [찾기] 바로 앞파일 고르기 창 → 지원 확장자 문서 하나
② 입력란에 끌어 놓기같은 입력란 위에 놓을 때만Windows 탐색기 · 바탕화면에서 끌어 온 파일
③ 결과 줄 메뉴찾기 결과 줄 오른쪽 클릭 → "비슷한 문서 찾기"목록에 보이는 문서(파일 창 없이, 결과에서 이어 가기)

입력란은 두 곳이다 — MoAI 탐색기 창 오른쪽 위 #q(browse.html:444), 탐색기 옆 패널(탐색기 모드)의 좁은 입력란 #pq(browse.html:502). 둘 다 같은 동작을 넣는다.

4-1. 입력란 [+] — 파일 고르기

  • [찾기] 앞에 [+] 버튼. 패널 입력란은 폭이 좁아 아이콘만. 툴팁 "문서를 골라 비슷한 문서 찾기" — 채팅의 [+](질문에 문서 붙이기)와 뜻이 다르므로 말을 분명히.
  • 앱이 rfd::FileDialog 로 연다(채팅 upload_pick 과 같은 방식, main.rs:1100).
    • .add_filter("문서", UPLOAD_EXTS) — 지원 확장자만 보인다(pdf · doc(x) · ppt(x) · xls(x) · hwp(x) · txt · md · csv · html · py · ipynb)
    • .pick_file() — 한 개만 고른다
    • 제목 "비슷한 문서를 찾을 기준 문서 고르기 — 파일당 N MB 이하"
    • .set_directory(지금 보는 폴더) — 보던 폴더에서 연다
    • .set_parent(탐색기 창) — [항상 위] 켬일 때 파일 창이 탐색기 창 뒤로 숨지 않게(채팅 코드는 부모를 안 정한다)
  • 파일 창 이름 칸에 *.* 를 쳐서 다른 파일을 고를 수 있으므로, 고른 뒤에도 확장자를 다시 검사한다(4-3).

4-2. 입력란에 끌어 놓기

  • 받는 범위: 창 전체가 아니라 입력란 위에 놓을 때만. 탐색기 창은 넓어 다른 곳에 잘못 놓기 쉽다. (채팅 패널은 패널 어디에 놓아도 받는다 — 채팅은 그대로 둔다.)
  • 받는 방법: 웹뷰 끌어 놓기 처리기(wry 0.47 with_drag_drop_handler)는 웹뷰 영역 전체에서 들어옴 · 움직임 · 놓음과 웹뷰 왼쪽 위 기준 좌표를 준다. 앱이 좌표를 화면 JS 에 넘기고, JS 가 document.elementFromPoint 로 입력란(.search) 안인지 판단한다.
    • 좌표 단위(물리 · 논리 픽셀)는 배율 125% · 150% 에서 놓아 보고 맞춘다 — 물리면 devicePixelRatio 로 나눈다
    • 처리기가 true 를 돌려 웹뷰 기본 동작(놓은 파일을 페이지로 열기)을 막는다
    • 탐색기 화면은 내부 끌기(draggable)를 쓰지 않아 처리기를 달아도 부딪히지 않는다
  • MoAI 탐색기 창: browse 웹뷰에 처리기를 새로 단다 → UserEvent::BrowseDrop.
  • 탐색기 옆 패널: on_panel_drop(main.rs:1130)의 "탐색기 모드면 아무것도 안 함"을 → 같은 처리로 바꾼다. 채팅 모드는 지금처럼 첨부.
  • 미리 보기(PDF)는 별도 창이라 그 위에 놓은 것은 받지 못한다 — 받지 않아도 된다(입력란만 받으므로).

4-4. 워커 안에서 — 인덱싱된 문서인가

A. 인덱스에 있는 문서

  • 경로가 인덱스에 있거나, 바깥 파일이라도 내용 해시가 인덱스에 있으면 A(메일 첨부가 폴더 문서의 사본인 경우)
  • 저장 벡터 사용 → 임베딩 0번(벡터 없는 청크만 ≤32개)
  • [+] 는 보던 폴더에서 열리므로 대부분 A 일 것으로 본다

B. 바깥 문서

  • extract_chunks → 고른 간격 32개만 임베딩 → 비교
  • 인덱스 · 업로드 폴더 어디에도 저장하지 않는다(일회성)
  • 진행 표시 "문서 읽는 중 → 비교 중"
  • [+] · 끌어 놓기가 주 입구가 되면서 바깥 문서도 흔하므로 1단계에 함께 넣는다

4-5. 넣은 뒤 입력란

  • 입력란에 "📄 문서명 ✕" 칩이 생기고 바로 찾는다. 칩 ✕ → 일반 찾기 화면으로.
  • 칩이 있을 때 검색어를 치고 [찾기] → 칩을 지우고 일반 찾기. 검색어 + 기준 문서를 함께 쓰는 검색은 1단계에서 하지 않는다.
  • 최근 검색 목록에는 남기지 않는다. [다시 찾기(F5)] 는 같은 기준 문서로 다시 찾는다.

5비슷함 계산

넣은 문서 청크→① 사본 · 판 차이 (해시)→② 고른 간격 32→③ 벡터: 문서별 최고 평균+④ BM25 핵심어→⑤ 합치기 · 상위 20→⑥ 겹친 문단 짝

① 사본 · 판 차이 — 점수 대신 분류

묶음판정비고
사본content_hash 가 같다경로만 다른 같은 파일
같은 문서의 다른 판넣은 문서 본문(공백 뺀 40자 이상 청크)의 20% 이상이 그대로 들어 있다실측에서 쓴 문턱. 겹친 비율을 % 로 보여 준다
  • 본문 → 문서 색인(squash(body) 해시 → 문서 id 들)은 저장소 적재 때 한 번 만들어 둔다. 실측 사본 적재 + 색인 약 33초(Python) — Rust 에선 적재와 함께 만들고, 처음 쓰일 때 만들어도 된다(§10 결정).
  • 40자 미만 청크는 판정에서 뺀다(find.rs SAME_BODY_MIN = 50 과 같은 뜻 — 별표 · 머리글 오판 방지).

② 청크 고르기

n = 넣은 문서 청크 수,  K = 32
n ≤ K  → 전부
n > K  → i = 0..K-1 마다 rows[floor(i · n / K)]   (chunk_idx 순)

③ 벡터 점수 — 문서별 최고 점수의 평균

score(D) = (1/K) · Σ_q  max_{c ∈ D} ⟨v_q, v_c⟩
  • 저장소에 doc_max_scan(qvs, allow) -> Vec<f32>(문서 수 길이) 추가. 점마다 문서 번호(u32)를 적재 때 붙여 두고 한 번 훑으며 문서별 최고값을 갱신.
  • 32 × 21만 × 384 ≈ 26억 곱셈 — 스레드 4개로 나눠 훑는다(목표 0.3초 안쪽, §8).
  • 벡터가 아직 없는 점(길이 0)은 건너뛴다 → 그 문서는 ④ BM25 로만 잡힌다.
  • A 경우 넣은 문서 청크에 벡터가 없으면 그 청크 글만 바로 임베딩(최대 32개).

④ BM25 핵심어

  • 넣은 문서 전체에서 TF-IDF 상위 20 단어(문서 df 는 BM25 색인 것을 씀) → 공백으로 이어 search_scored, 상위 300 청크 → 문서별 최고.
  • 임베딩이 필요 없으므로 B 경우에도 파싱 직후 바로 나온다 → 1차 결과(§8).

⑤ 합치기

  • 벡터 순위 · BM25 순위를 RRF(retrieve::rrf)로 합친다. BM25 를 최종에 넣을지는 §10 실측으로 정하고, 그 전엔 벡터 순위 그대로를 기본으로 둔다.
  • 자기 자신 · 사본 · 판 차이 제외 후 상위 20(find::MAX_DOCS). 폴더 범위 · 조건 칩은 찾기와 같이 allow 로.
  • 이름만 다른 같은 이름 문서(예: 경로 둘인 "Linux 설치 가이드 .doc")는 화면에서 한 줄로 묶는다.

⑥ 겹친 문단 짝 — "어디가 비슷한가"

  • 상위 20 문서만 다시 훑어(문서당 수백 청크라 작다) 점수가 가장 높은 (넣은 청크, 그 문서 청크) 짝 2개를 고른다.
  • 짝마다 양쪽 쪽 번호 · 발췌(clean_body 120자)를 싣는다. 클릭하면 상대 문서 그 쪽을 미리 보기.

6워커 명령 /similar

요청  /similar {"path": "D:\\...\\보고서.pdf", "folder": null, "off": [], "k": 32}
        path 가 인덱스에 있으면 A, 없으면 내용 해시로 찾고, 그래도 없으면 B

응답  @similar_stage {"stage": "keyword", "docs": [...]}        ← BM25 1차(선택, §8)
      @find {"kind": "similar", "no": 1, "group": "similar",
             "doc": {meta...}, "score": 0.81, "pct": 81,
             "pairs": [{"mine": {"page": 12, "snip": "…"}, "theirs": {"page": 7, "snip": "…", "id": 123}}]}
      @find {"kind": "similar", "group": "version", "overlap": 0.64, "doc": {...}}
      @find {"kind": "similar", "group": "copy", "doc": {...}}
      @find_done {"kind": "similar", "source": {"name": "보고서.pdf", "chunks": 412, "used": 32, "mode": "indexed|external"},
                  "ms": {"parse": 0, "embed": 0, "scan": 280, "bm25": 40}}
  • 찾기와 같은 @find · @find_done 줄을 써서 앱 worker.rs 의 읽기 코드를 그대로 쓴다. kind 로 화면 함수만 나눈다.
  • 워커 시작 줄 기능: 에 similar 추가. 앱은 w.knows("similar") 가 아니면 메뉴 항목을 숨기고, 끌어 놓으면 "simplerag-rs.exe 를 새로 빌드하세요".
  • CLI 로도 쓸 수 있게 simplerag-rs similar <파일> 추가(측정 · 시험용).

8속도 설계

단계A (인덱싱된 문서)B (바깥 100쪽 PDF, 추정)
파싱 · 청킹0~0.6초 (쪽당 6.4ms 실측)
임베딩0 (벡터 없는 청크만, ≤32)32청크 ~0.5초 (전부면 ~10초)
벡터 훑기32 × 21만 청크 — 목표 0.3초 (스레드 4)
BM25 · 해시 · 문단 짝~0.1초
합계 목표0.5초 안쪽1.5초 안쪽
  1. 뽑아 쓰기(32개) — 임베딩 · 훑기 모두 청크 수에 비례해 줄어든다.
  2. 내용 해시로 A 전환 — 바깥 파일도 인덱스에 같은 내용이 있으면 임베딩 없이.
  3. 두 단계 표시 — B 에서 임베딩이 길어지면(정밀 모델 bge-m3 등) 해시 묶음 · BM25 결과를 먼저 그리고, 벡터 결과로 다시 그린다. 기본 모델(e5-small)에선 0.5초라 먼저 보내는 결과 없이 한 번에 그려도 된다 — 임베딩 예상 시간 1초 넘을 때만 1차를 보낸다.
  4. 결과 기억 — content_hash + 인덱스 세대 를 키로 워커 메모리에 최근 8건. 같은 문서를 다시 넣거나 메뉴로 되돌아오면 즉시.
  5. 찾는 동안 벡터 채우기 쉼(w.note_use()) — 찾기와 같다.
하지 않는 것: 청크를 512토큰으로 합쳐 임베딩 횟수 줄이기(2026-10-30 실측: 크게 해도 같거나 느림), 문서 평균 벡터로 먼저 거르기(지금 규모에선 훑기가 이미 충분히 빠름 — 50만 청크를 넘으면 다시 본다).
