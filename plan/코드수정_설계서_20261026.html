1빌드가 배포 데이터를 지움 버그 · 최우선

무엇이 일어났나 (2026-10-26)

  • build_exe.py 는 PyInstaller 를 --noconfirm --distpath dist 로 돌린다. PyInstaller 는 출력 폴더 dist\simplerag 를 통째로 지우고 다시 만든다.
  • 그 폴더에는 빌드 산출물이 아닌 것도 있다 — 운영 인덱스(qdrant_data · bm25_index.npz · index_state.json), gen_backend.json, RAGSearchBox.exe · RAGSearchBox.ini, 배포본에서만 바꾼 config.yaml.
  • 이번에는 미리 백업해 복원했지만, 그냥 빌드하면 운영 인덱스와 설정을 잃는다(재인덱싱 필요, 트레이 앱 다시 빌드 필요).
  • 또 build_exe.py 248~252행이 빌드할 때마다 프로젝트 config.yaml 로 덮어쓴다 — 배포본의 parent: section 이 off 로 바뀐다.

수정 설계

  1. 보존 목록을 코드에 둔다: qdrant_data/ · bm25_index.npz · index_state.json · gen_backend.json · config.yaml · RAGSearchBox.exe · RAGSearchBox.ini*
  2. PyInstaller 실행 전에 보존 목록을 build\keep_<시각>\ 로 옮기고(복사가 아니라 이동 — 수십 MB), 빌드 성공·실패와 상관없이 finally 에서 되돌린다.
  3. config.yaml 은 배포 폴더에 없을 때만 복사한다. 새 키가 생겼으면 덮어쓰지 않고 "새 설정 키: echo_filter — 프로젝트 config.yaml 참고" 라고 알린다.
  4. 시작할 때 빌드 스크립트의 작업 폴더가 dist\simplerag 안이면 멈춘다(이번에 폴더가 잠겨 빌드가 반쯤 지우고 실패했다).
  5. Rust 쪽 rust/build_dist.ps1 은 이미 "있으면 덮어쓰지 않음"이라 고칠 것 없음 — 다만 실행 중인 RAGSearchBox-rs.exe 가 있으면 exe 만 건너뛰고 알리도록 한다(지금은 Copy-Item 오류로 끝남).

검증

  • 빌드 전후로 보존 목록 파일의 해시·개수가 같은지, simplerag.exe status 문서 수가 같은지. 빌드를 일부러 실패시켜도(잘못된 인자) 데이터가 돌아오는지.

2짧은 되뱉기 잡음 — 지연 없이 거르기 권장

배경

  • 되뱉기 거르기를 옵션(generation.echo_filter)으로 만들고 기본 끔으로 했다 — 화면 첫 글자가 TTFT 보다 늦은 시간 2.07~2.43초 → 0.08초.
  • 대신 골든셋 100문항(1.7B) 중 9건에 잡음이 남는다: "근거 [1]에 따르면" 5건(q011·q029·q035·q041·q096), "[1] 형식으로 표기:" (q056), "근거 번호: [2]" (q016), "[1]의 근거 번호는 [1]입니다" (q075), 끝 인용 두 번 찍기 1건(q020 — ③에서 다룸).
  • 켜 둔 거르기가 오래 붙드는 이유는 "…(최대 40자) 간결하게 답변합니다" 처럼 앞 40자까지 지우는 긴 패턴 때문이다. 위 9건은 모두 짧고 모양이 고정된 패턴이다.

수정 설계 — "짧은 거르기" 를 끔 상태의 기본 동작으로

  1. 짧은 패턴 목록(SHORT_ECHO)을 따로 둔다 — 길이가 정해진 것만: 근거\s*(?=\[\d+\])(뒤 인용 앞의 '근거' 낱말) · 근거\s*번호\s*:?\s*\[\d+\] · \[\d+\]\s*형식으로\s*표기[^.\n]* · \[\d+\]의\s*근거\s*번호는\s*\[\d+\]입니다\.?
  2. 출력기는 중단 문자열과 같은 방식으로 붙든다: 받아 둔 글의 끝이 짧은 패턴의 앞부분과 겹칠 때만 그 겹친 글자(최대 ~16자)를 붙든다. 예) 끝이 "근거" 이면 다음 글자가 "[" 인지 볼 때까지 2자만 붙든다. 겹치지 않으면 바로 내보낸다 → 지연은 대부분 0.
  3. 마무리 정리(clean_answer(echo=False))에도 같은 짧은 패턴을 적용한다(비스트리밍·평가 경로).
  4. 긴 패턴(_ECHO_PATTERNS 의 40자형)은 지금처럼 echo_filter: true 일 때만.
  5. 두 판 같은 규칙: Python generate/prompts.py(SHORT_ECHO · clean_answer) · cli.py(StreamWriter._ready_part) / Rust generate/prompts.rs · cli.rs(StreamWriter::ready_part). Rust 의 suffix_prefix(중단 문자열용) 를 그대로 쓸 수 있다.

주의

  • "근거" 가 본문 낱말인 경우("근거 규정은 제5조이다") — 뒤에 [숫자] 가 올 때만 지우므로 건드리지 않는다. 시험 사례로 넣는다.
  • "[1] 형식으로 표기" 는 지시문 문구 그대로라 정상 답에 나올 일이 드물다 — 그래도 지우면 안 되는 사례를 시험에 함께 넣는다.

검증

  • bench/rust_vs_py/perf.py chat 100문항: 화면 첫 글자 − TTFT 중앙값 ≤ 0.3초, 잡음(위 정규식으로 셈) 9 → 2건 이하, 두 판 답 일치 유지.
  • 시험: 위 9건 실제 답 + "근거 규정은" 같은 지우면 안 되는 사례 + 1·3·7자 흘려 넣기.

3스트리밍에서 인용 번호가 두 번 찍힘 권장

무엇이 일어났나

  • q020(끔): "…결을 맡는다. [1][3][1][3]". 모델이 끝 인용을 두 번 썼다.
  • 마무리 정리의 _TRAILING_CITES(끝의 중복 인용을 하나로 접기)는 동작하지만, 앞의 "[1][3]" 이 이미 화면에 나간 뒤라 되돌릴 수 없다.

수정 설계

  1. 출력기가 인용 번호 덩어리((\s*\[\d+\])+\s*$)로 끝나는 동안은 그 덩어리만 붙든다 — 뒤에 본문 글자가 오면 내보내고, 답이 끝나면 접어서 내보낸다.
  2. 덩어리가 문장 끝에 붙는 것이라 길이는 보통 3~12자 — 지연은 끝부분에만 생기고 첫 글자에는 영향이 없다.
  3. ②와 같은 함수(_ready_part / ready_part)에서 함께 처리한다.

검증

  • q020 원문 재현 시험, 본문 중간 인용("[1]에 따르면, …")은 붙들다가 바로 내보내는지. 100문항 측정에서 끝 인용 중복 0건.

4가끔 실패하는 감시 시험 권장

무엇이 일어났나

  • RAGSearchBox/tests/test_watcher.py::TestLive::test_live 가 이번 작업 중 2번 실패 — 둘 다 다른 무거운 작업(Rust 컴파일·인덱싱)과 동시에 돌 때. 따로 돌리면 3/3 통과.
  • 실제 파일 시스템 감시를 하므로, 시험의 wait(timeout=8.0) 안에 이벤트가 안 올 수 있다.

수정 설계

  1. 대기 한도를 환경변수로 늘릴 수 있게 한다(WATCH_TEST_TIMEOUT, 기본 8 → 20초).
  2. 실패 시 마지막으로 받은 배치(reason·changed)를 메시지에 남겨 원인을 바로 알 수 있게 한다.
  3. 그래도 흔들리면 이 시험만 "실시간" 표식을 달아 기본 실행에서 빼고, 릴리스 전 점검 때만 돌린다.

검증

  • 인덱싱을 돌리는 동안 10회 연속 실행해 모두 통과.

5인용 번호가 틀린 근거를 가리킴 실험

무엇이 일어났나

  • simplerag.exe ask "본인 결혼 시 경조금은 얼마인가요?" → 답 "500,000 원입니다. [1]" — 맞는 값은 근거 [2]·[3](경조사지원규정)에 있고 [1] 은 김영란법 사례집이다.
  • 얼마나 자주 생기는지는 아직 재지 않았다. 사용자는 인용 번호를 보고 근거를 확인하므로, 틀린 번호는 검증을 방해한다.

수정 설계

  1. 먼저 잰다: 골든셋 100문항 답에서 문장별 인용 [k] 마다, 그 문장의 숫자·고유어(정규식으로 뽑은 금액·일수·조항 등)가 근거 k 에 있는지 / 다른 근거에 있는지 센다 → "인용 정확도".
  2. 후처리 재지정: 문장의 핵심 토큰이 인용한 근거에 하나도 없고 다른 근거 하나에만 있으면 그 번호로 바꾼다. 애매하면(여러 근거에 있거나 아무 데도 없으면) 그대로 둔다.
  3. 스트리밍은 문장이 끝난 뒤에야 판정되므로, 바뀐 번호는 소요 블록 아래 "인용 근거" 줄과 RAGSearchBox 근거 강조에만 반영하는 방안부터 시작한다(본문은 이미 나감).

검증

  • 인용 정확도 개선, 정답 핵심어 포함률 불변. 사람 확인용으로 바뀐 사례 20건을 표로 남긴다.

6표현이 다르면 검색이 놓침 실험

무엇이 일어났나

  • "할아버지 돌아가시면 유급휴가는 며칠…" → 근거에 '조부모' 항목이 들어오지 않아 엉뚱한 항목(배우자 부모)으로 답했고, 그 혼란이 반복 루프로 이어졌다.
  • 골든셋 질문은 문서 용어를 그대로 써서(적중 100/100) 이런 문제를 잡지 못한다.

수정 설계

  1. 바꿔 말한 질문 세트를 먼저 만든다(30~50문항): 구어·동의어 질문 → 정답 문서·쪽. 예) 할아버지→조부모, 와이프·아내→배우자, 연차→연차휴가, 출장비→여비.
  2. 동의어 사전을 config.yaml(또는 옆 파일 synonyms.yaml)에 둔다 — 사용자가 사내 용어를 추가할 수 있게.
  3. 질의 확장은 BM25 쪽만: 질의 토큰에 동의어를 덧붙인다(dense 는 e5 가 이미 의미를 어느 정도 잡음). 재인덱싱 불필요.
  4. 두 판 같은 규칙(Python retrieve/hybrid.py · Rust retrieve.rs).

검증

  • 바꿔 말한 질문 세트의 문서 적중·쪽 적중 개선, 골든셋 100문항 적중 100/100 유지, 검색 시간 증가 < 10ms.

  • 추론: 계산을 틀린다(월급 환산, 일수×금액, 몇 배 비교). 멀티홉: 근거 3건 안에 두 번째 조항이 없거나, 있어도 한쪽만 쓴다.

실험 후보 (하나씩, 같은 57문항으로)

  1. 근거 수: top_k 3 → 5 (멀티홉 Recall 목표). TTFT 증가와 맞바꿈 — 수치로 비교.
  2. 모델: 배포 폴더에 있는 Mi:dm 2.0 Mini · Kanana 1.5 2.1B 와 1.7B 비교(멀티홉+추론 57문항만, TTFT 함께).
  3. 지시문: 계산이 필요한 질문이면 "근거의 숫자를 먼저 적고 식을 쓴 뒤 답" — 1단계에서 지시문 손잡이는 효과가 없었으므로(REPORT §40.5) 우선순위는 가장 낮다.

검증

  • 57문항 핵심어 포함률과 RAGAS(Claude 판정, 같은 방식) 비교, 싱글홉 43문항 퇴보 없음, TTFT 중앙값 변화 기록.

검토 결과 (2026-10-28) — 멀티홉은 검색, 추론은 1.7B 의 계산이 원인. 지금 손잡이로는 답이 안 오른다

결론: 근거 늘리기 · 생각 모드 · 계산기 보조 · 이웃 청크 넷 다 기본값으로 넣지 않는다. 근거는 채울 수 있지만(정답 발췌 63 → 73) 1.7B 의 답은 잡음 수준(50 → 51)만 오른다. 남은 손잡이는 더 큰 모델(4B) — 측정 전.

자료: 골든 100문항, Python chat 워커 최신 결과(⑤ 반영 뒤, results/rust_vs_py/chat_python.json). 정답 = 핵심어(must) 전부 포함, 정답 발췌 = 골든 발췌가 근거에 모두 듦. 규칙 지표만 썼다(RAGAS 판정 없음).
