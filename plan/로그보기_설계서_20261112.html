1. 요구 사항 정리

① 실패 문서 보기인덱싱에 실패한 문서마다 이름·위치·실패 원인을 보여 준다. 사용자가 무엇을 하면 되는지(스캔 PDF라 OCR 필요 등)까지 쉬운 말로.
② 로그의 경고·오류 보기인덱싱 말고도 로그에 남은 WARNING·ERROR 줄(워커 종료, 감시 실패, 저장 실패 등)을 함께 보인다.
③ 로그 폴더 옮기기기본 판 맨 아래 "로그 폴더" 묶음을 로그 판으로 옮긴다.
④ 이름·폴더 바꾸기RAGSearchBox._날짜.log → MoAISearch_날짜.log, 기본 폴더 → %LOCALAPPDATA%\MoAISearch\log.

이번 작업은 검토와 설계까지이다. 코드는 바꾸지 않았다.

2-2. 실패 문서는 어디에 남나

  • 로그: 자동 반영(/index-doc) 실패는 rsb.autoindex 반영 실패 index-doc: 경로 — "사유" 로 경로와 사유가 남는다(jobs.rs:591). 그러나 폴더 전체 index 명령 실패는 개수만 남는다(jobs.rs:834 "실패 N", round.failed 에 "?"). 이름은 워커 로그 [index] 줄에 섞여 있다.
  • 인덱스 상태 파일 index_state.json 의 "failed" 묶음: {경로: {fingerprint, why, name}}(indexer.rs:856). 지금 실패 중인 문서의 정답 목록이다 — 나중에 성공하거나 지워지면 failed_pop 으로 빠진다. 같은 파일(지문 같음)은 다시 시도하지 않는다(plan_changes 의 retry_skip, /index-doc 의 failed_before).
  • 사유 글은 why_of() 가 "종류: 내용" 꼴, 내용 80자로 줄인다. 예: ExtractError: 하이브리드 전엔진 실패(감지=pdf; pdf:empty).
결론 — 실패 문서 목록은 로그를 긁지 않고 index_state.json 의 failed 를 읽는다. 로그를 긁으면 ① 이미 고쳐진 문서가 계속 남고 ② 전체 인덱싱 실패는 이름이 없으며 ③ 5MB 돌려 쓰기·날짜 바뀜으로 빠진다. 상태 파일은 이 셋이 다 없다.

2-3. 함께 영향받는 것 — 로그 폴더의 "부모"를 쓰는 곳

주의 — 아래 둘은 log_dir() 의 부모 폴더를 앱 데이터 폴더로 쓴다. 로그 폴더만 바꾸면 이 둘도 몰래 따라 옮겨져 대화 기록이 사라진 것처럼 보이고 WebView 캐시가 새로 만들어진다.
  • history.rs:16 — 대화 기록 history.json = log_dir()/../history.json
  • main.rs:2824 — WebView2 사용자 데이터 = log_dir()/../webview
folder_icon.rs:41 는 RAGSearchBox-rs 를 직접 적어 따로 쓴다. 그래서 앱 데이터 폴더 함수(app_dir())를 따로 두고 위 둘을 그쪽으로 돌린 뒤 로그 폴더를 바꾼다(§6).

3-1. 실패 문서 묶음

  • 한 줄 = 한 문서. 이름(굵게) + 폴더(작게), 원인(쉬운 말) + 할 일 한 줄, 실패한 때, 단추.
  • 정렬: 최근 실패가 위. 같은 원인 묶음 알약(전체 · 원인별 개수)으로 거른다.
  • 원래 사유(why 원문)는 줄을 누르면 펼쳐 보인다 — 문의할 때 복사해 붙일 수 있게.
  • kept_old(옛 버전 유지)면 "예전 내용으로 검색됩니다" 를 덧붙인다 — 수정본만 실패했고 검색은 된다는 뜻.
  • 단추: [열기](기존 open_file), [폴더](기존 reveal), [다시 시도](§4-3). 파일이 없어졌으면 단추 대신 "파일 없음" — 다음 대조 때 목록에서 빠진다.
  • 문서 수가 많을 수 있으므로(분류함 수천 건 중 수백 건 가능) 처음 200줄만 그리고 [더 보기].
  • 없으면: "실패한 문서가 없습니다 ✓".

3-2. 로그 경고·오류 묶음

  • 최근 7일 프로그램 로그의 WARNI · ERROR 줄 + 워커 로그에서 오류로 보이는 줄(§5-2).
  • 같은 내용은 한 줄로 묶어 횟수를 보인다 — 감시 실패처럼 60초마다 되풀이되는 경고가 목록을 덮지 않게.
  • 반영 실패 · index 명령 실패 줄은 위 실패 문서 묶음과 겹치므로 기본으로 숨기고 "인덱싱 실패 줄도 보기" 를 켜면 보인다.
  • 줄을 누르면 그 묶음의 원래 줄들(최대 20줄, 시각 포함)을 펼친다.

3-3. 로그 폴더 묶음

기본 판의 "로그 폴더" fieldset 을 그대로 옮기고(logdir · b_logs · open_logs 재사용) 오늘 파일 이름과 기록 단계를 한 줄 덧붙인다. 기본 판에서는 지운다.

3-4. 언제 읽나

설정 창은 1초마다 info_json 을 다시 받는다. 로그 읽기는 그보다 무거우므로 1초 주기에 넣지 않는다. 로그 판을 열 때 한 번, [새로고침]을 누를 때 읽는다. 메뉴의 개수 표시(로그 (12))만 1초 주기의 info_json 에 n_failed 로 싣는데, 이는 상태 파일 수정 시각이 바뀔 때만 다시 센다(§4-1).

4. 실패 문서 — 데이터와 원인 풀이

4-1. 읽는 법

  • GUI 가 워커 폴더의 index_state.json 을 읽기만 한다. 워커는 write_atomic 으로 바꿔 끼우므로 반쯤 쓴 파일을 읽을 일이 없다.
  • 워커 명령으로 받지 않는 까닭: 모델을 올리는 중이거나 워커가 죽었을 때(=실패를 가장 보고 싶을 때)에도 보여야 한다.
  • 상태 파일 경로는 워커 config.yaml 의 인덱스 위치에서 정한다(GUI 는 이미 정밀 모드 때문에 config.yaml 을 찾는다 — main.rs:1507). 정확한 경로 계산은 simplerag config.rs:423(root/index_state.json)와 같게.
  • 크기: 운영 상태 파일은 수백 KB~수 MB(dist-rust/index_state.json 668KB). 수정 시각·크기를 기억해 바뀌었을 때만 다시 파싱하고, failed 만 꺼낸다.

4-2. 상태 파일에 더할 값 (simplerag)

지금 failed 에는 언제 실패했는지가 없다. 실패를 적는 곳(indexer.rs:856 외 같은 꼴)에 두 값을 더한다. 옛 항목엔 없으므로 읽는 쪽은 없으면 "—" 로 보인다(하위 호환).

"failed": {
  "D:\\분류함\\영업\\채널계약\\채널사협력계약(카파정보기술_230315).pdf": {
    "fingerprint": "…", "why": "ExtractError: 하이브리드 전엔진 실패(감지=pdf; pdf:empty)",
    "name": "채널사협력계약(카파정보기술_230315).pdf",
    "at": "2026-11-12 12:57:12",     // 새로 — 실패한 때(현지 시각)
    "kept_old": false                  // 새로 — 옛 버전이 인덱스에 남아 검색되는가
  }
}

Python 판과 상태 파일 모양을 맞춰 왔으므로(indexer.rs:12), 키를 더하기만 하고 기존 키는 그대로 둔다. Python 판은 모르는 키를 무시한다.

4-3. [다시 시도]

  • 지금 /index-doc 은 같은 지문의 실패 문서를 failed_before 로 바로 돌려보낸다(commands.rs:132). 그래서 인자에 "retry": true 를 받으면 이 검사를 건너뛰게 한다.
  • GUI 는 이를 자동 인덱싱 큐(jobs.rs)에 넣어 다른 반영과 같은 순서로 처리한다 — 질문 중이면 기다린다.
  • 쓸모: 파일이 잠겨 있었거나(읽기 실패) 추출기·설정이 바뀐 뒤. 스캔 PDF 처럼 다시 해도 같은 결과일 원인은 단추 옆에 "다시 해도 같을 수 있음" 을 작게 보인다.
  • 끝나면 결과를 알림(기존 notify)으로 보이고 목록을 새로 읽는다.

5. 로그 경고·오류 — 읽기와 묶기

5-1. 프로그램 로그

  • 대상: 로그 폴더의 MoAISearch_YYYY-MM-DD.log 와 돌려 쓴 .1 .2 .3, 오늘부터 7일.
  • 줄 모양 YYYY-MM-DD HH:MM:SS 단계 rsb.이름 내용 을 나눠 단계가 WARNI · ERROR 인 줄만 고른다. 여러 줄로 이어지는 경고(워커가 종료됨 뒤 stderr: …)는 앞줄에 붙인다.
  • 파일마다 끝에서 최대 2MB만 읽는다(5MB 돌려 쓰기 한도 안). 7일 × 수 MB 라도 수십 ms 수준 — 그래도 메인 스레드를 막지 않게 별도 스레드에서 읽고 결과를 보낸다.
  • 최대 500묶음까지. 넘으면 "더 오래된 것은 로그 폴더에서 보세요".

5-2. 워커 로그

워커 로그는 단계 없이 모두 INFO 로 적힌다. 그래서 내용에 panicked · error/Error · 오류 · 실패 가 있는 줄만 "워커" 로 골라 경고로 보인다. [index] 줄의 문서별 실패는 실패 문서 묶음과 겹치므로 숨김 대상(인덱싱 실패 줄)으로 친다.

5-3. 같은 내용 묶기

  • 묶음 열쇠 = (단계, rsb.이름, 내용 틀). 내용 틀은 숫자를 # 로, 따옴표·경로 뒤의 사유는 남기고 경로만 … 로 바꾼 글이다. 예) 폴더를 지켜볼 수 없다(60초 뒤 다시): \\NAS\공유 — 지정된 네트워크 이름… 는 하루 종일 하나로 묶인다.
  • 보이는 값: 마지막 시각, 첫 시각, 횟수, 대표 줄(마지막 줄 원문).
  • "인덱싱 실패 줄" = 이름이 autoindex 이고 내용이 반영 실패 · index 명령 실패 로 시작하는 줄 + 워커 [index] 실패 줄.

5-4. 단계 이름 바꿔 보이기

WARNI → 경고, ERROR → 오류. 로그 파일 형식은 바꾸지 않는다(Python 판 · 기존 분석 습관과 같게).

9. 확인 방법

  1. 단위 테스트: 파일 이름(MoAISearch_2026-11-12.log), 로그 줄 나누기, 원인 풀이표(붙여 주신 pdf:empty 표본 포함), 같은 내용 묶기, 옛 failed 항목(at 없음) 읽기.
  2. 대화 기록 유지: 바꾼 판을 켠 뒤 패널의 지난 대화가 그대로 있는지, RAGSearchBox-rs\webview 를 계속 쓰는지.
  3. 새 로그 폴더: %LOCALAPPDATA%\MoAISearch\log 에 두 파일이 생기는지, 설정 > 로그 > [열기] 가 그 폴더를 여는지.
  4. 실패 문서: 분류함의 스캔 PDF(예: 채널계약 폴더)가 "글자 없는 PDF" 로 보이는지, 개수가 상태 파일 failed 수와 같은지, 메뉴 로그 (N).
  5. 다시 시도: 문서를 다른 프로그램으로 잠가 실패시킨 뒤 풀고 [다시 시도] → 목록에서 빠지는지.
  6. 경고 묶기: 네트워크 폴더를 끊어 감시 경고를 여러 번 낸 뒤 한 줄 · 횟수로 보이는지.
  7. 부담: 운영 상태 파일(3,500건 규모)과 7일 로그로 로그 판 열기 시간 측정 — 목표 0.5초 안.

10. 정해 주실 것

① 앱 데이터 폴더 전체도 MoAISearch 로 옮길까? 제안: 이번엔 로그만 요청대로 로그 폴더만 MoAISearch\log 로 옮기고 대화 기록·WebView·아이콘은 RAGSearchBox-rs 에 둔다. 폴더가 둘이 되는 게 어색하면, 다음 판에서 RAGSearchBox-rs 전체를 MoAISearch 로 한 번 옮기는 작업(처음 켤 때 옮기기 · 실패 시 옛 폴더 계속 쓰기)을 따로 한다.
② 워커 로그 이름 제안: MoAISearch-worker_날짜.log 요청은 프로그램 로그만 말씀하셨다. 워커 로그를 worker_날짜.log 로 그냥 둘 수도 있다.
③ 옛 로그 처리 제안: 그대로 둠 옛 폴더의 로그를 새 폴더로 옮기거나, 로그 판이 옛 폴더도 함께 읽게 할 수도 있다(7일 지나면 의미 없어짐).
④ [다시 시도] 를 넣을까? 제안: 넣음 simplerag 쪽 retry 인자 한 개가 더 필요하다. 보기만 원하시면 빼고 [열기]·[폴더]만 둔다.
⑤ 경고·오류 보는 기간 제안: 7일 오늘만 · 3일 · 7일 고르기를 둘 수도 있다.
