2지금 동작과 한계

BM25 상위 60청크+코사인 상위 60청크→RRF · 사본 제거 → 60청크→앞 12개 리랭킹→문서 최대 20개 + 이름 일치 5개

관련도 임계값(RelevanceMin)은 탐색기에서 문서를 빼지 않고 흐리게만 표시한다. 그래서 결과를 줄이는 것은 임계값이 아니라 청크 60개 · 문서 20개 상한이다.

상한만 풀면 안 되는 이유

  • BM25 — 검색어를 작은 토큰으로 쪼개고 그중 하나만 있어도 일치로 친다. "프로젝트 교통비"는 교통 · 비 토큰으로 나뉘어 거의 모든 문서가 걸린다.
  • 코사인 — 모든 청크에 유사도 값이 있어 "검색됨"의 경계가 없다. 임계값 없이 "모두"를 보여 주면 항상 전체 문서다.

3"모두"의 기준

검색어 낱말이 문서 안에 글자 그대로 있는지로 정한다. 낱말이 같은 청크에 있을 필요는 없다. 세 묶음을 모두 쓰되 일부 포함은 접어 둔다.

묶음기준기본 표시이유
① 검색어 모두 포함모든 낱말이 문서 안에 있음펼침찾으려는 문서일 가능성이 가장 높다.
② 검색어 일부 포함낱말 일부만 있음접힘 · 건수 표시. ①이 0개면 자동으로 펼침빠짐없이 찾되 "프로젝트"만 든 문서가 화면을 채우지 않게 한다.
③ 비슷한 내용①②에 없고 지금 검색(하이브리드) 후보에 든 문서펼침 · 최대 20개글자가 달라도 의미가 가까운 문서를 놓치지 않는다.
1+3 안을 쓰지 않는 이유 — "리플레쉬 휴가"는 ①이 0개라 글자가 든 문서 83개가 모두 빠지고 코사인 후보만 남는다. "모두 찾기"라는 이름과 맞지 않아 ②를 접힌 채로 둔다.

파일 이름 일치 묶음은 지금처럼 맨 위에 둔다. 조건만 있는 찾기(낱말이 없는 메타데이터 검색)는 묶음을 쓰지 않고 조건에 맞는 문서를 상한 없이 보여 준다. 폴더 범위 · 조건 칩은 세 묶음 모두에 적용한다.

5동작 규칙

상황동작
체크박스를 바꿈지금 검색어로 바로 다시 찾는다. 앞선 AI 정리는 취소한다.
꺼진 상태에서 "모두 보기" 링크체크박스를 켜고 다시 찾는다.
②를 펼침이미 받은 문서 줄을 그린다. 다시 찾지 않는다.
문서를 펼침함께 받은 앞 5쪽을 바로 보여 준다(화면에는 지금처럼 3곳).
＋ N곳 더 보기그 문서의 나머지 쪽 줄을 가져와 잇는다.
쪽을 고름PDF 는 그 쪽을 띄우고, 글 미리 보기는 그 쪽의 본문을 그때 가져온다.
보기를 "쪽 목록"으로 바꿈모든 묶음의 쪽을 문서 구분 없이 관련도 순으로 보여 준다. 받지 않은 쪽은 이때 가져온다.
정렬을 이름 · 날짜로 바꿈묶음 안에서 정렬한다. 묶음 순서는 유지한다.
AI 답변창그대로 상위 최대 3건을 정리한다. 리랭킹 점수가 있는 문서만 후보로 쓴다.
앱을 다시 시작체크 상태를 유지한다.
탐색기 옆 패널이번 범위에서 제외한다. 폭이 좁아 묶음 목록에 맞지 않는다.

쪽(페이지) 검색 유지

"어느 문서의 몇 쪽 어디"를 보여 주는 지금 장점은 그대로 둔다. 모두 찾기를 켜도 문서 ▸ 쪽 ▸ 발췌 · 강조 · 쪽 클릭 미리 보기 · 그 쪽 열기 · 쪽 목록 보기가 모두 동작한다. 응답이 커지지 않게 문서마다 앞 5쪽의 줄만 먼저 보내고, 쪽 본문은 고를 때 가져온다.

지금 찾기는 0.8~1.1초 걸리고 대부분 임베딩 · 리랭킹이다. 모두 찾기는 글자 찾기와 표시가 더 붙어 약 1초대로 어림한다. 워커가 본문을 이미 메모리에 두고 있어 추가 메모리는 거의 없다.

측정 한계 — 찾기는 Python, 표시는 브라우저의 가짜 데이터로 쟀다. Rust 워커와 실제 앱 창의 값이 아니며 구현 뒤 다시 잰다. 문서별 발췌 생성 시간은 재지 않았다. 쪽 줄 약 2,000개의 발췌 생성 시간은 재지 않았고, 표시 측정도 문서 줄 기준이다. 쪽 줄이 많으면 표시가 더 걸릴 수 있어 §8 에서 다시 잰다. 기본이 켜짐이므로 이 시간은 모든 찾기에 더해진다.

7구현 설계

지금 찾기(하이브리드)+본문 글자 훑기→① ② ③ 묶기→문서 줄 응답→펼칠 때 쪽 조회

워커 — /find 확장

/find {"q":"프로젝트 교통비","folder":null,"all":true}
@find {"doc":1,"doc_path":"…","doc_name":"…","tier":1,"matched":2,"score":6.78,"hits":3,"mtime":…}
@find {"doc":1,"page":5,"section":"…","score":6.05,"snippet":"…","marks":[…],"chunk_idx":12,"pages_left":2}
@find_done {"docs":369,"tiers":[32,337,12],"ms":…}

/find-doc {"q":"프로젝트 교통비","path":"…"}          ← 더 보기 · 쪽 목록: 그 문서의 나머지 쪽 줄
/find-page {"path":"…","chunks":[12,13]}            ← 쪽을 고를 때: 글 미리 보기 본문
  • all 이 없으면(체크 끔) 지금과 글자까지 같은 출력을 낸다. 화면은 기본으로 all: true 를 보낸다.
  • 쪽 줄은 본문 text 를 빼고 쪽 · 위치 · 발췌 · 강조 위치만 싣는다. 문서마다 점수와 맞은 낱말 수가 높은 앞 5쪽을 보낸다.
  • 낱말은 기존 keywords() 로 조사를 뗀다. 메타데이터 계획이 있으면 조건을 뺀 p.query 를 쓴다.
  • 폴더 범위와 메타 문서 범위는 기존 allow · docs 를 그대로 쓴다.
  • tier 안의 순서는 리랭킹 점수가 있는 문서 → 맞은 낱말 수 → 맞은 청크 수 순이다.
  • 워커 기능 목록에 find-all 을 추가해, 옛 워커에서는 체크박스를 숨기고 지금처럼 찾는다.

9메모리 구조와 규모 한계

판단 — 지금 규모(20.6만 청크)에서는 메모리 전체 적재를 유지한다. 모두 찾기는 이미 메모리에 있는 본문을 훑으므로 메모리를 크게 늘리지 않는다. 청크가 100만 개에 이르면 메모리 검색 방식을 다시 검토한다.

지금 구조

points.sqlite (영구 저장)→워커 시작 때 벡터 · payload 전부 적재→검색은 메모리에서
  • 워커가 뜰 때 SELECT id, vec, payload FROM points 로 모든 행을 읽어 메모리 표에 넣는다(store.rs ensure_loaded). 필요할 때마다 읽는 방식이 아니다.
  • 새 문서는 SQLite 와 메모리에 함께 반영한다. 60분 유휴나 트레이에서 내리면 메모리를 돌려주고, 다음 사용 때 다시 전부 적재한다.
  • 20.6만 청크에서 워커 준비는 약 4.8초(모델 등과 병렬 적재), 시작 시간과 메모리는 청크 수에 비례한다.

규모별 어림 (저장 크기 기준)

청크 수본문본문 + 벡터 + BM25 + 그 밖의 payload판단
20만 (지금)약 80MB약 0.6GB유지
50만약 200MB약 1.5GB시작 시간 · 메모리 측정
100만약 400MB약 3GB방식 검토 필요

메모리에서는 관리 비용 때문에 저장 크기보다 커진다. 지금 워커 전체는 약 4.3GB(최대 약 5.1GB)이고 이 안에 생성 모델 약 1.1GB 가 포함된다. 항목별 실제 메모리는 재지 않았다.
