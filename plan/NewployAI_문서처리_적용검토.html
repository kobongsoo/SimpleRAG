1결론 요약

OCR 엔진이 아니라, Newploy 가 텍스트를 '페이지·영역 목록'으로 다루는 방식이 SimpleRAG 에 바로 쓸모 있다.

SimpleRAG 는 추출 결과를 한 덩어리 문자열로 받는다. 그래서 PDF 의 쪽 경계가 "\n".join(parts) 에서 사라지고, 머리말·쪽번호·목차 같은 잡음이 본문과 섞인 채 청킹된다. Newploy 의 핵심 아이디어인 쪽 보존 · 영역 종류로 잡음 구분 · 찾은 뒤 주변으로 확장은 레이아웃 모델 없이 규칙만으로도 상당 부분 흉내 낼 수 있고, 비용이 낮다.

2두 시스템의 문서 처리 흐름 비교

Newploy AI Desktop

  1. 입력 분기 — 텍스트층 PDF → 그대로(뷰어 모드) · HWPX/DOCX → 전용 파서 · 스캔/이미지 → OCR
  2. 추출 — 레이아웃(영역 20종) → 줄 검출 → 글자 인식 → 표 행·열 복원 → 맞춤법/LLM 보정
  3. 구조화 저장 — 페이지 → 영역 {type, bbox, text, source}
  4. 청킹 — 영역을 읽기 순서로 쌓아 300자 이상 또는 페이지 변경 시 끊음 · 표는 TSV 별도 · 겹침 없음
  5. 색인 — 키워드(FTS5) + e5-small 벡터, RRF 결합, 리랭커 없음
  6. 질의 — LLM 검색어 재작성 → 후보 64 → 문서당 4 → 최대 16 → 해당 페이지 전체로 확장

SimpleRAG (현재)

  1. 입력 분기 — 포맷 감지(OLE 보정) → CSO 전용 파서 11종 · 실패 시 사이냅 폴백 · 스캔 PDF 는 "추출 텍스트 없음"으로 건너뜀
  2. 추출 — 텍스트층/파서 결과 문자열 · PDF 쪽 경계는 "\n".join 으로 소실
  3. 정제 — 비문자·서로게이트 제거(sanitize) → Word 탭 표를 마크다운 표로(normalize_tables, 무손실 검사)
  4. 청킹 — 제목 문법 1종 + 부속서 표지로 절 분할 → 128토큰 예산 패킹 → 큰 절만 겹침 분할 · 표 머리글 재부착 · [문서 > 절] 접두
  5. 색인 — e5 dense + BM25, 리랭커 있음 · payload 에 chunk_idx 있음, 쪽 정보 없음
  6. 질의 — 후보 10+10 → 리랭크 → 상위 3 · 관련 근거 문턱(RelevanceMin)

정리하면 차이는 2단계(추출)의 출력 형태에 몰려 있다. Newploy 는 청킹이 '긴 문자열'이 아니라 '종류·쪽이 붙은 영역 목록'을 받는다. SimpleRAG 의 청킹(4단계)은 이미 구조를 인식하지만, 그 구조를 문자열에서 다시 추측해야 한다. 쪽 경계처럼 추출기는 알고 있었는데 문자열로 합치면서 버린 정보가 있다는 점이 가장 큰 개선 여지다.

3항목별 검토

3-1. 쪽 경계 보존 적용 권장 · P1

현재 — MpowerClassify 의 PdfiumExtractor.extract 가 쪽마다 get_text_range() 로 읽은 뒤 "\n".join(parts) 로 합친다. 쪽 구분이 줄바꿈 하나와 구별되지 않는다.

Newploy 에서 배울 점 — 청크가 쪽을 넘지 않게 해서 출처 쪽을 정확히 남기고, 답변 아래 "참조 원문 N페이지"를 보여 준다.

적용 방안

  • 쪽 사이에 폼피드 \f 를 넣어 경계를 남긴다. 다만 PdfiumExtractor 는 MpowerClassify 분류 엔진과 공유하므로 그쪽을 바꾸지 않고 SimpleRAG extract.py 에서 PDF 만 pypdfium2 로 직접 읽는 얇은 래퍼를 두는 편이 안전하다 (분류 쪽 회귀 위험 0, 상한 G5 로직은 복제 필요).
  • 청킹은 \f 를 절보다 약한 경계로 다룬다: 절이 쪽을 넘어가면 그대로 잇되, 청크마다 시작 쪽·끝 쪽을 기록한다. 조문이 쪽을 넘는 경우가 흔해서, Newploy 처럼 '쪽이 바뀌면 무조건 끊기'를 하면 SimpleRAG 가 애써 지킨 조문 경계(설계서 결정3)가 다시 깨진다.
  • payload 에 page_from/page_to 를 추가 → RAGSearchBox 출처 표시에 쪽 번호.
  • HWP/DOCX 는 쪽 개념이 렌더링 의존이라 대상에서 뺀다(쪽 정보 없음 = 현행 유지).

비용 — 작음. CHUNKER_VERSION 을 올려 PDF 재색인이 필요하다. Newploy 보고서의 "근거 쪽번호 1쪽 밀림 버그"를 교훈 삼아 0/1 기준을 처음부터 테스트로 고정한다.

3-2. 머리말·꼬리말·쪽번호 제거 규칙으로 대체 · P1

Newploy — 레이아웃 모델이 영역을 '머리말·각주·쪽번호·도장' 등으로 분류하므로 잡음 영역을 따로 다룰 수 있다.

SimpleRAG — 레이아웃 모델이 없다. 하지만 3-1 로 쪽 경계가 생기면 여러 쪽에 똑같이 반복되는 첫·마지막 몇 줄을 찾아 지울 수 있다.

쪽 N 머리 2줄 / 꼬리 2줄 수집
→ 숫자를 # 로 정규화 ("- 12 -" → "- # -", "회사규정 2024.3" 은 그대로)
→ 전체 쪽의 50% 이상에서 반복되는 줄 = 머리말/꼬리말 → 제거

효과 — 128토큰 청크에서 "OO주식회사 내부용 · - 12 -" 같은 10~20토큰이 빠지면 본문 비중이 크게 오른다. BM25 에서 문서명 단어가 모든 청크에 깔려 변별력을 떨어뜨리는 현상도 줄어든다. 제거 전·후 문자 수를 로그로 남기고, 문서의 일정 비율 이상을 지우면 원문으로 되돌리는 안전장치를 둔다(normalize_tables 의 무손실 검사와 같은 철학).

3-3. 목차 페이지 문제 적용 권장 · P2

Newploy 보고서는 "색인표 페이지가 근거로 자주 끌려와 정답 페이지 적중률 약 55%"라고 적었다. 목차는 모든 절 제목을 한곳에 모아 두므로 BM25·dense 모두에서 점수가 높게 나오지만 답이 없다. SimpleRAG 도 같은 위험이 있다 — 특히 structure.py 의 번호절 문법이 목차 줄(1.2 정의 ........ 3)을 제목으로 잡아 목차가 짧은 절 수십 개로 쪼개질 수 있다.

방안 — 점선/가운데점 리더 뒤 쪽번호로 끝나는 줄(…{3,}\s*\d+$)이 연속 N줄 이상이면 목차 블록으로 표시하고 ① 제목 문법 감지 대상에서 빼고 ② 청크로 만들지 않거나 별도 표식을 달아 검색에서 감점한다. 쪽 경계가 있으면 '목차 쪽' 단위로 판정할 수 있어 더 정확하다.

3-4. small-to-big → Parent-Child (부모 = 절) 방식 적용 · 부모 크기 조정 · P2

Newploy 의 실제 구조 — 검색과 LLM 입력의 단위가 다르다.

NewploySimpleRAG 현재
자식 (검색 단위)약 300자 영역 누적 청크128토큰 구조 청크 하나가 둘 다 맡음
부모 (LLM 입력)그 청크가 속한 페이지 전체(고정 크기 아님)
LLM 컨텍스트4096토큰 (앱 설정)2048토큰 (config.GEN_N_CTX)
그 대가TTFT 13초(1.7B) / 28초(4B)—

"작게 찾고 크게 읽힌다"는 방식 자체는 SimpleRAG 에도 맞다. 작은 조각일수록 임베딩이 한 주제에 모여 질문과 정확히 맞고, 큰 조각일수록 LLM 이 앞뒤 문맥(무엇이 3만원인지, 어느 조문의 ①항인지)을 본다. 막는 것은 방식이 아니라 부모 크기와 컨텍스트 예산이다.

생성 컨텍스트 2048
 − 답변 자리   200  (generation.max_tokens)
 − 지시문·질문 ~100
 = 근거 자리 ~1,700토큰

현재    : 128토큰 × 3       ≈   400토큰   여유
페이지  : 수백~2천토큰 × 3  →  초과      gguf_generator 가 뒷부분을 잘라 냄
절      : 128~400토큰 × 3   ≈ 400~1,200  들어감

페이지 부모를 그대로 쓰려면 ① 컨텍스트를 4096 이상으로 키우거나(내장 GPU 에서 prefill 이 길어져 Newploy 와 같은 TTFT 비용) ② 부모를 1개만 넣어야 한다(1위가 틀리면 답도 틀림). 둘 다 SimpleRAG 의 목표와 맞지 않는다. 대신 부모를 페이지보다 작고 의미가 정확한 '절'로 잡는다. SimpleRAG 는 structure.py 가 조문·번호절·부속서 경계를 이미 알고 있어, 페이지(인쇄상의 우연한 경계)보다 나은 부모를 쓸 수 있다 — Newploy 보다 유리한 조건이다.

방안

자식 (검색 · 색인) : 문장 또는 작은 조각  ~32–64토큰   ← 새로 추가
부모 (LLM 입력)    : 절, 또는 현재의 구조 청크  ~128–400토큰  ← 이미 만들고 있음
payload           : 자식마다 parent_id
  • 검색·리랭크는 자식으로 하고, 상위 자식의 부모를 중복 없이 모아 최대 3개를 LLM 에 넣는다(같은 부모의 자식이 여러 개 오르면 한 번만).
  • 부모가 예산을 넘는 큰 절(약 15%)은 지금처럼 내부 분할된 조각을 부모로 쓰고, 넘치면 절 전체 대신 자식 주변 조각만 넣는다.
  • 더 가벼운 1단계로, 새 색인 없이 payload 의 chunk_idx 로 같은 절의 ±1 청크만 붙이는 이웃 청크 확장을 먼저 실험할 수 있다. 같은 방향의 축소판이라, 효과가 보이면 본격 Parent-Child 로 넘어간다.

참고 기록 — 이전에 청크 128/192/256 을 비교했을 때 정답률은 평평하고 TTFT 만 늘었다(structure.py 상단 주석). 그러나 그 실험은 검색 단위와 LLM 입력 단위를 함께 키운 것이라, '작게 찾고 크게 읽히는' 구조의 효과는 아직 검증되지 않았다. 평가는 RAGAS Context Recall·Faithfulness, 정답 근거 적중률, TTFT 를 함께 본다. 128토큰 청크에서 '질문은 이 청크, 답은 다음 청크'로 갈리는 경우(Newploy 상담사례집 사례)가 주 겨냥이다.

3-5. 표 처리 현행 유지 + PDF 만 측정

Newploy 의 표 처리(TATR + 격자 후보 랭커 + 셀 OCR)는 이미지 속 표를 위한 것이다. 디지털 문서의 표에 대해서는 SimpleRAG 가 이미 ① Word 탭 표 → 마크다운 표(눕힌 행/셀 안 줄바꿈 구분, 무손실 검사) ② 표 행 청크에 머리글 재부착(길이 상한) ③ tableflat 의 "머리글: 값" 평문화·밀린 행 보정까지 하고 있어 Newploy 의 "[표] TSV 별도 청크"보다 정교하다.

남는 구멍은 PDF 의 표다. pdfium 텍스트층은 표를 읽기 순서의 글자 나열로 흘려 보내 셀 대응이 끊긴다. 대안은 pdfplumber(MIT) 의 표 검출로 표 영역만 따로 뽑는 것이다(PyMuPDF 는 AGPL 이라 exe 배포 시 라이선스 검토 필요). 단, PDF 표 문서가 질문 실패에 얼마나 기여하는지 먼저 재야 한다(§7).

3-6. 청킹 방식 자체 현행 유지

Newploy 세 경로(300자 영역 누적 / 문단 500자 / 문장)는 모두 구조 기반·겹침 없음이다. SimpleRAG 는

  • 문자 수가 아니라 토큰 예산(한국어 토큰 편차 대응),
  • 제목 문법을 문서마다 하나만 채택(조문 안의 1. 로 과분할 방지) + 부속서 표지 합집합,
  • 절 경계에서는 겹침 없이, 큰 절 내부 분할에만 겹침,
  • 절 경로 접두 [문서 > 제5조(지급 금액)] 로 BM25·dense·생성 모두에 문맥 제공

를 이미 하고 있어 Newploy 보다 앞서 있다. Newploy '지식 폴더' 경로의 제목 경로(heading path) 기록은 SimpleRAG 접두와 같은 발상이라 추가로 가져올 것이 없다. 바꿀 것은 청킹 알고리즘이 아니라 입력에 쪽 경계·잡음 표식을 넣어 주는 것(3-1~3-3)이다.

4OCR 파이프라인 도입 검토

Newploy 는 PaddleOCR 공식 모델(레이아웃 PP-DocLayout_plus-L 129MB, 줄 검출 PP-OCRv5_server_det 88MB) 위에 자체 한국어 인식기(text_ocr_ctc_v3, 암호화)와 자체 표 모델을 얹었다. 런타임으로 PyTorch·PaddlePaddle·ONNX Runtime 을 모두 동봉한다.

관점평가
재사용 가능성불가 한국어 품질의 핵심인 인식기·표 모델은 암호화된 자체 모델. 라이선스 파일도 'placeholder'. 가져다 쓸 수 있는 것은 PaddleOCR 공식 모델뿐이다.
배포 크기큼 Paddle/PyTorch 런타임만 GB 단위. SimpleRAG 는 ONNX Runtime 하나로 임베딩·리랭커를 돌리는 경량 exe 구조다.
속도느림 CPU 전용 PC 에서 쪽당 수 초 수준(레이아웃+검출+인식). 자동 인덱싱이 백그라운드에서 오래 붙잡힌다.
필요성미측정 현재 대상 코퍼스(회사규정·서식 등 디지털 문서) 중 스캔 PDF 비율을 모른다. MpowerClassify 는 이미 쪽마다 _is_scan_page 로 스캔 쪽 수를 센다 — 재료는 있다.

권장: 지금은 도입하지 않고, 필요가 확인되면 '스캔 쪽만 선택 OCR'을 옵션으로. ① 측정으로 스캔 문서·스캔 쪽 비율과 그 문서에 대한 질문 수요를 확인한다 ② 의미 있는 수준이면 ONNX 로 변환된 PP-OCRv5 계열(예: RapidOCR 방식 — 검출+인식만, 레이아웃 모델 생략)을 별도 설치 옵션으로 붙여 기존 ONNX Runtime 을 재사용한다 ③ 텍스트층 PDF 안에 섞인 스캔 쪽(Newploy 보고서의 "글자 30자 미만 17쪽" 사례)만 골라 OCR 한다. 한국어 인식 품질은 공식 모델 기준으로 따로 검증해야 한다 — Newploy 가 인식기를 자체 모델로 갈아 끼운 것 자체가 공식 모델 품질이 부족했다는 신호다.

레이아웃 모델(영역 20종)은 OCR 을 도입하더라도 생략을 권한다. 디지털 문서에서 그 역할(머리말·목차·표 구분)은 3-2·3-3·3-5 의 규칙과 파서가 대신하고, 스캔 쪽은 수가 적을 것이므로 '본문 줄 나열'만으로 충분할 가능성이 높다.

7착수 전 측정 항목

  1. 포맷 분포 — 인덱싱 대상 중 PDF 비율, 그중 텍스트층 PDF / 스캔 PDF / 스캔 쪽이 섞인 PDF 수. (MpowerClassify notes.set_layout 의 쪽 수·스캔 쪽 수 재사용)
  2. 머리말·꼬리말 잡음량 — PDF 문서별로 반복 줄이 차지하는 토큰 비율. 5% 미만이면 P1-2 의 우선순위를 낮춘다.
  3. 목차 오염 — 골든셋 질문 상위 3 근거 중 목차 청크가 차지하는 비율.
  4. 경계 분리 실패 — 오답 사례 중 '정답이 1위 근거의 이웃 청크에 있었던' 비율. 이 값이 이웃 확장(P2-a)의 상한 효과다. 같은 질문에서 '정답이 1위 근거와 같은 절 안에 있었던' 비율은 Parent-Child(P2-b)의 상한 효과다.
  5. 절 길이 분포 (토큰) — 부모를 절로 잡았을 때 상위 3개가 근거 자리 ~1,700토큰에 들어가는 비율. 넘치는 절의 처리 규칙을 정하는 근거다.
  6. PDF 표 실패 — 정답이 PDF 표 안에 있는 질문의 정답률.
  7. 현재 건너뛰는 문서 — cli.py 의 "추출 텍스트 없음" 경로로 빠지는 문서 수(=OCR 수요의 하한).

8위험과 제약

  • 공유 추출기 — csoclassify.extract 는 MpowerClassify 분류 엔진과 공유한다. 쪽 경계·잡음 제거를 그쪽에 넣으면 분류 결과가 바뀔 수 있으므로 SimpleRAG 쪽 래퍼/후처리로 한정한다.
  • 재색인 비용 — CHUNKER_VERSION 상향 시 PDF 전체 재색인. 자동 인덱싱과 겹치지 않게 한 번에 묶는다.
  • 무손실 원칙 — 반복 줄·목차 제거는 '지우는' 변경이다. normalize_tables 처럼 제거량을 측정해 상한을 넘으면 원문으로 되돌린다.
  • 쪽 번호 기준 — 0 기반/1 기반, 표지 유무로 인쇄 쪽번호와 PDF 쪽 순번이 다르다. 표시는 'PDF 쪽 순번'으로 통일하고 테스트로 고정한다(Newploy +1 밀림 버그 교훈).
  • OCR 도입 시 — 배포 크기·인덱싱 시간·한국어 인식 품질 세 가지가 모두 미검증이다. 공개 모델 라이선스(Apache-2.0 계열)는 문제없으나 Newploy 자체 모델은 어떤 형태로도 사용 불가.
