문서 자동 인덱싱 설계서

설정한 폴더에 문서가 추가되거나 수정되면 사람이 simplerag index 를 돌리지 않아도 그 문서만 알아서 인덱스에 반영한다. 수정된 문서는 수정 전 벡터와 정보를 지우고 수정 후 것으로 바꾼다 — 이때 "지우는 순간과 넣는 순간 사이" 에 문서가 사라지거나 두 벌이 섞이지 않게 하는 것이 이 설계의 중심이다.

1목표와 범위

한다

  • 지정 폴더(하위 포함)의 문서 추가·수정·삭제·이름 변경을 알아채 인덱스에 반영
  • 수정 문서는 옛 청크 삭제 + 새 청크 추가를 한 덩어리처럼 처리(중간에 끊겨도 복구)
  • 벡터(Qdrant)·키워드(BM25)·상태 파일(index_state.json) 세 곳을 서로 맞게 유지
  • 프로그램이 꺼져 있던 동안 바뀐 것도 다음 시작 때 따라잡기
  • 질문에 답하는 일을 방해하지 않기 — 질문이 항상 먼저

하지 않는다

  • 청킹 설정이 바뀌었을 때의 전체 재구축 — 지금처럼 --rebuild 를 사람이 돌린다
  • 문서 안의 일부만 바뀐 청크를 골라 고치기 — 문서 단위로 통째 교체한다(§5 이유)
  • 지정 폴더 밖 문서 관리 — 다른 경로로 인덱싱된 문서는 건드리지 않는다
  • 여러 PC 가 한 인덱스를 함께 쓰기
핵심 1 — 새것을 먼저 넣고 옛것을 지운다지금 코드는 "지우고 넣기" 라 그 사이 문서가 비고, 넣기가 실패하면 문서가 사라진다. 순서를 뒤집어, 새 청크를 넣은 뒤 방금 넣은 것 말고 그 문서의 청크를 지운다(§5).
핵심 2 — 인덱스를 쥔 프로세스가 실행한다Qdrant local 은 폴더를 한 프로세스만 연다. 워커가 떠 있으면 워커에게 명령으로, 내려가 있으면 index 명령을 따로 돌린다(§8).
핵심 3 — 이벤트는 힌트, 최종 판단은 대조파일 알림은 놓치거나 겹친다. 알림으로 "어디를 볼지" 만 정하고, 무엇이 바뀌었는지는 상태 파일과 대조해 정한다(§4).
핵심 4 — 지우기는 겁을 내고 한다드라이브가 빠지거나 네트워크가 끊기면 "파일이 전부 사라졌다" 로 보인다. 폴더 자체가 안 보이면 지우지 않고, 한꺼번에 많이 사라지면 멈추고 묻는다(§6).

2지금 인덱싱은 어떻게 도는가 — 코드 분석

simplerag index --dir <폴더> 를 사람이 돌리면 indexer.index_folder() 가 아래 순서로 처리한다. 증분 인덱싱의 뼈대는 이미 있다 — 자동화는 이것을 "누가, 언제 부르나" 와 "빈틈 메우기" 의 문제다.

  1. ①

    대상 나열

    list_files() 가 하위 폴더까지 훑어 확장자(TEXT_EXTS)로 거른다.

  2. ②

    변경 판정 — 파일 지문

    file_fingerprint() = sha1(절대경로 | mtime(초) | 크기). 상태 파일의 지문과 같으면 건너뛴다. 내용을 읽지 않으므로 수천 개도 금방 끝난다.

  3. ③

    문서마다 추출 → 청킹 → 임베딩

    실패하면 그 문서만 건너뛴다(옛 청크는 그대로 남는다 — 좋은 동작).

  4. ④

    옛 청크 삭제 → 새 청크 추가

    store.delete_doc(경로) 로 그 문서의 점을 모두 지운 뒤 store.upsert(). 점 id 는 상태 파일의 next_id 부터 이어 붙인다.

  5. ⑤

    문서 단위 체크포인트

    save_state() 가 임시 파일에 쓰고 os.replace 로 바꿔 끼운다(중단돼도 상태 파일이 깨지지 않는다).

  6. ⑥

    BM25 전체 재구축

    Qdrant 에서 모든 청크를 다시 읽어(_collect_all) BM25 를 처음부터 만든다. 실측 43,058청크 14.3초.

자동화 전에 메워야 할 빈틈

빈틈지금 무슨 일이 생기나이 설계의 처리
지운 파일이 인덱스에 남는다index_folder 는 있는 파일만 본다. 상태 파일에는 있는데 디스크에서 사라진 문서를 찾는 단계가 없다. 지운 문서가 계속 근거로 나온다§6 삭제 대조
수정 때 "지우고 넣기" 사이의 빈틈④ 에서 지운 뒤 넣는 동안 그 문서는 검색에 안 나온다. 넣기가 실패(디스크 가득·예외)하면 문서가 통째로 사라진 채 남는다(상태 파일은 옛 지문이라 다음 실행에 다시 하긴 한다)§5 넣고 지우기 + 세대 표시
BM25 가 옛 점 id 를 가리킨다문서를 지우고 BM25 를 아직 안 만든 사이, BM25 가 없는 id 를 돌려주면 hybrid.py 가 payloads.get(pid) or {} 로 빈 근거를 만든다. 지금도 clear --doc 뒤에 생길 수 있다§7 없는 id 는 버린다
인덱스 폴더 잠금워커(simplerag chat)가 떠 있으면 simplerag index 가 Qdrant 폴더를 열지 못한다. 그래서 지금은 트레이 "모델 내리기" 후에 돌린다§8 쥔 쪽이 실행
파일 지문이 내용과 무관하다저장만 다시 하고 내용이 같아도(백업·동기화 도구가 날짜만 바꿀 때) 다시 임베딩한다. 수동 실행에선 드물어 괜찮았지만 자동이면 잦아진다§4 내용 해시 2차 확인

4변경 감지 — 알림은 힌트, 판단은 대조

두 가지를 함께 쓴다

폴더 알림 (빠름)

  • Windows ReadDirectoryChangesW(하위 폴더 포함). pywin32 의 win32file 로 부른다 — 이미 쓰는 라이브러리라 새 의존성이 없다
  • 지정 폴더마다 스레드 하나. 알림이 오면 "이 경로를 다시 봐라" 만 기록한다
  • 알림 버퍼가 넘치면(대량 복사) Windows 가 "놓쳤다" 를 알려 준다 → 그 폴더 전체 대조로 바꾼다

대조 순찰 (확실함)

  • 폴더를 훑어 상태 파일과 지문을 비교 — 지금 index_folder 의 ②와 같다. 파일 수천 개도 1초 안쪽(내용을 읽지 않는다)
  • 언제: 프로그램 시작 때, 10분마다, 알림이 넘쳤을 때, 폴더 이름이 바뀌었을 때
  • 네트워크 드라이브(UNC)는 알림을 믿기 어려워 순찰만으로도 동작해야 한다

알림은 "무엇을 볼지" 만 정한다. 무엇이 바뀌었는지는 언제나 상태 파일과 대조해서 정한다 — 그래서 알림을 놓치거나 같은 알림이 열 번 와도 결과가 같다.

거를 것 — 저장할 때 잠깐 생기는 파일

모양누가 만드나처리
~$보고서.docxWord·Excel·PowerPoint — "지금 열려 있음" 표시 파일. 확장자가 .docx 라 지금 필터로는 못 거른다이름이 ~$ 로 시작하면 제외
~WRL0001.tmp, 보고서.docx.tmpOffice 가 저장할 때 임시로 쓰고 바꿔 끼운다확장자 필터로 이미 제외
.~lock.보고서.docx#LibreOffice.~lock. 으로 시작하면 제외
숨김·시스템 파일, Thumbs.db, desktop.iniWindows속성으로 제외
복사 중인 큰 파일탐색기 복사아래 "안정화" 로 다 써질 때까지 기다린다

안정화 — 다 써진 파일만 읽는다

  • 잠잠해질 때까지 기다린다: 같은 파일에 알림이 계속 오면 마지막 알림 뒤 5초가 지나야 처리 대상으로 넘긴다. Word 저장 한 번에도 알림이 여러 개 온다
  • 크기·수정 시각이 두 번 연속 같아야 한다(1초 간격). 복사 중이면 계속 커진다
  • 읽기로 열려야 한다. 공유 위반으로 못 열면 5초 → 15초 → 60초 간격으로 다시 시도하고, 그래도 안 되면 다음 순찰로 미룬다
  • 많이 쏟아지면(폴더째 복사) 모아서 한 묶음으로 넘긴다 — BM25 재구축을 한 번만 하기 위해서다

AI3 에서 실측으로 알게 된 것

  • 폴더 핸들은 폴더를 "따라간다". 지켜보는 폴더의 이름을 바꾸거나 옮기면, 핸들은 옮겨 간 폴더를 계속 지켜보며 오류도 내지 않는다. 그대로 두면 옛 경로로 엉뚱하게 알리고 폴더가 없어진 것도 모른다 → 1초마다 그 자리에 폴더가 있는지 직접 보고, 없으면 핸들을 닫고 다시 연결을 시도한다. 돌아오면 전체 대조
  • 감시 중에도 사용자가 폴더 이름을 바꿀 수 있다(FILE_SHARE_DELETE). 감시 때문에 폴더가 "사용 중" 으로 잠기지 않는다
  • 알림 버퍼 64KB 로 3,000개를 한꺼번에 만들어도 넘치지 않았다 — 3,000개 모두 알림으로 왔다. 넘침 처리는 버퍼를 줄여 확인했다(넘치는지는 읽는 속도에 달려 들쭉날쭉해, 판단 부분을 떼어 직접 시험한다)
  • Word·Excel·PowerPoint 실제 저장: 저장 한 번에 묶음 한 번, ~$ 표시 파일·~WRL….tmp 임시 파일 때문에 엉뚱한 추가·삭제가 오지 않는다. 문서를 열어 둔 채 다시 저장해도 온다(Office 는 읽기 공유를 허락한다)
  • 한글(HWP)은 자동화하면 보안 확인 창이 사용자 화면에 뜰 수 있어 이번 확인에서 뺐다 — 저장 방식이 같다면 같은 규칙으로 걸러진다. AI4 에서 손으로 한 번 저장해 본다

내용 해시로 한 번 더 확인

지문(경로·시각·크기)이 달라도 내용이 같으면 다시 임베딩하지 않는다. 지문이 다른 파일만 통째로 읽어 sha1 을 내고, 상태 파일의 content_hash 와 같으면 지문만 새로 적는다. 읽는 비용은 바뀐 파일에만 들고, 임베딩(문서당 수 초)을 아낀다. 이름 바꾸기(§6)에서도 이 해시를 쓴다.

5수정 문서 교체 — 옛것 지우고 새것 넣기를 안전하게

이 기능의 핵심 요구다. "수정 전 벡터와 정보를 지우고, 수정 후 벡터와 정보를 넣는다" 를 그대로 순서대로 하면 그 사이에 문서가 비고, 넣기가 실패하면 문서가 사라진다. 그래서 순서를 뒤집는다.

왜 문서 단위로 통째 바꾸나 (바뀐 청크만 고치지 않는 이유)

문단 하나만 고쳐도 그 뒤 청크의 경계가 모두 밀린다(청크는 토큰 수로 자르고 겹침이 있다). 청크 번호로 짝을 맞출 수 없고, "같은 내용 청크는 벡터 재사용" 을 해도 한 문서가 보통 수~수십 청크라 임베딩 절약은 1초 안팎이다. 복잡도에 비해 얻는 게 없다.

세대 표시 — 청크마다 "어느 버전의 문서에서 나왔나" 를 단다

Qdrant 의 각 점(payload)에 gen 필드를 추가한다. 값은 그 버전 문서의 지문이다. 그러면 "이 문서의 청크 가운데 지금 세대가 아닌 것만 지워라" 를 한 번의 조건 삭제로 할 수 있다.

# 지금 payload
{text, doc_path, doc_name, folder, chunk_idx, mtime}
# 추가
{..., gen: "bfd3c35d…"   # 이 청크를 만든 문서 버전의 지문
      content_hash: "…" }  # 문서 내용 해시(이름 바꾸기 재사용용, §6)

교체 순서

  1. 1

    새 버전을 만든다 — 인덱스는 아직 안 건드린다

    추출 → 청킹 → 임베딩. 여기서 실패하면 옛 버전을 그대로 둔다(비밀번호 걸린 파일, 저장 도중 깨진 파일). 실패를 상태 파일에 적어 같은 지문으로는 다시 시도하지 않는다.

  2. 2

    새 점 id 를 예약하고 상태 파일에 먼저 적는다

    next_id 를 청크 수만큼 올려 저장한다. 3 에서 죽어도 다음 실행이 같은 id 를 다른 문서에 주지 않는다.

  3. 3

    새 청크를 넣는다 (gen = 새 지문)

    이 순간엔 옛것과 새것이 함께 있다. 워커 안에서는 질문과 번갈아 한 줄씩 처리하므로(§8) 이 순간에 검색이 끼어들지 않는다.

  4. 4

    옛 청크를 지운다

    조건: doc_path == 이 문서 그리고 id 가 3 에서 방금 넣은 목록에 없음. "방금 넣은 것 말고 이 문서의 나머지 전부" 라서, 옛 버전은 물론 예전에 넣다 만 찌꺼기와 gen 필드가 없는 옛 인덱스의 청크까지 한 번에 지워진다.

  5. 5

    상태 파일을 새 버전으로 바꾼다

    {fingerprint, content_hash, chunks, ids 범위, gen} 을 적고 원자적으로 교체.

  6. 6

    BM25 에 "다시 만들어야 함" 표시

    바로 만들지 않는다 — 묶음이 끝나고 한가할 때 한 번(§7).

어디서 끊겨도 다음 실행이 바로잡는다

끊긴 곳남은 모습다음 실행에서
1 도중옛 버전 그대로. 상태 파일도 옛 지문지문이 달라 다시 처리 — 정상
2 뒤, 3 전id 만 예약됨(빈 번호가 생길 뿐)다시 처리 — 정상
3 뒤, 4 전옛것 + 새것 두 벌. 상태 파일은 옛 지문지문이 달라 다시 처리 → 새 id 로 또 넣고 → 방금 넣은 것 말고 전부 삭제. 옛것과 지난번에 넣다 만 새것이 함께 정리된다
4 뒤, 5 전새것만. 상태 파일은 옛 지문다시 처리(같은 결과를 한 번 더 만든다 — 낭비지만 정확)
5 뒤, 6 전벡터는 새것, BM25 는 옛것§7 — 시작 시 BM25 가 상태 파일보다 오래됐으면 다시 만든다

왜 세대(gen) 대신 id 목록으로 지우나: 3·4 사이에서 끊긴 뒤 다시 돌리면 같은 버전을 두 번 넣게 된다. 두 벌 모두 세대가 같아서 "세대가 다른 것 지우기" 로는 먼저 넣은 벌이 남는다. id 목록은 이번에 넣은 것만 정확히 가리킨다. gen 은 진단과 고아 청소(아래)에 쓴다.

Qdrant 필터로 표현: must=[doc_path == P], must_not=[HasId(이번 id 목록)]. 문서 하나가 수백 청크여도 목록 크기는 문제되지 않는다.

시작할 때 한 번 — 고아 청소

상태 파일에 없는 doc_path 의 점, 상태 파일의 id 범위 밖에 있는 점을 찾아 지운다. 중간에 죽어서 남은 두 벌을 여기서 정리한다. 전체 점을 훑어야 하므로(scroll, payload 는 doc_path 만) 시작 때와 수동 명령에서만 한다.

지우기 안전 확인 — 인덱스를 통째로 날리지 않게

  • 지정 폴더 자체가 안 보이면 아무것도 지우지 않는다. USB·외장 드라이브가 빠졌거나, 네트워크 드라이브가 끊겼거나, 드라이브 문자가 바뀐 것이다. 파일이 사라진 게 아니다
  • 한 번에 많이 사라지면 멈추고 묻는다. 그 폴더 문서의 30% 이상(단 5건 이상일 때) 또는 50건 이상이 한꺼번에 사라지면 지우지 않고 트레이 알림으로 알린다("문서 120건이 사라졌습니다 — 인덱스에서 뺄까요?"). 사용자가 트레이 메뉴에서 확인해야 지운다
  • 지정 폴더 아래 문서만 삭제 후보가 된다. 상태 파일에는 다른 경로로 인덱싱한 문서가 섞여 있을 수 있다 — 그것은 절대 건드리지 않는다
  • 경로 비교는 대소문자를 무시한다(os.path.normcase). 상태 파일의 키는 인덱싱 당시 표기 그대로라 알림의 표기와 다를 수 있다

7BM25 반영

BM25 는 전체 문서 통계(IDF·평균 길이)로 점수를 내므로 문서 하나만 끼워 넣을 수 없다. 지금처럼 통째로 다시 만든다. 대신 언제 만들지와, 만들기 전 빈틈을 다룬다.

문제처리
재구축이 무겁다(43,058청크 14.3초, 지금 sample 498청크는 1초 안쪽 예상)묶음이 끝나고, 질문이 10초 이상 없을 때 한 번 만든다. 늦어도 5분 안에는 만든다
만들기 전 BM25 가 지워진 점 id 를 돌려준다hybrid.py: payload 를 못 찾은 id 는 버린다(지금은 빈 근거가 된다). 이것은 자동 인덱싱과 상관없이 먼저 고칠 버그다
만들기 전 새 청크는 BM25 에 없다그동안은 벡터 검색으로만 찾힌다. 수 초~수 분의 일이라 허용한다
워커 안에서 만들면 그동안 질문이 기다린다1단계: 한가할 때만 만들므로 대개 문제없다. 2단계(청크 수만 개 이상): 점 읽기는 워커 스레드에서, 계산은 별도 스레드에서 하고 다 되면 바꿔 끼운다
워커가 들고 있는 BM25 는 메모리에 있다Bm25Index.build() 가 같은 객체의 내용을 바꾸므로, 워커의 검색기가 들고 있는 그 객체가 곧바로 새 BM25 가 된다 — 따로 바꿔 끼울 것이 없다(AI2 에서 확인)
BM25 파일이 상태 파일보다 오래됐다(§5 의 5·6 사이에서 끊김)상태 파일에 bm25_built_at 과 index_changed_at 을 적는다. 시작할 때 앞이 뒤보다 이르면 다시 만든다

8누가 실행하나 — 인덱스 폴더 잠금

Qdrant local 모드는 인덱스 폴더를 한 프로세스만 열 수 있다. 워커가 떠 있는 동안 simplerag index 를 돌리면 열지 못한다 (그래서 지금 트레이에 "모델 내리기" 가 있다). 자동 인덱싱은 그 순간 인덱스를 쥔 쪽이 실행하게 한다.

워커가 떠 있을 때 — 워커에게 명령

  • RAGSearchBox 가 워커 stdin 에 /index-doc <경로> 같은 명령을 보낸다(§9)
  • 워커의 입력 루프는 한 줄씩 차례로 처리한다 → 질문과 인덱싱이 저절로 번갈아 돌고, 동시에 인덱스를 만지는 일이 없다. 잠금·스레드 설계가 필요 없다
  • 이미 올려 둔 임베딩 모델·Qdrant·BM25 를 그대로 쓴다 — 추가 메모리 없음

워커가 내려가 있을 때 — index 명령

  • simplerag.exe index --dir <폴더> 를 따로 띄운다. 생성 모델(2.5GB)은 올리지 않는다 — 지금도 index 는 임베딩만 쓴다
  • 일부러 워커를 깨우지 않는다. 60분 쉬어 내려간 워커를 파일 하나 때문에 다시 올리면 "쉬면 메모리 돌려주기" 가 무너진다
  • 도는 동안 질문이 오면: 워커를 띄우지 않고 기다렸다가(상태 "인덱스 갱신 중 — 곧 답합니다") 끝나면 띄운다

질문이 항상 먼저

  • RAGSearchBox 의 워커 관리(rag_worker.py)는 지금 "보낼 질문 한 칸" 만 있다. 이것을 두 줄짜리 대기열로 바꾼다 — 질문 줄, 인덱싱 줄. 워커가 "질문> " 을 띄울 때마다 질문 줄을 먼저 비운다
  • 인덱싱은 한 번에 문서 하나만 보낸다. 문서 하나는 보통 1~2초(청크 수십 개 × 초당 47~69청크), 큰 문서도 수 초다. 그래서 질문이 들어와도 길어야 그만큼만 기다린다
  • 답변이 흘러나오는 중에는 인덱싱 명령을 보내지 않는다(생성과 임베딩이 CPU 를 다툰다)

처음 켜는 폴더 — 규모가 크면 묻는다

지정 폴더를 새로 추가하면 대조 결과 "전부 추가" 가 된다. 문서 371건 기준 전체 인덱싱은 19분이 걸렸다. 추가 대상이 50건을 넘으면 바로 시작하지 않고 트레이 알림으로 알린 뒤, 트레이 메뉴 "지금 인덱싱" 을 눌러야 시작한다. 시작하면 질문 사이사이 문서 하나씩 처리하므로 그동안도 질문은 된다.

9워커 명령 — stdin 으로 주고받기

지금 워커 입력 루프(cli.cmd_chat)에는 /help·/topk·/status 같은 슬래시 명령이 이미 있다. 같은 자리에 넣는다. 결과는 한 줄짜리 JSON으로 내보내, RAGSearchBox 가 답변 출력과 헷갈리지 않게 한다.

# RAGSearchBox → 워커
/index-doc {"path": "D:\\분류함\\규정.docx"}   # 추가·수정(§5 교체). 경로만 써도 된다
/remove-doc {"path": "…"}                  # 삭제 — 파일이 실제로 없을 때만
/bm25                                       # BM25 다시 만들기 + 고아 청소
/index-plan {"path": "D:\\분류함"}          # 폴더와 인덱스 대조 — 할 일 목록(바꾸지 않음)

# 워커 → RAGSearchBox  (한 줄, 그 뒤 평소처럼 "질문> ")
@index {"op":"index-doc","ok":true,"path":"…","result":"modified","chunks":7,"ms":64}
#   result = added | modified | same(내용 같음) | unchanged(지문 같음) | failed_before
@index {"op":"index-doc","ok":false,"path":"…","result":"modified","why":"추출 실패 …","kept_old":true,"ms":…}
@index {"op":"bm25","ok":true,"chunks":499,"orphans":0,"build_s":0.07,"ms":71}
@index {"op":"index-plan","ok":true,"add":[…],"modify":[…],"remove":[…],"delete_blocked":"","bm25_stale":false,"ms":6}
  • [AI2 에서 바꿈] 경로는 ASCII JSON({"path": …})으로 보낸다. 워커 stdin 은 cp949 라 이모지 같은 글자가 깨지는데, JSON 은 그런 글자를 \uXXXX 로 적으므로 인코딩 문제가 아예 없다. 처음 생각한 "경로 안의 \u 를 되돌리기" 는 D:\users 같은 평범한 경로와 헷갈려 버렸다. 사람이 칠 때를 위해 경로를 그대로 써도 받는다
  • [AI2 에서 바꿈] 처음 적은 /index-state 대신 /index-plan 을 두었다. 대조 규칙(추가·수정·삭제·대량 삭제 멈춤)을 RAGSearchBox 에 한 벌 더 만들지 않고, index 명령과 같은 indexer.plan_changes() 를 쓰게 하려는 것이다
  • 줄 앞의 @index 로 RAGSearchBox 의 해석기(chat_parser)가 답변과 구분한다. 이 줄은 답변 칸에 나오지 않는다
  • 명령의 몸통은 indexer.py 에 새로 만드는 sync_doc() · remove_doc() 이다. index --dir 도 이 두 함수를 쓰게 바꿔, 수동 실행과 자동 실행이 같은 코드로 돈다

12오류·경계 사례

상황처리

워커가 인덱싱 도중 죽음§5 표대로 다음 실행이 바로잡는다. RAGSearchBox 는 그 문서를 대기열에 다시 넣는다
사람이 simplerag index 를 직접 돌리는 중잠금 때문에 워커가 못 뜨는 것은 지금과 같다. 자동 인덱싱은 잠금 오류를 보면 1분 뒤 다시 시도
드라이브 분리·네트워크 끊김폴더가 안 보이면 삭제 대조를 건너뛴다(§6). 알림 스레드는 다시 연결을 시도한다
수백 개 한꺼번에 복사알림 버퍼 넘침 → 대조 순찰. 50건 넘으면 묻는다
cp949 로 못 쓰는 문자가 든 파일명경로를 ASCII JSON 으로 보낸다(§9). 이모지가 든 파일명으로 추가·삭제 확인(AI2)
Qdrant 삭제 후 디스크local 모드는 sqlite 라 지운 자리를 다시 쓴다. 파일이 줄지 않는 것은 정상 — 필요하면 --rebuild
같은 문서가 지정 폴더 두 곳에 걸침(폴더 A 와 그 하위 B 를 둘 다 지정)경로가 같으면 한 문서다. 폴더 목록에서 하위 폴더는 합친다

  • A1
    감지는 RAGSearchBox, 실행은 인덱스를 쥔 쪽

    대안: ① 워커 안에서 감시 — 워커가 쉬어 내려가면 못 본다. ② 독립 감시 프로그램 — 잠금 때문에 결국 워커와 조율해야 해 한 단계가 더 생긴다.

    결정: 이 설계대로. SimpleRAG 만 쓰는 사람을 위한 simplerag watch 는 나중에 같은 함수로 만들 수 있다.

  • A2
    기본으로 켤 것인가

    켜 두면 저장하는 대로 반영된다. 끄면 지금과 같다.

    결정: 켬(Enabled = 1). 단 50건 넘는 첫 인덱싱과 대량 삭제는 묻는다.

  • A3

    바로 하면 simplerag index 가 잠깐 뜬다(임베딩 모델만, 수 초). 미루면 첫 질문 전에 밀린 것을 처리해야 해서 첫 답이 늦어진다.

    결정: 바로 한다.

  • A4
    이름 변경 때 벡터 재사용(2단계)을 할 것인가

    구조 청킹은 청크 앞머리에 파일명(제목)을 넣으므로, 이름이 바뀌면 청크 본문도 달라진다. 재사용하면 검색에 옛 이름이 남는다.

  • A5
