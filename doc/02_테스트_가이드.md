# SimpleRAG 테스트 가이드

내 문서로 **문서 → 인덱싱 → 검색 → 답변** 전 과정을 확인하는 방법.

> 이 가이드의 핵심 원칙: **한 번에 다 돌리지 말고 단계마다 끊어서 확인한다.**
> RAG는 실패 지점이 4곳(추출·청킹·검색·생성)이라, 끝에서 "답이 이상하다"만
> 보면 어디가 문제인지 알 수 없다. 각 단계를 따로 볼 수 있는 명령이 있다.

모든 명령은 프로젝트 루트(`D:\Project\SimpleRAG`)에서 실행한다.

> **exe 로 실행하는 경우**: 명령·옵션은 완전히 같다. 아래의
> `.venv\Scripts\python.exe src\simplerag\cli.py` 를 `simplerag.exe` 로 바꿔 읽으면 된다.
> 빌드·배포는 [03_exe_배포_가이드.md](03_exe_배포_가이드.md) 참조.

## 0단계 — 환경 점검 (최초 1회)

```
.venv\Scripts\python.exe bench\sysinfo.py
```

CPU·RAM·SIMD 지원을 확인한다. 이 프로젝트의 성능 수치는 **i5-1340P / 16GB /
GPU 없음** 기준이므로, 사양이 다르면 아래 기준값도 비례해 달라진다.

> **내장 GPU(iGPU)가 있는 PC** 는 첫 질문 때 CPU/iGPU 속도를 재서 빠른 쪽을 쓴다
> (약 15~40초, 1회). 무엇을 골랐는지는 `cli.py backend` 로 확인한다. 아래 CPU
> 기준값과 비교하려면 `set SIMPLERAG_GEN_BACKEND=cpu` 로 CPU 에 고정한다.

이어서 구성요소가 전부 올라오는지 본다.

```
.venv\Scripts\python.exe src\simplerag\cli.py warmup
```

```
  embedder  1109ms
  qdrant    2279ms
  bm25       104ms
  llm       1122ms
  합계      4675ms (병렬 총합)
```

- `❌` 가 뜨면 그 구성요소부터 해결한다.
- 지금 버전은 첫 줄에 `생성 iGPU(Vulkan) / 리랭킹 켬` 처럼 고른 백엔드가 나오고, 리랭킹이
  켜지면 `reranker` 줄, 예열 생성 시간인 `llm_warm` 줄이 더해진다([doc/03 §5](03_exe_배포_가이드.md)).
- `bm25  — 캐시 없음` 은 정상이다(인덱싱 전이라 아직 없음).
- `llm ❌ 생성 모델 없음` → `py bench\download_models.py` 실행.

## 1단계 — 문서 준비

### 지원 포맷

| 그룹 | 확장자 | 비고 |
|---|---|---|
| 오피스(신) | `.docx` `.xlsx` `.pptx` | OOXML 직접 파싱 |
| 오피스(구) | `.doc` `.xls` `.ppt` | OLE 전용 파서 — **표 구조 보존됨** |
| 한글 | `.hwp` `.hwpx` | |
| PDF | `.pdf` | **텍스트층이 있는 것만** |
| 텍스트 | `.txt` `.md` `.html` `.py` `.ipynb` | |

`.jpg` `.png` `.zip` 등은 자동으로 건너뛴다.

### ⚠️ 안 되는 것

- **스캔 이미지 PDF** — 텍스트층이 없어 추출 불가. OCR 없이는 원리상 불가능하다.
  실제 코퍼스 375건 중 9건이 여기 해당했다(계약서·설치확인서·제안서).
- **암호 걸린 문서**
- **이미지 안의 글자** (표를 그림으로 붙여넣은 경우 포함)

### 폴더 구성 조언

- 하위 폴더는 자동으로 재귀 탐색한다.
- **같은 문서를 여러 폴더에 두면 검색 결과가 중복으로 잠식된다.**
  실제로 `2.회사규정\경조사지원규정.doc` 과 `#외부유출금지_회사규정#\경조사지원규정.doc`
  이 둘 다 있어 top-3 중 2칸을 같은 내용이 차지하는 일이 있었다.
  테스트 목적이면 중복을 미리 정리하는 편이 결과 해석에 좋다.

## 2단계 — 추출 확인 (인덱싱 전에 반드시)

인덱싱은 오래 걸린다(4만 청크 기준 25분). **새 문서군을 넣기 전에 대표 파일
몇 개로 추출이 되는지 먼저 본다.**

```
.venv\Scripts\python.exe src\simplerag\cli.py extract "D:\문서\규정.doc"
```

출력 예:

```
파일    : 03.경조사지원규정_12.01.01.doc
문자수  : 1,077
표 복원 : 16행
청크수  : 5개 (128토큰 기준)
------------------------------------------------------------------
2. 경조사 지원기준
| 본인 결혼 | 5 | 500,000 |
| 자녀 결혼 | 1 | 300,000 |
...
```

### 무엇을 봐야 하나

| 확인 항목 | 정상 | 이상 |
|---|---|---|
| **문자수** | 문서 분량에 맞는 값 | `0` → 스캔 PDF 등 추출 불가 |
| **청크수** | 문자수 ÷ 약 300 | 지나치게 적으면 토크나이저 절단 의심 |
| **표 복원** | 표 있는 문서면 `N행` | 표가 있는데 `없음` → 아래 참조 |
| **본문** | 읽을 수 있는 텍스트 | 깨진 글자 → 인코딩 문제 |

**표가 복원되지 않는 경우**는 원본 표 구조에 따라 발생한다. 셀 병합이
불규칙하거나 한 셀에 값 두 개가 붙어 있으면(`1,000,000    500,000`) 열 정렬이
어긋나 일부만 복원된다. 이 경우 해당 표에 대한 질문은 정확도가 떨어진다.

여러 파일을 한꺼번에 점검하려면:

```
.venv\Scripts\python.exe bench\bench_extract.py --dir "D:\문서"
```

## 3단계 — 인덱싱

```
.venv\Scripts\python.exe src\simplerag\cli.py index --dir "D:\문서"
```

### 로그 읽는 법

```
확장자 제외 4건(이미지/압축 등)
문서 371건 중 371건 처리 대상
  [1/371] 03.경조사지원규정.doc          5청크  (8.5 문서/s, 남은시간 43s)  표16행
  [2/371] 취업규칙.doc                 106청크  (3.1 문서/s, 남은시간 118s)
  ...
BM25 인덱스 구축 중...
BM25 인덱스 43,058건 구축 14.3s
  ❌ 채널사협력계약.pdf — ExtractError: 하이브리드 전엔진 실패(pdf:empty)
문서 371건 / 변경 371건 / 청크 43,058개 / 1503.9s
실패 9건
```

| 항목 | 의미 |
|---|---|
| `표N행` | 표가 마크다운으로 복원됨 |
| `남은시간` | **최근 구간 이동평균** 기준. 발열로 처리량이 떨어지므로 초반 추정보다 늘어난다 |
| `❌` | 실패 문서. **인덱싱은 계속 진행된다**(문서 단위로 격리) |
| `⚠️ 청크 N개는 문자수 대비 비정상적으로 적습니다` | 토크나이저 절단 회귀 경고 |

### 소요 시간 예상

| 문서 규모 | 청크 | 소요 |
|---:|---:|---:|
| 18건 | 385 | 약 9초 |
| 371건 | 43,058 | 약 25분 |

임베딩 처리량은 발열로 **69 → 47 chunk/s** 까지 떨어진다. 긴 작업은 하단값
기준으로 잡을 것. 노트북이라면 전원을 연결하고 통풍을 확보한다.

### 증분 갱신

같은 명령을 다시 실행하면 **변경된 문서만** 처리한다.

```
문서 371건 중 0건 처리 대상
문서 371건 / 변경 0건 / 청크 0개 / 0.0s
```

변경 감지는 `(경로, 수정시각, 크기)` 해시로 한다. 내용은 같은데 다시
저장한 파일은 변경으로 잡힌다.

**전체를 다시 만들려면** `--rebuild` 를 붙인다. 추출기나 청킹 설정을 바꿨다면
반드시 `--rebuild` 해야 한다(증분은 옛 설정으로 만든 청크를 그대로 둔다).

### 인덱스 삭제

깨끗한 상태에서 다시 시작하거나, 다른 문서 폴더로 바꿔 테스트할 때 쓴다.

```
.venv\Scripts\python.exe src\simplerag\cli.py clear
```

```
데이터 루트: D:\Project\SimpleRAG
문서 371건 / 다음 항목을 삭제합니다:
  벡터 인덱스          190.5 MB  qdrant_data
  BM25 캐시            22.7 MB  bm25_index.npz
  증분 상태              0.1 MB  index_state.json

⚠️ 되돌릴 수 없습니다. 다시 인덱싱하려면 문서 수에 따라 수십 분이 걸립니다.
정말 삭제할까요? [y/N]
```

| 사용법 | 설명 |
|---|---|
| `clear` | 전체 삭제. 무엇을 지우는지 보여주고 확인을 받는다 |
| `clear -y` | 확인 없이 삭제 (배치 스크립트용) |
| `clear --doc <경로>` | **그 문서의 청크만** 제거 |

**세 파일은 한 묶음으로 지운다.** 하나만 남기면 상태가 어긋난다 — 특히
`index_state.json` 만 남기면 증분 갱신이 "이미 처리함"으로 착각해
재인덱싱을 통째로 건너뛴다.

#### `--doc` — 문서 1건만 빼기

전체 재인덱싱 없이 특정 문서를 인덱스에서 제외한다.

```
.venv\Scripts\python.exe src\simplerag\cli.py clear --doc "D:\문서\폐기된규정.doc"
```

⚠️ **BM25 인덱스는 갱신되지 않는다.** 전체 코퍼스로 한 번에 만들어지기
때문이다. 검색에서 그 문서를 완전히 빼려면 이후 `index --dir <폴더>` 를
한 번 돌려야 한다(명령이 안내 문구를 출력한다).

> `--rebuild` 와 `clear` 의 차이: `--rebuild` 는 지우고 **바로 다시 만든다**.
> `clear` 는 지우기만 한다 — 다른 폴더로 대상을 바꾸거나, 디스크를 비우거나,
> 문제 재현을 위해 빈 상태에서 시작할 때 쓴다.

## 5단계 — 검색 테스트 (생성 없이)

**답이 이상할 때 원인이 검색인지 생성인지 가르는 가장 중요한 단계다.**
생성 모델을 올리지 않아 빠르다.

```
.venv\Scripts\python.exe src\simplerag\cli.py search "리프레시 휴가비는 얼마인가요?"
```

```
질의: 리프레시 휴가비는 얼마인가요?
검색 118ms (임베딩 6 + dense 81 + BM25 1 + 융합 0)

[1] 42.리프레시 휴가 지원 지침_230406.docx  (폴더: 2.회사규정)
    제4조(신청 내용) 1. 임직원은 3년에 1회 ...

[2] 1_Agentic_RAG_기초.ipynb  (폴더: 교육)
    ...
```

### 무엇을 봐야 하나

1. **정답이 든 문서가 top-3 안에 있는가** — 없으면 검색 문제다. 생성 모델을
   바꿔도 해결되지 않는다.
2. **정답 *문장* 이 청크 안에 실제로 있는가** — 문서만 맞고 엉뚱한 부분이
   왔을 수 있다. 이게 실패 원인의 상당수를 차지한다.
3. **단계별 지연** — dense 가 300ms 를 넘으면 Qdrant 서버 모드를 검토한다.
   BM25 가 수십 ms 를 넘으면 인덱스가 잘못 만들어진 것이다(정상은 1ms 내외).
4. **중복 문서가 top-3 을 잠식하는가** — 같은 문서가 2칸 이상 차지하면
   실질 근거가 1건뿐이다.

> **첫 질의는 느리다.** 캐시가 차기 전이라 dense 가 250~350ms 로 나온다.
> 두세 번 반복한 뒤의 값을 기준으로 볼 것.

### top-k 조정

```
.venv\Scripts\python.exe src\simplerag\cli.py search "질문" --top-k 10
```

top-10 에는 있는데 top-3 에 없다면 **순위 문제**다. 질의 표현을 바꾸거나
청크 크기 조정을 검토한다. top-10 에도 없으면 **인덱싱 문제**다.

## 6단계 — 질의 테스트 (전체 파이프라인)

### 여러 개 물어볼 때는 `chat` (권장)

```
.venv\Scripts\python.exe src\simplerag\cli.py chat
```

```
모델 적재 중...
준비 완료 (4.4초) — 43,152청크 / Qwen3-0.6B-Q4_K_M.gguf
질문을 입력하세요.  종료: exit 또는 Ctrl+D   도움말: /help

질문> 리프레시 휴가비는 얼마인가요?
...
질문> /topk 5
  근거 개수를 5개로 변경했습니다.

질문> 육아휴직 기간은 최대 얼마인가요?
...
질문> exit
```

**`ask` 는 질문 하나마다 모델을 새로 올린다(약 4.5초).** 테스트로 여러 개를
물어볼 때는 반드시 `chat` 을 쓴다 — 예열이 1회로 끝나고, 두 번째 질문부터는
바로 검색·생성으로 들어간다.

| 대화형 명령 | 설명 |
|---|---|
| `/topk N` | 근거 개수 변경 — 모델을 다시 올리지 않는다 |
| `/status` | 인덱스 상태 |
| `/help` | 도움말 |
| `exit` / `Ctrl+D` | 종료 |

답변 생성 중 `Ctrl+C` 는 **그 답변만 취소**하고 프롬프트로 돌아온다(앱은 안 죽는다).

### 질문 하나만 확인할 때는 `ask`

```
.venv\Scripts\python.exe src\simplerag\cli.py ask "리프레시 휴가비는 얼마인가요?"
```

출력은 세 구역이다.

```
── 근거 3건 (118ms) ─────────────────────      ← ① 검색 결과 (즉시)
  [1] 42.리프레시 휴가 지원 지침.docx
      제5조(지급 금액) 리프레시 휴가비는 100만원으로 한다 ...

── 답변 (AI 요약 — 위 근거로 확인하세요) ──      ← ② 생성 (스트리밍)
리프레시 휴가비는 100만원으로, 3년에 한 번 신청할 수 있다. [1]

── 소요 ─────────────────────────────────      ← ③ 성능
  검색 118ms (임베딩 6 + dense 81 + BM25 1)
  첫 글자 2.53s / 완료 4.37s
  인용 근거: [1]
```

### 읽는 순서가 중요하다

**① 근거를 먼저 읽고, ② 답변이 그 근거와 맞는지 확인한다.**
생성 모델의 정답률은 76%다 — 약 4분의 1은 틀린다. 근거가 화면에 함께 있는
이유가 이것이다. 답변만 믿으면 안 된다.

### 정밀 모드

```
.venv\Scripts\python.exe src\simplerag\cli.py ask "질문" --model qwen3-1.7b-q4
```

1.7B 는 45문항 평가에서 0.6B 와 **정답률이 같았다**(76%, McNemar p=1.000).
TTFT 만 2.6배 느려지므로 상시 사용은 권하지 않는다. 특정 질문에서
0.6B 가 계속 틀릴 때 대조용으로 써 본다.

## 7단계 — 내 문서로 품질 평가셋 만들기

한두 개 질문으로는 성능을 알 수 없다. **20문항 이상**을 만들어야 의미 있는
숫자가 나온다.

### 7-1. 문항 작성

`bench\eval_cases.py` 를 열어 `CASES` 를 자기 문서에 맞게 바꾼다.

```python
CASES = [
    {"cat": "복리후생",                              # 카테고리(원인 분석용)
     "q": "리프레시 휴가비는 얼마인가요?",              # 질문
     "src": ["리프레시"],                            # 정답 문서 파일명 조각(복수 가능)
     "must": ["100만원"],                           # 답변에 있어야 할 표현
     "must_not": ["200만원", "20만원"]},             # 나오면 틀린 것으로 보는 표현
]
```

### 7-2. 문항 작성 규칙 (중요)

이 프로젝트에서 채점 규칙 때문에 **네 번** 잘못된 결론에 도달할 뻔했다.
같은 실수를 피하려면:

| 규칙 | 이유 |
|---|---|
| **문서를 직접 읽고 확인한 사실만** 쓴다 | 상식으로 답할 수 있는 질문은 검색 없이도 맞아서 RAG 평가가 안 된다 |
| **질문이 요구하는 것과 `must` 를 일치**시킨다 | "언제 지급되나요?"라고 묻고 `must` 에 금액을 넣으면 맞는 답이 오답 처리된다 |
| `must_not` 은 **"나오면 무조건 틀림"일 때만** | 원문에 그 숫자가 다른 맥락으로 있으면 정답이 오답이 된다. 실제로 "5년에 상환"을 맞히고 "3년 이내 재신청 제한"을 인용했다가 오답 처리된 적이 있다 |
| 같은 뜻의 다른 표기는 `\|` 로 허용 | `"2백만원\|200만원"` |
| **중복 문서가 있으면 `src` 를 복수로** | 어느 쪽이 검색돼도 정답이어야 한다 |
| **카테고리를 나눈다** | 집계 숫자만 보면 원인을 못 찾는다. 카테고리별로 쪼개야 "표 문서만 못 한다" 같은 게 보인다 |

### 7-3. 검색만 평가 (빠름, LLM 미사용)

```
.venv\Scripts\python.exe bench\eval_large.py --stage retrieval
```

```
  === 검색 (n=45) ===
  Recall@1 : 91%
  Recall@3 : 96%
  지연     : 중앙값 118ms / 최대 256ms

  카테고리별 Recall@3:
    경조사     4문항    75%
    근로조건   8문항   100%
```

Recall@3 이 낮은 카테고리가 **검색 단계에서 이미 실패**하는 영역이다.
여기는 생성 모델을 바꿔도 개선되지 않는다.

### 7-4. 답변까지 평가

```
.venv\Scripts\python.exe bench\eval_large.py --stage answer --model qwen3-0.6b-q4
```

```
  검색 성공(@3)   :  43/45  96%
  최종 정답       :  34/45  76%
  검색OK·생성실패 :   9/45  20%   ← 모델 한계
  혼동(환각)      :   0/45   0%
```

**`검색OK·생성실패` 가 핵심 지표다.** 근거는 제대로 왔는데 모델이 못 읽어낸
비율이다. 이 값이 높으면 모델·프롬프트 문제이고, `검색 성공` 이 낮으면
추출·청킹·검색 문제다.

## 문제 진단표

| 증상 | 먼저 확인 | 원인과 대처 |
|---|---|---|
| 특정 문서가 아예 안 잡힌다 | `status -v` 에 있나 | 없으면 3단계 `❌` 확인 → 스캔 PDF 등 추출 실패 |
| 문서는 잡히는데 청크가 1~2개 | `extract` 문자수 | 추출이 거의 안 됨. 포맷·암호 확인 |
| 검색에 엉뚱한 문서가 온다 | `search --top-k 10` | top-10 에 있으면 순위 문제, 없으면 인덱싱 문제 |
| 표 안의 값을 못 찾는다 | `extract` 의 `표 복원` | `없음`이면 표 구조 복원 실패 — 해당 표는 정확도 낮음 |
| 근거는 맞는데 답이 틀리다 | `search` 로 청크 확인 | 정답 문장이 청크에 있으면 **생성 문제** |
| 답에 없는 숫자가 나온다 | 근거와 대조 | 환각. 근거 노출 UX가 안전장치인 이유 |
| 첫 질의만 느리다 | 두세 번 반복 | 정상(캐시 예열) |
| 질문 후 프롬프트가 안 돌아온다 | 몇 초 기다려 본다 | `ask` 는 1회용이라 답변 후 종료된다. 계속 물으려면 `chat` 사용. 종료 시 모델 해제에 약 0.5초 걸린다 |
| 질문마다 4~5초씩 느리다 | 명령 확인 | `ask` 를 반복 실행 중이면 매번 모델을 다시 올린다 → `chat` 사용 |
| 검색이 계속 300ms 이상 | `search` 단계 분해 | dense 가 크면 Qdrant 서버 모드 검토, BM25 가 크면 인덱스 재구축 |
| 인덱싱이 예상보다 오래 걸린다 | 전원·발열 | 처리량이 69→47 chunk/s 로 떨어진다. 정상 |
| 문서를 지웠는데 계속 검색된다 | `status -v` | 인덱스에 남아 있다. `clear --doc <경로>` 후 `index` 로 BM25 갱신 |
| 재인덱싱했는데 옛 결과가 나온다 | 설정 변경 여부 | 청킹·추출 설정을 바꿨으면 증분으로는 안 바뀐다. `--rebuild` 또는 `clear` 후 재인덱싱 |
| 인덱스를 지웠는데 파일이 남아 있다 | 다른 프로세스 | `chat` 등이 실행 중이면 잠긴다. 종료 후 다시 `clear` |

## 실전 사례 — 같은 주제인데 답이 갈린 경우

실제로 관찰된 사례다. 진단 흐름을 그대로 보여준다.

**질의 A**: `본인 결혼 시 경조금은 얼마인가요?` → `search` 결과 top-3 에
표가 복원된 청크가 포함됨:

```
[3] 경조사지원규정.doc
    ... | 본인 결혼 | 5 | 500,000 | ...
```

**질의 B**: `본인 결혼 시 경조금과 휴가는 얼마인가요?` → `ask` 결과:

```
── 근거 3건 ──
  [1] 03.경조사지원규정.doc  ... 4. 경조휴가일수 공휴일과 경조사가 중복되었을 경우 ...
  [2] 03.경조사지원규정.doc  ... (같은 내용) ...
  [3] 경조사지원규정.doc      ... (같은 내용) ...

── 답변 ──
본인 결혼 시 경조금과 휴가는 6개월 이내에 결혼할 경우, 공휴일을 제외하여 ...   ← 틀림
```

### 진단

1. 질문에 "휴가"를 추가하자 **"휴가일수" 조항 쪽으로 검색이 끌려갔다.**
2. top-3 이 **중복 문서**로 채워져 실질 근거가 1건뿐이었다.
3. **정답 표 청크가 top-3 에서 빠졌다** → 생성 모델은 없는 정보를 답할 수 없다.

**결론: 생성이 아니라 검색 실패다.** 모델을 1.7B 로 바꿔도 해결되지 않는다.

### 대처

- 질문을 나눠서 묻는다(금액 / 휴가일수 별도)
- `--top-k 5` 로 근거를 늘린다
- 중복 문서를 정리한다
