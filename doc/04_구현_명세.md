로컬 CPU 한 대에서 도는 한국어 사내문서 RAG.
GPU·네트워크·외부 API 를 쓰지 않는다. 문서를 넣으면 색인하고, 질문하면

## 2. 전체 흐름

### 2.1 인덱싱

```
파일 나열 (확장자 필터)
   └─ 지문 비교 (sha1+mtime) → 안 바뀐 파일은 건너뜀 (증분)
        └─ 추출        extract.py            : 하이브리드 엔진 → 표 정규화 → sanitize
             └─ 청킹   chunk.py+structure.py : 절 경계 유지 패킹
                  └─ 임베딩 embed/           : passage: 프리픽스, 배치 8
                       └─ 적재  index/       : Qdrant upsert + BM25 역색인
                            └─ 500청크마다 체크포인트
```

### 2.2 질의

```
질문
 └─ 임베딩(query: 프리픽스)  ─┐
 └─ BM25 서브워드 토큰화     ─┤ 각 10건
                              └─ RRF 융합 → 중복 제거 → top-3
                                   └─ [근거] 화면에 먼저 표시   ← 여기서 체감 응답 시작
                                        └─ 프롬프트 조립 → llama.cpp 스트리밍
                                             └─ 지시문 되뱉기 제거 → 인용번호 파싱
```

**근거를 먼저 내보내는 것이 UX 설계의 핵심이다.** 검색은 130ms 에 끝나지만
첫 토큰까지는 2.5초가 걸린다. 그 2.4초 동안 화면이 비어 있으면 안 된다.

## 4. 추출 계층 (`extract.py`)

### 4.1 대상 확장자

```
.pdf .doc .docx .ppt .pptx .xls .xlsx .hwp .hwpx .txt .md .html .htm .py .ipynb
```

### 4.2 엔진

CSOClassify 의 `HybridExtractor` 를 재사용한다. 확장자별 전용 엔진을 먼저
쓰고, 실패하면 사이냅 `snf_exe` 로 폴백한다.

| 형식 | 1차 엔진 |
|---|---|
| pdf | PdfiumExtractor |
| hwp / hwpx | Hwp5Extractor / HwpxZipExtractor |
| doc / docx | DocExtractor / DocxExtractor |
| xls / xlsx | XlsExtractor / XlsxExtractor |
| ppt / pptx | PptExtractor / PptxExtractor |
| html / txt | HtmlTextExtractor / PlainTextExtractor |
| ipynb | 자체 (`extract_ipynb` — 셀 소스+마크다운만, 출력 제외) |

실측 실패 8건/376건(2.1%). 대부분 스캔 PDF(이미지)라 텍스트가 애초에 없다.

### 4.3 표 정규화 — Word 표 복원

Word 표를 추출하면 **탭이 셀 구분자, 탭 두 개가 행 끝**으로 나온다.
셀 안 개행은 두 가지 뜻을 갖고, 이 둘을 구별하는 것이 이 함수의 전부다.

**(A) 세로로 눕힌 여러 행** — 한 셀에 8줄이 들어 있고 실제로는 8개 행이다.

```
경 사 ⇥ 본인 결혼/자녀 결혼/… ⇥ 5/1/… ⇥ 500,000/300,000/… ⇥⇥
                (/ 는 셀 안의 개행)
```

**(B) 한 셀 안의 줄바꿈** — "일비"와 "(1일당)"은 같은 셀이다.

```
구 분 ⇥ 철도운임 ⇥ … ⇥ 일비/(1일당) ⇥ 숙박비/(1박당) ⇥⇥
```

판별 규칙:

```
셀 안 줄 수 ≥ 3 인 셀이 2개 이상  →  (A) zip 으로 펼침
그 외                              →  (B) 개행을 공백으로 이어 붙임
```

- 펼칠 때 줄 수는 **최댓값**을 쓰고 짧은 셀은 빈칸으로 채운다.
  (최빈값을 쓰면 긴 셀의 남는 줄이 사라진다 — 실제로 41,773자 문서를
  2,990자로 날린 적이 있다. REPORT §22.3)
- 한 줄짜리 셀은 그룹 이름표로 보고 모든 행에 되풀이한다.
- 한 행이 60행 넘게 펼쳐지면 표가 아니라 본문 덩어리로 보고 포기한다.
- **무손실 가드**: 정규화 결과의 공백 제외 글자 수가 원문보다 줄면
  변환을 통째로 버리고 원문을 반환한다.

출력은 마크다운 표 행 `| a | b | c |`.

### 4.4 문자 정화 (`sanitize`)

유니코드 **비문자**(U+FFFE, U+FDD0–FDEF, 사용자 정의 영역 U+F000–F8FF)를
공백으로 바꾼다.

> 🔴 이것들은 UTF-8 인코딩 검사를 **통과한다**. 그래서 `encode()` 성공 여부만
> 보던 예전 빠른 경로가 이 문자들을 그대로 통과시켰다. PDF 추출에서 공백이
> U+FFFE 로 나오는 문서가 있어 BM25 토큰이 통째로 붙어 버렸다. REPORT §20.4

서러게이트(U+D800–DFFF)도 함께 제거한다.

## 5. 청킹 계층 (`structure.py` + `chunk.py`)

여기가 이 시스템에서 가장 많이 손댄 부분이다.

### 5.1 왜 구조를 보는가

고정 크기 청킹은 문서 구조를 전혀 보지 않는다. 실측에서 회사규정
**조문 123개 중 89개(72%)가 청크 경계에 걸려** 두 조각으로 나뉘어 있었다.
검색이 그중 한쪽만 가져오면 모델은 조문의 절반만 보고 답한다.

**크기를 키우는 것은 답이 아니다.** 128/192/256 을 전수 비교했을 때
정답률은 평평했고 TTFT 만 컨텍스트 길이에 비례해 늘었다(REPORT §17).
필요한 것은 크게 자르는 것이 아니라 **경계를 지키는 것**이다.

### 5.2 문법 감지 — 문서마다 하나만

우선순위 순으로 훑어 **3회 이상** 나타나는 첫 문법을 채택한다.

| 순위 | 이름 | 패턴 예 |
|---|---|---|
| 1 | 조문 | `제5조(지급 금액)`, `제 5 조 【 시행일 】` |
| 2 | 마크다운 | `## 제목` |
| 3 | 번호절 | `1. 적용대상`, `1.2 정의` |
| — | 폴백 | 셋 다 3회 미만이면 고정 크기로 처리 |

> 🔴 **하나만 고르는 것이 핵심이다.** 조문 문서 안의 `1.` `2.` 는 조문의
> 하위 항목이지 절이 아니다. 둘을 함께 쓰면 조문이 오히려 더 잘게 부서진다 —
> 취업규칙이 조문 77개 대신 절 119개로 쪼개졌다.

코퍼스 표본 77건 기준 문법 분포: 번호절 38% · 표 25% · 마크다운 19% ·
**조문 6%**. 조문만 보고 만들었으면 94% 의 문서에서 아무 효과가 없었다.

### 5.3 부속서 표지 — 문법과 별개로 항상 경계

`별표1`·`[붙임 2]`·`(별첨 #1)`·`부칙` 은 본문 조문 안에 나타나지 않는
최상위 구분이다. 채택 문법이 무엇이든 **합집합**으로 경계에 넣는다.

인식 대상: `별표 · 별첨 · 붙임 · 참고 · 서식 · 부록 · 첨부` + 번호, 그리고 `부칙`.

> 🔴 같은 표지가 **참조로도** 쓰인다.
> ```
> 별표1        국내출장여비      ← 제목 (경계 O)
> 별표1에 따라 지급한다.          ← 참조 (경계 X)
> ```
> 번호 뒤에 한글이 바로 붙으면 참조로 본다 — 정규식 `(?![가-힣])`.

실측(367건): 별표 6건 · 별첨 7건 · 붙임 8건 · 참고 6건 · 서식 3건 ·
부록 1건 · 부칙 22건.

### 5.4 긴 제목 처리

번호절 문서에서는 **제목 줄이 곧 내용**인 경우가 많다.

```
14.2 가족이 유해를 운구할 경우 가족 1인에 대하여 왕복여비로 지급한다.
```

- 통째로 이름표에 넣으면 → 접두가 길어져 본문 예산을 잡아먹는다
- 잘라 버리면 → **내용이 사라진다**

40자를 넘으면 **번호만 이름표로 쓰고 줄 전체는 본문에 남긴다.**

### 5.5 패킹 — 왜 '절 = 청크' 가 아닌가

실측한 절 413개의 길이 **중앙값이 36토큰**이다. 절을 그대로 청크로 쓰면
변별력 없는 조각이 쏟아진다. 대신 **85%가 128토큰 안에 들어가므로**,
크기를 키우지 않고도 대부분의 절을 온전히 담을 수 있다.

```
절 ≤ 남은 예산   → 현재 청크에 이어 붙인다
절 > 남은 예산   → 청크를 끊고 새 청크에서 시작   (겹침 없음)
절 > 예산 (15%)  → 그 절만 내부 분할              (이때만 겹침 16토큰)
```

절 하나를 쪼갤 때는 **줄 단위로 모으다가, 한 줄이 예산을 넘을 때만
토큰으로 자른다.** 접두(`[문서명 > 절제목]`)가 차지하는 토큰은 예산에서
미리 빼 둔다.

절 경계에서 겹침을 두지 않는 것은 의도적이다 — 경계가 의미 단위이므로
겹칠 이유가 없고, 겹치면 같은 내용이 두 청크에 들어가 중복 근거가 된다.

### 5.6 표 머리글 되살리기

표 행만 담긴 청크는 머리글이 없으면 해석이 불가능하다.

```
| 내역 | 휴가(일) | 금액(원) |     ← 이 줄이 다른 청크에 있으면
| 본인 결혼 | 5 | 500,000 |        5가 일수인지 금액인지 알 수 없다
```

표로 시작하는 청크에는 그 표의 머리글 줄을 앞에 되살려 넣는다.
머리글 판별은 "칸이 2개 이상이고 숫자만인 칸이 하나도 없을 것".
(값 행을 머리글로 착각하면 뒤따르는 행 전체가 엉뚱한 이름표를 단다.)

### 5.7 출처 접두

모든 청크 앞에 `[문서명 > 절제목]` 을 붙인다. 10~15토큰을 쓰고 셋을 얻는다.

- **BM25** — 제목 단어가 색인에 들어가 짧은 질의가 걸린다
- **dense** — 임베딩에 문맥이 실린다
- **생성** — 모델이 "지금 보는 것이 제5조(지급 금액)"임을 안다

## 6. 임베딩

- 모델 `e5-small-ko` ONNX **int8** (`model.onnx`). fp32 대비 2.5배 빠름 —
  AVX-512 없는 이 CPU 에서도 int8 이 유리하다.
- 프리픽스 규약: 색인 `passage: `, 질의 `query: `
- 스레드 4 (8로 올려도 이득 없음 — P-core 4개가 실질 상한)
- 배치 8 (1→8 에서 65→77 chunk/s, 그 이상은 하락)

> ⚠️ **절단 해제가 필수다.** e5 의 `tokenizer.json` 에는 max_length=512 절단이
> 박혀 있다. 해제하지 않고 encode 하면 긴 문서의 앞 512토큰만 남고 나머지가
> **조용히** 사라진다(취업규칙 11,830토큰 → 512토큰, 96% 유실).
> `OnnxEmbedder.ensure_loaded()` 가 `no_truncation()` 을 호출한다.

## 7. 색인

### 7.1 Qdrant (local 모드)

- 임베디드. 서버 프로세스 없음. `qdrant_data/` 폴더가 곧 DB.
- 컬렉션 `rag`, 384차원, 코사인
- upsert 배치 1000

> ⚠️ **배타적 파일 잠금**이 걸린다. 한 번에 **한 프로세스만** 열 수 있다.
> 인덱싱이나 평가가 도는 중에는 질의가 `PermissionError` 로 실패한다.
> 웹 UI 를 붙일 때 반드시 고려해야 한다(설계서 R15).

### 7.2 BM25 (자체 구현)

numpy 역색인. `bm25_index.npz` 에 저장. k1=1.5, b=0.75.

토큰화는 **서브워드**(임베딩 토크나이저 재사용)를 쓴다.

> 공백 분리는 한국어 조사 때문에 Recall@1 이 67% 로 떨어진다.
> "휴가비는" 과 "휴가비" 가 다른 토큰이 되기 때문이다. 서브워드로 바꾸면
> 92~100% 로 회복된다(REPORT §13.4).

### 7.3 증분 갱신

`index_state.json` 에 파일별 `{fingerprint(sha1), mtime, chunks, folder}` 를
남긴다. 지문이 같으면 건너뛴다. 500청크마다 체크포인트를 남겨
중단·재개가 가능하다(장시간 인덱싱 중 발열로 처리량이 떨어진다).

> ⚠️ 청크 크기나 청킹 방식을 바꾸면 **전체 재인덱싱**이 필요하다.
> 증분 갱신은 옛 방식으로 만든 청크를 그대로 둔다.

## 8. 검색

### 8.1 RRF 융합

dense 10건 + BM25 10건 → RRF(k=60) → 상위 3건.

```
score(d) = Σ  1 / (60 + rank_i(d))
```

### 8.2 근거 중복 제거

**코퍼스의 50%(367건 중 183건)가 완전 동일 사본이었다.** 같은 파일이 여러
경로에 색인돼 있으면 top-3 가 사본으로 채워져 서로 다른 근거가
**3건이 아니라 1~2건**이 된다. 45문항 실측에서 근거 슬롯의 19% 가 이렇게
낭비됐다(REPORT §19).

RRF 결과를 순서대로 훑으며 **공백 제거 후 완전 일치**하는 텍스트를 건너뛴다.
버린 것은 모아 두었다가 3건을 못 채우면 뒤에 붙인다(빈 슬롯을 만들지 않는다).

- 끄기: `SIMPLERAG_DEDUP=0`
- 판정 기준을 완전 일치로만 둔 것은 의도적이다. 유사도 기반으로 하면
  "비슷하지만 다른 조문"을 지워 버릴 위험이 있다.

### 8.3 리랭킹

`retrieve/reranker.py` — bge-reranker-base int8 ONNX(283MB), CPU 4스레드.

```
_search(top_k=RERANK_POOL=10) → RRF + 사본 제거 후보 10건
reranker.score(질의, 10건)     → 쌍마다 관련성 점수 1개 (배치 1회)
점수 내림차순 안정 정렬        → 상위 TOP_K(3)건
```

| 설정 | 값 | 근거 |
|---|---|---|
| `RERANK` | auto | iGPU 일 때만 켠다. CPU 에서는 TTFT 3초 달성률이 74→53% 로 무너졌다 |
| `RERANK_POOL` | 10 | 506문항 답변 정답 5→10 에서 +16(p=0.056), TTFT +0.36초(§35.9). §27 스윕(204문항·검색 지표)의 5 를 대체 |
| `RERANK_MAX_TOKENS` | 512 | 질의+근거 절단 길이 |
| `RERANK_SHARE_TOKENIZER` | True | 임베더 토크나이저 구성요소 재사용 — 기동 −0.57초(§33) |
| `RERANK_DEFER_LOAD` | True | 준비 완료 뒤 백그라운드 적재 — chat 준비 단축, ask 총시간 불변(§34) |

- 실험 스크립트(`exp5_rerank`, `exp8_igpu`)와 **같은 절차**다. 정렬 방향·동점 처리·
  풀 크기가 바뀌면 실험 수치가 운영에서 재현되지 않는다(`bench/test_backend_rerank.py`
  가 지킨다).
- 리랭커 예외는 삼키고 RRF 순서로 답한다(`timing["rerank_error"]`). 적재 실패면
  `warmup()` 이 리랭커를 떼어 매 질의 실패를 막는다.
- `index` / `clear --doc` 은 `warmup(rerank=False)` — 검색을 안 하는 명령은 리랭커를
  올리지 않는다.
- **토크나이저는 임베더 것을 재사용해 조립한다**(`RERANK_SHARE_TOKENIZER`). 17MB
  `tokenizer.json` 파싱이 0.88초 동안 GIL 을 쥐어 병렬 예열의 Qdrant 적재를 멈췄기 때문이다.
  두 모델은 같은 XLM-R 어휘라 model·normalizer·pre_tokenizer·post_processor·decoder 가 같고
  `<mask>` 플래그만 다르다. 검증한 파일(바이트 크기)일 때만 재사용한다. 506문항 실제 입력
  2,530쌍에서 ids·점수·상위 3 선택이 모두 같았고, 리랭킹의 기동 비용이 약 1.15초 → 0.58초가
  됐다(REPORT §33).
- **리랭커는 준비 완료 뒤 백그라운드로 올린다**(`RERANK_DEFER_LOAD`). 병렬 예열에 넣으면
  ONNX 세션 생성(약 0.6초, GIL 점유)이 Qdrant 적재를 멈춰 준비가 늦어진다. 리랭커는
  리트리버에 처음부터 붙어 있고, 첫 질문이 적재 중에 오면 락에서 기다렸다가 리랭킹한다 —
  결과는 같고 그 질문만 늦다. 적재가 실패하면 떼어내고 RRF 로 답한다. `chat` 준비가
  빨라지는 대신 `ask`(준비 직후 바로 질문)의 총시간은 줄지 않는다(REPORT §34).
  1회용 명령(`ask`·`search`)과 `bench/eval_large.py` 는 `warmup()` 직후 `app.wait_rerank()` 로
  기다렸다 묻는다 — 기다리지 않으면 검색이 적재(GIL 점유)와 겹쳐 총시간은 같은데 첫 글자·검색
  시간만 부풀어 보였다(첫 글자 1.50→2.27초). `chat` 만 백그라운드 적재의 이득을 쓴다.

### 9.1 프롬프트 (V0 — 채택본)

```
당신은 사내 문서 검색 도우미입니다. 아래 [근거] 안의 내용만 사용해 한국어로

답변은 3~5문장으로 요약하고 마지막에 근거 번호를 [1] 형식으로 표기하세요.
```

> ⚠️ **프롬프트를 바꾸면 반드시 실코퍼스로 재측정할 것**(설계서 R9).
> 인용 강제형(V3)을 썼다가 실문서에서 정답률이 83%→50% 로 무너져 폐기했다.
> 합성 데이터로 튜닝한 프롬프트는 실데이터에서 역전될 수 있다.

### 9.2 thinking 비활성

Qwen3 는 thinking 모드가 켜지면 사고토큰 수백 개를 먼저 뱉어 약 3배 느려진다.
`<think>` 블록을 프롬프트에서 **미리 닫아** 바로 답변을 시작하게 한다.

### 9.3 지시문 되뱉기 제거

0.6B 모델은 시스템 지시문의 일부를 답변에 그대로 섞는다.

```
… 근속 5년마다 지급합니다. 답변은 3~5문장으로 요약하고 근거 번호를 [1] 형식으로 표기 [1]
```

정규식으로 이 조각들을 지운다. **프롬프트 자체는 건드리지 않는다** — 프롬프트를
바꾸면 정답률이 흔들리기 때문이다(R9). 출력만 정화한다.

- 지우는 대상: `[N] 형식으로 표기`, `N~M문장으로 요약`, `추측하지 마세요`,
  선행 `[질문]`/`[근거]` 표지, 꼬리 인용번호 중복
- 정화 결과가 비면 원문을 그대로 둔다(과잉 삭제 방지)

> 🔴 **스트리밍에서 이게 어렵다.** 이미 화면에 뿌린 토큰은 지울 수 없다.
> 그래서 `StreamWriter` 가 항상 뒤 90자를 손에 쥐고 있다가(hold-back)
> 끝날 때 전체를 정화한 뒤 나머지를 뱉는다. 중간에 Ctrl-C 로 끊어도
> `finally` 에서 정화가 돌게 해 두었다.
>
> ⚠️ 이어 붙일 수 있는지 판정할 때 **공백을 무시하고 글자만 본다.**
> 정화 함수가 공백을 한 칸으로 접기 때문에, 단순 `startswith` 로 보면
> 이미 나간 부분에 줄바꿈이 하나만 있어도 판정이 실패해 정화가 조용히
> 건너뛰어진다. 실제로 그렇게 동작하고 있었다(REPORT §24.3).
>
> 실측: 45문항 중 **36건**의 답변에 되뱉기가 있었다. 다만 채점 결과는
> 0건 변했다 — 보기 흉했을 뿐 오답의 원인은 아니었다(REPORT §18).

### 9.4 인용 번호 파싱

모델은 답변 끝에 `[1]` 형식으로 근거 번호를 단다. 이것을 뽑아 `cited` 목록을
만든다.

🔴 **대괄호 표기가 청크 접두와 겹친다.**

```
근거 3번 접두 : [12.원격지 근무자 비품 구매 관련 지침_22.01.25]
인용 표기 규약 : [1] [2] [3]
                 ^^^^ 모델 눈에는 같은 모양이다
```

문서명이 번호로 시작하는 일이 잦아서, 모델이 접두를 따라 쓰면서 근거가
3건뿐인데 `[12]` 를 인용처럼 찍는다. **구조 인식 청킹이 접두를 도입하면서
생긴 결함이다** — 고정 청킹 때는 접두가 없어 드러나지 않았다.

`drop_invalid_cites(body, n_evidence)` 가 **유효 범위(1~n) 밖의 번호를
본문과 목록 양쪽에서** 걷어낸다. 목록에서만 빼면 화면에 없는 근거를 가리키는
표기가 남기 때문이다. `n_evidence` 를 주지 않으면 아무것도 건드리지 않는다 —
개수를 모르면 판단할 수 없으므로 보존이 안전하다.

🔴 **숫자를 지우지 않고 괄호만 벗긴다.** 대괄호 안이 인용이 아니라 **값**인
경우가 있다.

```
사업예산은 [1]에 따르면, [75]억 원입니다.
                         ^^^^ 인용이 아니라 금액이다
```

지우면 "억 원입니다" 가 되어 숫자가 사라진다. 괄호만 벗기면 `75억 원` 이
되어 내용이 보존되고, 헛인용이었더라도 군더더기 숫자 하나가 남을 뿐이다.
괄호가 없어지므로 인용으로 읽히는 일은 어느 쪽이든 없다.
**틀릴 수 있는 규칙보다 잃지 않는 규칙을 골랐다**(REPORT §24.8).

> 근본 해결은 접두의 괄호 모양을 바꾸는 것이지만, 색인된 텍스트가 달라져
> **전체 재인덱싱(28분) + 204문항 재측정**이 필요하다. 지금은 출력만 고쳤다.

**스트리밍의 한계** — 잘못된 인용이 답변 앞쪽에 있어 이미 화면에 나갔으면
지울 수 없다. `cited` 목록은 항상 정확하고, `--no-stream` 과 평가 경로는
본문까지 깨끗하다.

### 9.5 파라미터

`n_ctx=2048` · `threads=8` · `temperature=0.0` · `max_tokens=200`

| 백엔드 | `n_gpu_layers` | `flash_attn` | 근거 |
|---|---:|:--:|---|
| CPU | 0 | 켬 | prefill 이득이 decode 손해보다 크다(RAG 는 prefill 지배) |
| iGPU(Vulkan) | -1(전부) | **끔** | 속도 차이 0, 정답률 +3/+5문항(비유의) — REPORT §31.12 |

⚠️ 이 인자들은 `GgufGenerator.ensure_loaded()` 의 `wanted` 에 **명시**한다.
적재 인자는 `inspect.signature(Llama.__init__)` 로 걸러지므로, `Llama` 를 하위
클래스로 덮어 인자를 끼워 넣으면 `model_path` 까지 걸러져 적재가 실패한다
(REPORT §31.5 에서 실제로 터졌다).

### 9.6 생성 백엔드 선택 (CPU / iGPU)

`generate/backend.py`. llama-cpp-python 은 **import 하는 순간 DLL 을 고르고 바꿀 수
없다.** 그래서 `App.warmup()` 이 LLM 을 올리기 전에 `backend.select()` 로 정하고
`LLAMA_CPP_LIB_PATH` 에 반영한다.

```
select()
 ├ llama_cpp 이미 적재?         → 그 DLL 을 따른다          (source=loaded)
 ├ SIMPLERAG_GEN_BACKEND=cpu    → CPU                        (config)
 ├ 사전 점검 탈락                → CPU                        (check)
 │   런타임 폴더·DLL 5개 / VERSION.txt = llama-cpp-python / vulkan-1.dll
 ├ gen_backend.json 키 일치      → 저장된 결정                (cache)
 └ 자식 프로세스 2개로 측정      → decide() → 저장            (probe)
     simplerag _probe-backend vulkan|cpu <모델> <런타임>
     운영과 같은 모양의 프롬프트 611토큰, 1회 버림 + 2회 평균
```

| 판정 | 조건 |
|---|---|
| iGPU | iGPU prefill ≥ CPU × `GPU_MIN_SPEEDUP`(1.3) |
| CPU | iGPU 측정 실패(적재 실패·크래시·시간 초과) 또는 1.3배 미달 |

왜 이렇게 하는가

- **자식 프로세스** — Vulkan 판은 `vulkan-1.dll` 을 직접 링크한다. 드라이버가 깨진
  PC 에서 본 프로세스가 적재하다 죽으면 앱이 죽는다. 손상 DLL 로 실측: 자식이
  `WinError 193` 으로 실패 → 앱은 CPU 로 계속(REPORT §32).
- **두 벌 동봉** — Vulkan 판은 `n_gpu_layers=0` 이어도 큰 행렬곱을 iGPU 로 보낸다
  (1041토큰 2.87초 vs CPU 판 4.0~4.2초). 'CPU 모드'가 되지 않는다.
- **1.3배 문턱** — iGPU 답변은 CPU 와 문장이 약 70% 다르고 정답률 −3/−4문항 신호가
  있다(비유의, R18). 확실히 빠를 때만 쓴다.
- **런타임은 프로그램 폴더 기준**(`config.APP_DIR`) — 데이터 루트(`SIMPLERAG_HOME`)를
  옮겨도 iGPU 가 조용히 꺼지지 않는다.
- **캐시 키** — PC 이름·모델·바인딩 버전·Vulkan DLL(크기+수정시각)·문턱·스레드.
  드라이버 갱신은 키에 없다(R19) → `backend --reprobe`.

예열 생성(`GgufGenerator.warm()`) — 적재 직후 1토큰 생성. 새 PC 의 셰이더 컴파일
(9.75초, 1회)과 시스템 프롬프트 KV 를 첫 질문에서 떼어낸다. 셰이더는 드라이버가
캐시해 두 번째 프로세스부터 첫 prefill 이 평소와 같다(1.35초 vs 1.31~1.38초).
캐시는 **실행 파일별**이다 — `python.exe` 에 캐시가 있어도 `simplerag.exe` 첫 실행은 13.2초를
다시 컴파일했고, 측정 단계(1회 버림)가 이를 흡수했다(REPORT §32.6).

## 11. 설정값과 근거

`config.py` 에 모두 모여 있고 값 옆에 실측 근거가 주석으로 붙어 있다. 검색·청킹 계수는
**`config.yaml`** 로 코드 수정 없이 바꿀 수 있다 — 우선순위 환경변수 > config.yaml > 기본값,
찾는 순서 `SIMPLERAG_CONFIG` → `<데이터 루트>/config.yaml` → `<프로그램 폴더>/config.yaml`,
오타·범위 밖 값은 `ConfigError` 로 멈춘다(`settings.py`, REPORT §35). 아래 표의 yaml 키는
`chunk.tokens` 처럼 적었다.

| 상수 | 값 | 근거 |
|---|---:|---|
| `CHUNK_TOKENS` | 128 | 512→128 로 TTFT 9.07s→2.71s. 192/256 은 정답률 동일 + TTFT 만 증가 |
| `CHUNK_OVERLAP` | 16 | 청크의 12.5%. 경계 문장 손실 방지 최소값 |
| `MIN_CHUNK_TOKENS` | 16 | 꼬리 조각은 검색 노이즈만 늘린다 |
| `TABLE_HEADER_MAX_TOKENS` (`chunk.table_header_max_tokens`) | 64 | 표 조각에 다시 붙이는 머리글 길이 상한 — 실측 머리글 분포(p75 44, p90 74)에서 정함. 청크 최대 = 크기 + 이 값(§35) |
| `CHUNK_MODE` | structured | 조문 72%가 경계에 걸려 있었다 |
| `TOP_K` | 3 | 실측 포화점. 4 이상은 정답률 정체 + TTFT 만 증가 |
| `DENSE_TOP_K` (`retrieval.dense_top_k`) | 10 | 코사인 1차 후보 수 |
| `BM25_TOP_K` (`retrieval.bm25_top_k`) | 10 | BM25 1차 후보 수(0 = BM25 끔). §35 이전에는 `FIRST_STAGE` 하나로 둘 다 |

### 왜 총점 비교로는 판정하지 않는가

68% → 69% 는 문항 2개 차이다. 204문항에서 2개는 우연으로도 흔히 나온다.
중요한 것은 총점이 아니라 **어떤 문항이 뒤집혔는가**다.

```
b = 이전만 맞음 (잃은 문항)
c = 이후만 맞음 (얻은 문항)
```

총점이 같아도 b=20, c=20 이면 40문항이 뒤집힌 것이고, 그것은
"안 변했다"가 아니라 **"완전히 다른 시스템이 됐다"**는 뜻이다.

`compare_runs.py` 는 b+c 만 보고 정확 이항 검정을 돌린다.
b+c 가 10 미만이면 **"차이 없음"이 아니라 "알 수 없음"**이라고 명시한다 —
검정력이 없는 것을 없다고 말하면 안 된다.

### 왜 문항을 기계로 검증하는가

사람이 쓴 문항은 반드시 틀린다. 채점 규칙 오류로 **네 번** 헛발질한
전례가 있다(설계서 R5). 그래서 문항을 쓰고 나면 기계로 검사한다.

1. `src` 조각이 실제 색인 문서명과 맞는가
2. `must` 용어가 그 문서의 **색인된 텍스트**에 실제로 있는가
   → 원문에 없는 답을 요구하면 영원히 오답이 된다
3. `must` 용어가 지나치게 흔하지 않은가 (코퍼스 30% 초과 = 검색 없이도 맞춤)
4. 질문 중복

표 추론 문항(`kind="표추론"`)은 정답 문자열이 원문에 그대로 없는 것이
정상이므로 ②를 건너뛴다.

### 평가셋을 45 → 204 로 늘린 이유

45문항은 **고유 문서의 5.2%** 만 건드리고 있었다. 늘리고 나서 실제
정답률이 78% 가 아니라 63% 라는 것이 드러났다. 쉬운 5% 만 재고 있었던 것이다.

## 13. 현재 성능

### 13.1 인덱스 버전별 (204문항, Qwen3-0.6B)

| 인덱스 버전 | 청크 | Recall@1 | Recall@3 | 검색 | 정답률 | TTFT |
|---|---:|---:|---:|---:|---:|---:|
| 고정 청킹 | 43,152 | 78% | 92% | 177ms | 63% | 2.95s |
| 구조 인식 | 61,734 | 88% | 97% | 106ms | 69% | 2.59s |
| + 표 수정 | 62,144 | 88% | 97% | 151ms | 68% | 2.58s |
| **+ 부속서·긴제목** | **59,747** | **89%** | **98%** | **129ms** | **70%** | 2.60s |

`compare_runs.py` 판정:

| 비교 | 잃음 b | 얻음 c | p | 판정 |
|---|---:|---:|---:|---|
| 표수정 → 부속서 (Recall@3) | **0** | 2 | 0.500 | 검정력 없음. 단 **완전 포함** |
| 표수정 → 부속서 (정답률) | 4 | 8 | 0.388 | 유의차 없음 |

정답률 +4문항은 통계적으로 유의하지 않다. 그럼에도 채택하는 근거는
**손해 보는 축이 하나도 없다**는 것이다 — 검색에서 잃은 문항 0건,
청크 −4%, 인덱싱 −23%, 검색 지연 −15%.

### 13.2 오답 61건의 성격

| 구분 | 건수 |
|---|---:|
| 검색 실패 (근거 자체를 못 찾음) | 3 |
| **검색은 됐는데 답을 못 함** | **58** |
| 혼동(다른 문서 내용을 섞음) | 0 |

**병목은 검색이 아니라 생성이다.** Recall@3 이 98% 인데 정답률이 70% 라는
것은, 근거가 눈앞에 있는데도 0.6B 모델이 읽어 내지 못한다는 뜻이다.
검색을 더 손봐서 얻을 수 있는 상한은 남은 3문항, 즉 **1.5%p** 뿐이다.

혼동 0건은 좋은 신호다 — 모르면 틀리지, 엉뚱한 문서를 지어내지는 않는다.

## 15. 이 프로젝트에서 배운 것

같은 코퍼스에서 네 번 고쳤다. 세 번은 헛발질이었다.

| 관찰 | 진단 | 실제 효과 |
|---|---|---|
| §18 답변에 지시문이 섞인다 | 되뱉기가 오답 원인 | 36건 정화, **채점 0건 변화** |
| §19 근거가 사본으로 채워진다 | 중복이 오답 원인 | 슬롯 19% 회복, Recall +2%p, **정답률 미미** |
| §22 표가 뭉개진다 | 표 붕괴가 오답 원인 | 표는 완벽 복원, **정답률 69→68%** |
| §23 절 경계가 틀렸다 | 경계 오류가 오답 원인 | 검색 잃음 **0건**, **정답률 +4**, 청크 −4% |

앞의 세 번은 **관찰이 사실이었지만 그것이 정답률의 원인은 아니었다.**

네 번째만 달랐던 이유는 분명하다. §18·§19·§22 는 모두 **청크 안의 내용**을
손봤고, §23 은 **청크의 경계**를 손봤다. 이 코퍼스에서 병목은 내용의 품질이
아니라 경계의 위치였다.

> **고치기 전에 "이걸 고치면 무엇이 달라지는가"를 먼저 측정할 수 있게 만들어라.**

그리고 실험 격리에 대해:

> **격리는 "입력을 분리했는가"가 아니라 "출력이 서로 덮어쓰지 않는가"로 확인한다.**
