1한눈에 보기

iGPU 는 "답변 생성(LLM)" 한 군데에만, 그것도 Vulkan 을 통해서만 쓴다. 임베딩·리랭커(ONNX)는 providers=["CPUExecutionProvider"] 로 못 박아 항상 CPU 다 (src/simplerag/embed/onnx_embedder.py:96).

핵심 한 줄

iGPU 를 무조건 쓰지 않는다. 첫 실행 때 이 PC 에서 CPU 와 iGPU 를 직접 재 보고, iGPU 가 1.3배 이상 확실히 빠를 때만 iGPU 를 쓴다. 결과는 파일에 저장해 다음부터는 재지 않는다.

2핵심 아이디어 — DLL 두 벌을 동봉한다

llama-cpp-python 은 파이썬 껍데기일 뿐이고, 실제 계산은 네이티브 llama.dll 이 한다. SimpleRAG 는 같은 버전(0.3.35)의 DLL 을 두 벌 가진다.

판위치성격
CPU 판llama_cpp 패키지 내부 (기본)순수 CPU
Vulkan 판runtime/llama_vulkan/ (약 59MB, DLL 5개)vulkan-1.dll 링크 → iGPU 사용

전환 스위치는 환경변수 하나다 — LLAMA_CPP_LIB_PATH. 이걸 Vulkan 폴더로 가리키면 iGPU 판이 올라온다 (backend.py:427 _apply()).

if info["backend"] == "vulkan":
    os.environ["LLAMA_CPP_LIB_PATH"] = config.VULKAN_LIB_DIR
제약

import llama_cpp 하는 순간 DLL 이 확정되고, 한 프로세스에서는 바꿀 수 없다. 그래서 백엔드 선택은 반드시 import 이전에 끝나야 한다. 코드 구조가 이 제약을 중심으로 짜여 있다.

왜 Vulkan 판을 CPU 용으로 겸하지 않는가

  • n_gpu_layers=0 으로 둬도 Vulkan 판은 큰 행렬곱을 iGPU 로 보낸다(실측 1041토큰 2.87초 vs CPU 판 4.0~4.2초). 즉 'CPU 모드'가 사실은 CPU 가 아니게 되어 비교가 무의미해진다.
  • vulkan-1.dll 이 없는 PC 에서는 적재 자체가 실패한다. CPU 판이 없으면 앱이 아예 못 돈다.

3왜 CUDA 가 아니라 Vulkan 인가

내장 그래픽(Intel Iris Xe, AMD Radeon 등)에는 CUDA 가 없다. Vulkan 은 Intel·AMD·NVIDIA 를 모두 덮는 표준이고, 그래픽 드라이버만 최신이면 C:\Windows\System32\vulkan-1.dll 이 이미 깔려 있다. 사용자가 별도 런타임을 설치하지 않아도 iGPU 를 굴릴 수 있다는 것이 채택 이유다.

4선택 절차 — 무조건 쓰지 않고 "재서" 쓴다

backend.py:366 _select() 의 5단계:

1) llama_cpp 가 이미 import 됐나?   → 그 DLL 그대로 (바꿀 수 없음)
2) SIMPLERAG_GEN_BACKEND=cpu 인가?  → 끝, CPU
3) 사전 점검 vulkan_available()      → 탈락이면 CPU
4) 저장된 측정이 이 환경과 맞나?      → 그대로 사용 (source=cache)
5) 아니면 자식 프로세스로 둘 다 재고 decide()  (source=probe)

3단계 사전 점검(backend.py:131 vulkan_available())은 프로세스를 띄우기 전에 파일만 보고 거른다.

  1. 런타임 폴더와 DLL 5개가 있는가
  2. VERSION.txt 가 파이썬 바인딩 버전과 일치하는가 — 다르면 구조체 배치가 달라 죽거나 조용히 오작동한다
  3. System32\vulkan-1.dll 이 있는가 — 없으면 적재 자체가 실패

5왜 자식 프로세스에서 재는가

backend.py:301 run_probe() 는 subprocess 로 자기 자신을 _probe-backend 라는 숨은 명령으로 띄운다. 이유는 두 가지다.

  1. 안전 — 드라이버가 깨진 PC 에서 Vulkan DLL 적재 실패는 파이썬 예외가 아니라 네이티브 크래시다. 본 프로세스에서 하면 앱이 통째로 죽는다. 자식이 죽으면 부모는 "비정상 종료"로 읽고 조용히 CPU 로 폴백하면 된다.
  2. 비교 불가능성 — 한 프로세스엔 DLL 이 하나뿐이니, 두 판의 속도를 비교하려면 프로세스가 둘이어야 한다.

자식은 결과를 표준출력의 마지막 JSON 한 줄로 넘긴다. 부모는 뒤에서부터 { 로 시작하는 줄을 찾아 파싱하고, 못 찾으면 실패로 처리한다.

6무엇을 어떻게 재는가

backend.py:454 probe_main() 이 운영과 같은 모양의 프롬프트 (시스템 지시문 + 근거 3건, 611토큰)로 잰다.

for i in range(3):
    llm.reset()                                     # KV 재사용 방지 — 매번 전체 prefill
    llm.create_completion(prompt(i), max_tokens=1)  # 1토큰만 = 순수 prefill 시간

sec = sum(times[1:]) / len(times[1:])   # 첫 회는 셰이더 컴파일 포함 → 버린다
  • max_tokens=1 — decode 는 iGPU 나 CPU 나 비슷하고, RAG 는 프롬프트가 길어 prefill 이 체감 속도를 지배하므로 prefill 만 끊어서 잰다. (→ 11장)
  • llm.reset() — llama.cpp 는 프롬프트 앞부분이 같으면 KV 캐시를 살려 prefill 을 건너뛴다. 그냥 3회 돌리면 2·3회차가 거의 공짜가 되어 엉터리 숫자가 나온다. (→ 12장)
  • 회차마다 질문 번호만 바꾼 프롬프트를 쓴다 — 길이는 같고 내용은 다르게.
  • 첫 회를 버리는 이유 — Vulkan 은 최초 실행 시 셰이더를 컴파일하므로 그 시간이 섞인다.

7판정 — 1.3배 이상 빨라야만 iGPU

backend.py:162 decide() 는 부수효과 없는 순수 함수라 테스트하기 쉽게 분리돼 있다.

ratio = gpu["prefill_tps"] / max(cpu["prefill_tps"], 1e-6)
if ratio >= min_speedup:      # GPU_MIN_SPEEDUP = 1.3
    return "vulkan", ...
문턱을 둔 이유

config.py:326 에 적힌 대로, iGPU 는 부동소수 연산 순서가 달라 답변 문장이 CPU 와 달라지고 정답률이 조금 내려가는 신호가 있었다(−3/−4문항, 통계적으로 비유의). 또 iGPU 성능은 PC 편차가 커서 구형 UHD 그래픽은 CPU 보다 느릴 수도 있다. 그래서 "확실히 빠를 때만" 바꾼다.

8측정 결과 캐싱

매번 15~40초씩 재면 못 쓴다. backend.py:189 cache_key() 가 만드는 키로 "이 측정이 아직 유효한가"를 판단한다.

키 구성요소바뀌면
host — PC 이름다른 PC → 다시 측정

llama_cpp_python — 바인딩 버전업그레이드 → 다시 측정

모델별로 최대 4개(_CACHE_KEEP)를 보관해서, ask ↔ ask --precise 를 오갈 때마다 재측정하지 않는다. 저장은 임시 파일에 쓰고 os.replace 로 바꿔치기해 쓰다 죽어도 반쪽 파일이 남지 않게 한다.

주의

그래픽 드라이버 갱신은 키에 없다(조회에 WMI 가 필요해 느리다). 드라이버를 업데이트했거나 전원 설정을 바꿨다면 backend --reprobe 로 직접 다시 재야 한다.

10iGPU 는 리랭킹 스위치도 겸한다

backend.py:76 rerank_enabled() 는 설정이 auto 일 때 iGPU 인 경우에만 리랭킹을 켠다.

조합TTFT 3초 달성률

CPU + 리랭킹 켬53% — 무너짐

LLM 을 iGPU 로 넘기면 CPU 가 한가해지고, 그 여유를 리랭커(CPU ONNX)가 쓴다. 즉 iGPU 채택은 속도뿐 아니라 검색 품질까지 끌어올리는 결정이다.

11배경 개념 ① — prefill 이란

LLM 이 답을 만드는 과정은 성격이 완전히 다른 두 단계로 나뉜다.

[ prefill ]  질문+근거를 통째로 읽는 단계  ──→  [ decode ]  답을 한 글자씩 뱉는 단계
   (한 번에 쭉)                                   (1토큰씩 반복)

비유

사람이 시험 문제를 푼다고 하자.

  • prefill = 문제지와 참고자료 5장을 훑어 읽는 시간
  • decode = 답안지에 한 글자씩 써 내려가는 시간

읽기는 눈으로 전체를 빠르게 병렬로 스캔할 수 있다. 하지만 쓰기는 앞 글자를 써야 다음 글자를 쓰니 무조건 순차다.

기술적으로

prefilldecode
처리 단위입력 토큰 611개를 한꺼번에1토큰씩 순차
연산 모양행렬 × 행렬행렬 × 벡터 1개
병목연산량 (compute)메모리 대역폭
GPU 코어 활용꽉 채워 쓴다논다
iGPU 효과큼 (2.8배)거의 없음
산출물KV 캐시 생성KV 캐시에 1칸씩 추가

SimpleRAG 에서 왜 prefill 만 재는가

RAG 는 입력이 길고 출력이 짧다. 검색된 근거 문서 3건을 프롬프트에 다 넣으니 입력 600~1000토큰, 답변은 1~2문장(50토큰 남짓). 그래서 "첫 글자가 나오기까지의 시간(TTFT)"을 prefill 이 거의 다 잡아먹는다.

prefill_tps = 토큰수 / 걸린시간 — 1초에 몇 토큰을 읽어내는가다. 862 t/s 는 "1초에 862토큰 분량의 프롬프트를 소화한다"는 뜻이다.

12배경 개념 ② — KV 캐시란

문제 상황부터

LLM 은 토큰을 하나씩 만드는데, 매 토큰마다 그때까지의 문장 전체를 다시 본다.

"서울"   을 만들려면 → [질문 611토큰] 을 본다
"특별시" 를 만들려면 → [질문 611토큰 + "서울"] 을 본다
"의"     를 만들려면 → [질문 611토큰 + "서울" + "특별시"] 을 본다
...

순진하게 짜면 토큰 하나 만들 때마다 611토큰을 처음부터 다시 계산한다. 50토큰짜리 답이면 같은 계산을 50번 반복하는 셈이다.

해결 = KV 캐시

핵심 관찰

이미 지나간 토큰의 계산 결과는 절대 안 변한다. "서울"이라는 새 토큰이 붙어도 611번째 토큰의 계산 결과는 그대로다 — LLM 은 왼쪽→오른쪽으로만 보기 때문에, 앞 토큰이 뒤 토큰의 영향을 받지 않는다. 그러니 한 번 계산해서 저장해 두고 재사용하면 된다.

prefill:  611토큰을 한 번 계산 → 611개분 K/V 를 저장   ← 이게 KV 캐시
decode:   새 토큰 1개만 계산  → 캐시에 1칸씩 덧붙임

K 와 V 는 뭔가 — 도서관 비유

Attention(주의 집중)에서 각 토큰은 세 가지 역할을 한다.

이름도서관 비유
QQuery (질의)"나는 지금 이런 걸 찾고 있다" — 검색어
KKey (색인)"나는 이런 내용의 책이다" — 책등 라벨
VValue (내용)실제 책 내용

새 토큰을 만들 때, 그 토큰의 Q 로 앞의 모든 토큰의 K 를 훑어 "누가 관련 있나"를 점수 매기고, 점수가 높은 토큰의 V 를 가져와 섞는다.

여기서 Q 는 매번 새로 만들지만(지금 찾는 게 매번 다르니까), K 와 V 는 고정이다. 611번 토큰의 "책등 라벨"과 "내용"은 영원히 안 변한다. 그래서 K 와 V 만 저장한다 → KV 캐시.

크기 감각 — n_ctx 를 크게 잡으면 손해인 이유

캐시 크기는 n_ctx(최대 문맥 길이)에 비례해 미리 통째로 잡아 둔다. config.py:304:

GEN_N_CTX = 2048    # top-3 x 128토큰이면 충분. 크게 잡을수록 손해

SimpleRAG 의 Qwen3 는 토큰 1개당 KV 캐시가 112 KiB 다. 그래서 n_ctx=2048 이면 224 MiB, n_ctx=32768 이면 실제로 611토큰만 쓰더라도 3.5 GiB 를 미리 예약한다. iGPU 는 시스템 메모리를 공유하므로 더 아프다. RAG 는 검색된 근거 3건만 넣으니 2048 이면 충분하다. 계산 방법과 실측은 14장에 따로 정리했다.

헷갈리기 쉬운 점

n_ctx 를 키우는 비용은 메모리다. 첫 글자 속도(TTFT)를 늘리는 것은 n_ctx 값이 아니라 실제로 넣은 프롬프트 토큰 수다 — n_ctx 를 4096 으로 올려도 프롬프트가 600토큰이면 prefill 은 거의 그대로다.

SimpleRAG 코드에 KV 캐시가 등장하는 세 곳

① 측정할 때 — 캐시를 일부러 지운다

backend.py:498

llm.reset()   # 앞 측정의 KV 를 재사용하지 않게 — 매번 전체 prefill

llama.cpp 는 프롬프트 앞부분이 이전과 같으면 그 구간의 KV 캐시를 그대로 살려 쓰고 prefill 을 건너뛴다(prefix 재사용). 측정 3회를 그냥 돌리면 2·3회차는 거의 공짜가 되어 "iGPU 가 1000배 빠르다" 같은 엉터리 숫자가 나온다.

② 예열할 때 — 캐시를 일부러 남긴다

①과 정반대다. gguf_generator.py warm() 이 운영과 똑같은 시스템 프롬프트로 1토큰짜리 더미 생성을 미리 돌린다. 답은 버린다 — 결과가 아니라 부수 효과가 목적이다.

[시스템 지시문]   ← 항상 동일 → KV 캐시 재사용 ✅ (prefill 건너뜀)
[근거 문서 3건]   ← 질문마다 다름 → 새로 계산
[사용자 질문]     ← 매번 다름   → 새로 계산
설계 포인트

고정된 부분을 프롬프트 맨 앞에 두었기 때문에 재사용이 가능하다. 순서를 뒤집어 질문을 앞에 두면 이 이득이 통째로 날아간다.

예열은 Vulkan 셰이더 컴파일 비용(새 PC 첫 실행 9.75초)도 함께 흡수한다. 드라이버가 컴파일 결과를 캐시하므로 두 번째 실행부터는 거의 0이다.

③ flash_attn — 캐시를 읽는 방식

flash_attn 은 KV 캐시를 읽으며 attention 을 계산할 때 중간 결과를 메모리에 다 펼치지 않고 조각내어 처리하는 최적화다. 메모리를 덜 쓰고 보통 더 빠르다. 다만 실측이 백엔드마다 갈려 SimpleRAG 는 나눠 놓았다 — CPU True(prefill 1.6배), iGPU False(속도 차 0, 정답률 근소 우위).

한 줄 정리

KV 캐시 = "이미 읽은 부분의 계산 결과를 적어 둔 메모장". prefill 이 이 메모장을 만드는 단계고, decode 는 메모장을 보며 한 칸씩 덧붙이는 단계다. SimpleRAG 는 측정할 땐 메모장을 지워 공정하게 재고, 운영할 땐 시스템 프롬프트분 메모장을 미리 채워 첫 질문을 빠르게 만든다.

13배경 개념 ③ — iGPU 메모리는 몇 GB 인가

iGPU 는 "자기 메모리"가 없다

외장 GPU(dGPU)는 보드에 VRAM 칩이 따로 붙어 있다. iGPU 는 CPU 안에 들어 있어서 메모리 칩이 없다. 그래서 시스템 RAM 을 빌려 쓴다.

[ dGPU ]  CPU ─ RAM(16GB)        GPU ─ VRAM(8GB)     ← 완전히 별개
[ iGPU ]  CPU ─ RAM(16GB) ─ GPU                      ← 같은 RAM 을 나눠 씀
              └─ 여기서 일부를 GPU 몫으로 떼어 감

전용 메모리 vs 공유 메모리

항목뜻일반적 크기
전용 GPU 메모리
Dedicated		 BIOS 가 부팅 때 미리 떼어 고정 예약한 몫
(Intel DVMT Pre-Allocated / AMD UMA Frame Buffer)		 128MB ~ 1GB
(의외로 작다)
공유 GPU 메모리

총 그래픽 메모리

헷갈리기 쉬운 점

전용 메모리가 128MB 라고 해서 iGPU 가 128MB 만 쓰는 게 아니다. DVMT(동적 비디오 메모리 기술)가 부족분을 실시간으로 시스템 RAM 에서 끌어온다. 전용 메모리는 화면 출력용 최소 버퍼일 뿐이고, LLM 을 올릴 때 봐야 할 숫자는 Display Memory 다.

숨은 제약

Vulkan 드라이버는 "한 번에 할당 가능한 최대 크기(maxMemoryAllocationSize)"를 따로 두는데, Intel iGPU 는 흔히 2~4GB 다. 공유 메모리가 8GB 있어도 7B 급 모델(4GB+)을 통째로 올리려다 할당에 실패하는 경우가 이래서 생긴다. SimpleRAG 규모(최대 1.1GB)에서는 걸릴 일이 없다.

14배경 개념 ④ — KV 캐시와 GPU 메모리 계산하기

"이 모델을 이 조건으로 돌리려면 GPU 메모리가 얼마나 필요한가"는 세 덩어리를 더하면 나온다.

필요한 GPU 메모리 = ① 모델 가중치 + ② KV 캐시 + ③ 부가 메모리(연산 버퍼·런타임)

먼저 용어 두 개

용어뜻흔한 오해
문맥 길이입력 프롬프트 + 생성되는 답변 토큰 수입력만 센다 — 답변도 한 토큰씩 만들어질 때마다 KV 캐시에 쌓인다
동시 요청 수같은 순간에 처리 중인 요청 수접속자 수 — 답을 읽는 동안엔 요청이 없으니 실제 동시 요청은 보통 더 적다. 설계는 최악(전원 동시 질문)으로 잡는다

① 모델 가중치

가중치 ≈ 파라미터 수 × 자료형 비트 ÷ 8

fp16 / bf16     : 16비트  → 파라미터 1B 당 2 GB
fp8             :  8비트  → 1B 당 1 GB
Q4_K_M · AWQ 4비트 : 실효 약 4.8비트 → 1B 당 약 0.6 GB  (스케일·임베딩 등 부가정보 포함)

실제로는 모델 파일 크기가 곧 가중치 크기라 그걸 보는 게 가장 정확하다 (예: Qwen3-1.7B-Q4_K_M.gguf 1.1 GB).

② KV 캐시 — 공식

토큰 1개당 KV = 2(K와 V) × 층 수 × KV 헤드 수 × 헤드 차원 × 자료형 바이트(f16 = 2)

전체 KV       = 토큰 1개당 KV × 문맥 길이 × 동시 요청 수

필요한 값 세 개는 모델의 config.json 에 있다.

공식의 항목config.json 키llama.cpp 로그(verbose=True)
층 수num_hidden_layersn_layer
KV 헤드 수num_key_value_headsn_head_kv
헤드 차원head_dim (없으면 hidden_size ÷ num_attention_heads)n_embd_head_k
핵심

KV 캐시는 파라미터 수(0.6B·1.7B)가 아니라 구조(층·KV 헤드·헤드 차원)로 정해진다. 그래서 "가중치의 몇 %" 같은 고정 비율이 없다. 최근 모델이 쓰는 GQA(KV 헤드를 쿼리 헤드보다 적게 — Qwen3 는 쿼리 16 · KV 8)나 MLA(DeepSeek)는 바로 이 토큰당 크기를 줄이려는 설계다.

예시 1 — SimpleRAG 실측 (Qwen3-0.6B / 1.7B, llama.cpp)

Qwen3-0.6B · 1.7B 모두: 층 28 · KV 헤드 8 · 헤드 차원 128
토큰당 = 2 × 28 × 8 × 128 × 2바이트 = 114,688바이트 = 112 KiB
× 2048토큰 = 224 MiB
× 4096토큰 = 448 MiB

두 모델을 실제로 적재해 llama.cpp 가 출력한 값과 정확히 일치한다(CPU 경로):

llama_kv_cache: size = 224.00 MiB (2048 cells, 28 layers, 1/1 seqs), K (f16): 112.00 MiB, V (f16): 112.00 MiB
모델가중치 (적재 실측)KV, n_ctx=2048KV, n_ctx=4096가중치 대비 KV (2048)
Qwen3-0.6B Q4_K_M205 MiB224 MiB448 MiB약 110%
Qwen3-1.7B Q4_K_M646 MiB224 MiB448 MiB약 35%

1.7B 가 더 큰 것은 층 안쪽의 은닉 크기·FFN 폭 때문이고, 이것은 KV 캐시와 무관하다. 그래서 두 모델의 KV 캐시가 같다. 빠름 모드(0.6B)에서는 KV 캐시가 가중치보다 크다 — 가중치는 4비트로 줄였지만 KV 캐시는 여전히 16비트이기 때문이다. GEN_N_CTX 를 작게 잡은 이유가 여기서 가장 분명하게 드러난다.

"가중치의 몇 %" 는 경우마다 다르다

모델 / 조건가중치KV 캐시가중치 대비
Qwen3-0.6B Q4, 문맥 2048, 1요청 (실측)205 MiB224 MiB약 110%
Qwen3-1.7B Q4, 문맥 2048, 1요청 (실측)646 MiB224 MiB약 35%

KV 비중이 커지는 조건은 세 가지다 — 작은 모델을 양자화했을 때, 문맥이 길 때, 동시 요청이 많을 때.

③ 부가 메모리

연산 중간 결과를 담는 버퍼, CUDA 컨텍스트, vLLM 의 CUDA Graph 등이다. 서버용 vLLM 은 경험상 1~3 GB (아래 예시에서는 2 GB 로 잡는다). llama.cpp 소형 모델은 수십~수백 MB 수준이다.

llama.cpp 와 vLLM 은 KV 캐시를 잡는 방식이 다르다

llama.cpp (SimpleRAG)vLLM (GPU 서버)
크기 결정n_ctx × 토큰당 크기 — 사용자가 정함(GPU × gpu_memory_utilization) − 가중치 − 부가 = 남는 전부
할당 방식시작할 때 통째로 예약PagedAttention — 16토큰 블록을 필요할 때 나눠 줌
목적요청 1개를 적은 메모리로많은 요청을 동시에(처리량)
꽉 차면프롬프트가 n_ctx 를 넘으면 오류 → SimpleRAG 는 _fit_prompt 로 근거를 깎아 막는다새 요청은 대기, 진행 중 요청 일부를 선점(preemption)했다가 나중에 다시 계산
조절 손잡이n_ctxgpu_memory_utilization(기본 0.9) · max_model_len · kv_cache_dtype=fp8(절반) · prefix caching

vLLM 의 max_model_len 은 KV 캐시 전체 크기가 아니라 요청 하나의 최대 길이다. 시작할 때 "이 길이 요청 하나라도 들어가는가"만 검사하고, 안 들어가면 값을 줄이라는 오류를 낸다.

주의

Qwen3 의 thinking 모드는 답변 전에 <think> 추론을 수천 토큰 만들 수 있다. 그러면 요청당 2,500 이 아니라 5,000~10,000토큰이 되어 KV 캐시가 2~4배 필요하다. RAG 용도면 thinking 을 끄거나 그만큼 잡아야 한다. 또 같은 27~32B 급이라도 구조가 다르면(KV 헤드 수·층 수, 선형 어텐션 혼합 여부) 토큰당 크기가 몇 배 달라지므로, 모델이 정해지면 반드시 그 모델의 config.json 으로 다시 계산한다.

    GPU KV cache size: 27,800 tokens
Maximum concurrency for 2,500 tokens per request: 11.1x
    첫 줄이 요청당 토큰 × 동시 요청 수(예시 2 는 12,500) 이상이면 조건을 만족한다.
한 줄 정리

GPU 메모리 = 가중치(파일 크기) + 토큰당 KV × (입력+답변) × 동시 요청 + 부가 1~3 GB, vLLM 이면 이것을 0.9 로 나눈다. "가중치의 몇 %"로 어림하지 말고, 동시 요청 수와 문맥 길이로 직접 곱한다.

현재 이 PC 가 무엇으로 답을 만드는지, 왜 그렇게 골랐는지 보여 준다. 인덱스를 열지 않으므로 다른 명령과 겹쳐 실행해도 된다.
